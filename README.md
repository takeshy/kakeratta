# dokking

本を読むAIではなく、**あなたと同じところまで読んでいるAI**。

読む、聞く、その本について聞く、メモを残す。それだけをやる読書アプリです。
小説では、AIは読者が到達した位置までしか知りません。同じ質問でも、100ページ進めば答えが変わります。
技術書では逆に、本の先も、本が書かれた後に変わったことも持ち込みます。

Wails（Go + WebView）の単一実行ファイル。ログイン不要、MITライセンス。
読む・聞く・メモを取る・原文に戻るは、ネットワークもAPIキーもなしで動きます。

## 動かす

```sh
task build      # ビルド（bin/dokking）
task run        # 起動
task test       # go test ./internal/... と node --test tests/
task frontend   # frontend/dist の再生成（バンドラなし、コピーのみ）
```

初回は書棚の「サンプルを読む」で、同梱の短編（`internal/sample`）をすぐ試せます。
保存先は `%AppData%/dokking`（macOS は `~/Library/Application Support/dokking`、Linux は `~/.config/dokking`）。
`DOKKING_HOME` で変更できます。

## カテゴリが先

本を開いてまず決めるのは、小説か技術書かです。決まるまでモデルには何も送りません。

| カテゴリ | AIが見るもの | 読了 |
| --- | --- | --- |
| 小説 | 読んだ区間の本文と、そこまでの要約だけ | `is_completed` で振り返りが解禁される |
| 技術書 | 全文の要約と、Web検索で調べた最新の情報 | 読了の概念を持たない |

**境界は本の属性であり、ペルソナの裁量ではありません**（`internal/book/book.go` の `Category`）。
何をどこまで見せるかはここで決まり、ペルソナは本体が用意したものを参照するだけです。
守らせるのではなく、越える手段を渡していません。

## 読了エントリ（このアプリの中核）

どこまで読んだかを**区間の集合**で持ちます（`internal/book/reading.go`）。

```
ReadEntry[]  102-118（9/11 22:04-22:41） / 119-135（9/12 07:10-07:38）
current_position  50   ← 「あの鍵の場面どこだっけ」で戻っても、区間は動かない
```

- **ページを離れるたびに更新します。** 閉じたときだけだとクラッシュで失われます。
- **ペラペラめくるだけでは記録しません。** 画面に居座った時間が閾値（1ページ12秒相当）を
  超えたら読んだと見なします。判定は Go 側の1か所（`book.RequiredDwell`）にあり、画面は
  「この範囲が何秒そこにあったか」を報告するだけです。
- **連続していて時間が近ければ束ねます。** 日をまたぐ・間が空く（30分）・離れたページに飛ぶ、の
  いずれかで新しいエントリになります。
- **飛ばしたページはAIも知りません。** 読者本人も読んでいないので困りません。

再開位置、読書量、カレンダー、そしてAIに渡す範囲を、すべてこの一つのデータから導きます。
読了判定は `max(entries.end) >= content_end` です。途中に飛ばした区間があっても問いません
（読者本人が読み終えたと思っている以上、穴を理由に振り返りを閉じておく意味はない）。
`content_end` を書籍の終端と分けているのは、あとがき・解説・奥付を含む EPUB で読了判定が
立たなくなるのを避けるためです。

## 位置モデル

```
EPUB ─┐
青空文庫 ─┼→ SectionID / BlockID / CharOffset ─┬→ 表示位置 / 読み上げ位置 / しおり
テキスト ─┘   （+ 比較用の Absolute）          ├→ ハイライト / メモの引用位置
PDF ─────┘                                     ├→ 読了エントリの端点
                                               └→ AIの知識境界
```

**位置を形式間で正規化はしていません。** 1冊は1形式であり、必要なのは同一書籍内で
「ここまで」が比較できることだけです。`Absolute`（本文先頭からの文字数）はその本の中だけで
意味を持つ比較用の値で、別の本や別の形式と突き合わせることはありません。

- オフセットは **本文テキスト（`Block.Plain`）だけ** を数えます。ルビ（`Block.Ruby`）と
  注記（`Block.Notes`）はオフセット付きで別に持ち、表示にだけ使います。表示の装飾を変えても
  しおりは動きません。
- 読むモードと聞くモードは同じ位置を共有します。読み上げの `onboundary` がそのまま現在位置になり、
  声が通り過ぎた範囲は画面をスクロールしたのと同じ「読んだ」になります。
- 表示形式は位置モデルから切り離しています。連続スクロールが既定で、「ページ送り」は同じレイアウトを
  1画面ずつ送る操作です（Space / PageDown / PageUp）。
- 本文はストリーミング表示しません。ストリーミングするのはAIの応答だけです。

## 知識境界

境界は読了エントリの端（`state.Boundary()`）です。前に戻って読み返しても動かないので、
**場面の遡りを使うたびにAIの知識が巻き戻ることはありません**。
判定は `knowledge.Reached(p, boundary)` の一箇所に集約していて、厳密（`<`）です。
章の終わりと次章の先頭は同じ `Absolute` を指すため、「1章を読み終えた」が2章の1文字目を
含んではいけないからです。

会話として続きます（`chat.json`）。「この人だれ」の次に「いつ出てきた?」が成立するのは履歴が
あるからです。各回答は答えた時点の境界を持ち、読み進めた後に見ると「◯% 時点の答え」と表示されます。

**どの経路を使うかはアプリが決めます**（`internal/answer/route.go`）。読者にモードを選ばせません。
まず語句のルールで振り分け、それでも決まらないときだけ軽いモデルに1語で分類させます。
モデルが未設定でもルールだけで必ず答えに辿り着きます。

- 人物・用語、ここまでのあらすじ → **境界までの本文をそのまま渡す**
- 場面の遡り → 章要約で章を特定 → その章のページ要約で当たりをつける → 原文へ
- いまの文脈 → `Book.TextUpTo(from, boundary)`
- 読了後の振り返り → `is_completed` が真になるまで閉じている
- 技術書 → 経路を分けない。全文の要約と Web 検索で答える

### 名寄せを事前に行わない

日本語は呼称のゆらぎ（姓・名・愛称・敬称・訳語）が激しいですが、**同一性を先に解決しません**。
境界までの本文を渡して、モデルにその場で解かせます。

先に全文を処理して人物を統合すると、**統合された知識そのものが境界を越えます**。
「山田太郎」と「謎の男」が同一人物だと確定する位置より前で、その同一性がどこかに存在してしまう。
後から位置でフィルタしても、一度作った統合は取り消せません。読者が本文から読み取れることを、
読者と同じ材料から、同じタイミングで解くのが唯一の筋です。

### 保証範囲

技術的な保証は「アプリから未来の情報を提供しない」ことと、「モデルに先読み禁止を指示する」ことまでです。
モデル自身が有名作品の結末を学習している場合、位置フィルタだけでは漏れを防げません。

**Spoiler Leakage Test（手動）**: 結末が広く知られた作品を取り込み、1章分だけ読んだ状態で
「この人は誰か」「このあとどうなるか」を各経路で20回聞き、未読情報を含む回答の割合を数えます。
同梱サンプル（`internal/sample`）はこのアプリのために書き下ろした短編なので、学習由来の漏れがない対照として使えます。

## 要約

本体が作ります。ペルソナは作りません。要約は本に紐づくので、同じ本に何体入れても一度しか作られません。

### 小説 — 読み進むごとに作る（`internal/pipeline`）

```
読んだ区間が伸びた
   ↓ （6秒バッファ。集中して読んでもキューが詰まらない）
まだ要約されていないページを1200文字ずつ切る
   ↓
軽いモデルで1〜2行のページ要約を作って積み上げる
   ↓
章を読み終えた時点で、その章のページ要約から章要約を作る
```

- **未読の章は積み上げのまま持ちます。** 要約を要約で上書きし続けると情報が痩せ、50ページ目の
  細部が落ちて場面の遡りが効かなくなります。圧縮するのは確定した章だけなので、劣化は読み終えた
  範囲にしか起きません。
- **章の区切りは、構造があればそれを使います。** EPUB・青空文庫・アウトラインを持つ PDF は
  持っている章構造をそのまま使い、無い場合だけページ要約のついでにモデルに「ここで区切りか」を
  返させます（追加の呼び出しは要りません）。
- 1回のパスで要約するのは8ページまでです。取り込んで最終章に飛んだだけで100回呼ばれないように。

### 技術書 — 取り込み時に一度通す

全文が対象なので、読み進みに合わせて作る意味がありません。カテゴリを選んだ時点で章ごとに通します。

**PDF はそのまま渡します**（設定「技術書はPDFのまま渡す」）。コードリスト、表、図、数式が保たれます。
取り込み時に一度通すだけで追記がないため、塊で渡して構いません。
接続先がファイル入力を受けなければ、抽出済みテキストの章ごとの処理に自動で落ちます。
どちらになるかは `internal/llm` と `internal/pipeline` に吸収させていて、呼び出し側は
「この本を通す」としか言いません。

## ペルソナ

配布可能なプラグインです。本ごとに最大3体。内蔵は3体（みかげ・なぎ・こよみ）。

### 宣言するもの

| 項目 | 内容 |
| --- | --- |
| 名前・アイコン・口調 | 表示と応答の性格 |
| 対象カテゴリ | novel / technical |
| Web検索 | 要否 |

**本文へのアクセスは宣言に含まれません。** 何が読めるかは本のカテゴリで既に決まっています。
`persona.json` を「ペルソナを追加」から読み込むと `<workspace>/personas/<id>/` に入ります。

```json
{
  "id": "tsumugi",
  "name": "つむぎ",
  "icon": "📚",
  "tone": "静かな読書仲間。情景に反応し、解釈を押しつけない。",
  "categories": ["novel"],
  "webSearch": false
}
```

### いつ動くか

常駐しません。イベントで起きて、処理して終わります。読者が読んでいない間は何も走りません。

```
ページを読了と判定した / 読者が発言した / 読者がメモを書いた
   ↓
PersonaState を読む（自分のメモと last_processed_position）
   ↓
LLM ── 新しく読んだ分＋自分のメモ＋直近の会話
   ↓
private notes を更新
   ↓
発言するか判断 ── no → 黙る（既定）
   ↓ yes
チャットに出す
```

- **黙るのが既定です。** 毎ページ「これは怪しいですね」と言う相手は鬱陶しいだけです。
  100ページ読んだところで突然「今の発言、42ページで彼が言っていたことと矛盾してない?」と
  来るから一緒に読んでいる感じが出ます。メモに位置が刻まれているので離れた箇所を指せます。
- **コンテキストはペルソナごとに分かれます。** 小説ペルソナの文脈に、読んでいない範囲のテキストが
  物理的に存在しません。フィルタではなく構造で守られます。
- **メモはペルソナ間で共有しません。** 技術書ペルソナは全文を見ているため、そのメモが小説ペルソナに
  渡ると境界が壊れます。
- **読むのは新しく進んだ分だけです。** 過去の理解は private notes に残っているので、3体いても
  本文が多重に乗りません。
- **取り消してもメモと会話は消しません。** 再度追加したときに、続きから読んでいる相手として
  戻れます。消すと同じ本を最初から読み直した別人になります。
- 途中で追加したペルソナにもチャット履歴を渡します。要約は本に紐づくので「読んだところまで」は
  追いつけますが、読者が何を気にしていたかはチャットにしかありません。

### 技術書の「古いかも」

外れると黙っているより有害なので、発火条件を限定しています。

- 陳腐化しうる記述の型（バージョン番号、非推奨・廃止の語）を本文から検出したときだけ起きる
- 根拠は Web 検索の結果からのみ出す。モデルの記憶から固有名詞・バージョンを出さない
- 出典リンクを必須とする。検索結果がなければ発言しない

**Web検索は本体が API として渡します**（`internal/websearch`）。プラグインは検索の実装も鍵も
持ちません。Brave / Tavily / SearXNG に対応し、未設定なら技術書ペルソナは黙ります。

## チャット欄

読書画面の脇に置きます。こちらからの質問も、ペルソナからの反応も、同じ場所に流れます。

- **本文中に注記を差し込みません。** 本文は本文、反応はチャット欄。読む面を壊しません。
- **折り畳めます。** 反応は畳んでいる間も溜まり、開けば残っています。
- **各メッセージは原文へのリンクを持ちます。** 選べばその位置に飛べます。
- **本ごとに残ります。** 遡れば、その本をどう読んだかがそのまま並んでいます。
- 「つぶやく」は答えを求めない発言です。ペルソナが反応することがあります。

## Timeline とカレンダー

**Timeline は自分の発言だけを、本をまたいで時系列に並べます。** AIの返答は同じ本を同じところまで
読めば誰でも似たものが出ますが、自分が何をどこで思ったかは代わりが効きません。残す価値のある側だけを残します。
質問もメモも区別せず全部残します。項目はチャットの該当メッセージにリンクし、そこから原文に飛べます。

**カレンダーは同じデータを日ごとに畳んで見せます。** 読了エントリが読んだ日そのものを持っているので、
黙って読んだ日も空白になりません。持つデータは増えません。

```
82ページ  「この人怪しい」
164ページ 「やっぱり違うかも」
231ページ 正体判明
```

「本を要約して」は誰が聞いても似た回答になりますが、「私がこの本をどう読んだか振り返って」は
その人にしか生成できません。この非対称性がこのアプリ固有の資産になります。

## 音声入力

speech-popup（gemihub-desktop の音声機能の移植版）の実装を**そのまま**持ち込んでいます。
`frontend/src/` の `speech.js` / `recorder.js` / `browser_speech.js` / `live_recognizer.js` /
`pcm_capture.js` / `silence.js` / `replacements.js` / `speech_commands.js` / `send_phrases.js` /
`speech_languages.js` / `meter.js` と、Go 側の `internal/speech`（HTTPプロキシ、ライブ文字起こし、
Vertex OAuth）です。移植元のテストも `tests/` にそのまま置いています（`node --test`、75件）。

- 方式は3つ: ブラウザ音声認識 / 録音して送る音声認識API / ライブ文字起こし（話している途中から文字になる）。
- 接続先は OpenAI、whisper.cpp、OpenAI互換、Gemini API、Vertex AI、Azure。鍵はGo側から送るので、
  WebView に鍵が出ず、ローカルの whisper.cpp でも CORS の問題が起きません。
- 無音での自動停止、送信の合図（`over, オーバー`）、記号コマンド（「クエスチョン」→`?`）、
  置換ルール（`日記書いて => /daily`）まで移植済みです。
- 使い道はこのアプリでは2つ: **メモの口述**と**本への質問**。どちらも送信の合図で確定します。
- 口述メモは話し言葉のまま保存しません。軽いモデルで整えてから保存し、整える前の発話も残します。

## 取り込み

ファイルを置いた時点で行うのは、構造化と索引作りだけです。
要約はカテゴリを選んでから始まります（小説は読み進むごと、技術書は一度に）。

1. 章・節で分割（青空文庫は見出し記法、EPUB は spine、PDF は見出し、テキストは慣習的な見出し）
2. ローカル索引の作成（モデル不要。接続先が未設定でも「あの場面どこ」が動きます）

- バイトやページで機械的に分割しません。章の途中で切ると読みの単位が壊れます。
- 処理中も本文表示とメモは使えます。
- 索引は語単位のローカル索引です。埋め込みモデルもベクトル検索も持ちません。
  探しているのは「駅で変な男に会ったところ」のような出来事であり、要約に書かれる粒度と一致するので、
  場面の遡りは要約の二段絞り込みで行い、索引は要約がまだ無いときの代替として残しています。

## モデル

既定は **Nebius Token Factory 上の NVIDIA Nemotron** です
（`https://api.tokenfactory.nebius.com/v1` / `nvidia/nemotron-3-super-120b-a12b`）。
[Nebius x NVIDIA Global AI Hackathon](https://nebiusglobalaihackathon.devpost.com/) の要件
（Nebius 上で動かし、NVIDIA のオープンソースモデルを1つ以上使う）を満たす構成です。

実行場所は設定で切り替えられます。

| 実行場所 | 既定のエンドポイント |
| --- | --- |
| Nebius Token Factory（既定） | `https://api.tokenfactory.nebius.com/v1` |
| OpenAI 互換 | `https://api.openai.com/v1` |
| ローカルLLM: Ollama | `http://127.0.0.1:11434/v1` |
| ローカルLLM: LM Studio | `http://127.0.0.1:1234/v1` |
| ローカルLLM: vLLM | `http://127.0.0.1:8000/v1` |
| ローカルLLM: AnythingLLM | `http://127.0.0.1:3001/api/v1/openai` |
| ローカルLLM: OpenCode | `http://127.0.0.1:4096`（セッションAPI。モデルは `<providerID>/<modelID>`） |

OpenCode だけは chat completions ではなくセッションAPIなので、`internal/llm/opencode.go` が
その差を吸収します。呼び出し側はどの実行場所でも「モデル名で頼む」だけです。
モデル一覧は設定画面の「モデル一覧を取得」で `/v1/models` から取ってきて補完に使います。

| 用途 | 負荷 | 設定項目 |
| --- | --- | --- |
| ページ要約 | 軽（1ページ＋直前の数行） | 軽いモデル |
| 章の再要約 | 軽〜中（1章1回） | 軽いモデル |
| メモの整形、経路の判定、章の絞り込み | 軽 | 軽いモデル |
| 質問への回答 | 中〜重（入力が長い） | 回答モデル |
| ペルソナの反応 | 中 | 回答モデル |
| 読了後の総括 | 重（全文＋全メモ） | 重いモデル |
| 音声認識 | 専用モデル | 音声入力の設定 |
| 読み上げ | ブラウザ内蔵（Web Speech API） | — |

**マルチモーダルが要るのは技術書を扱う場合だけです。** 小説はテキストで完結するので、
小説しか読まない人にマルチモーダルを要求しません。

**プレフィックスキャッシュとの相性がいい構造です。** 読了エントリは伸びる一方なので、渡す内容は
常に前回の続きが足されるだけで、current_position が戻っても渡す内容は変わりません。
ただしキャッシュの寿命は数分〜1時間程度が一般的で、翌日開き直せば一から乗せ直しになります。

Nebius Token Factory に文字起こしAPIはないので、音声入力の接続先は別に持ちます。

## データ

すべて JSON ファイルです。パブリックドメイン作品は取り込み結果がそのまま共有できます
（本の ID は内容のハッシュなので、同じファイルなら同じ ID になります）。

```
<workspace>/settings.json
<workspace>/personas/<id>/persona.json   追加したペルソナ
<workspace>/books/<bookId>/book.json     構造化した本文（カテゴリを含む）
```

### PDF

PDF はテキストとして扱います（`internal/ingest/pdf.go` ほか、依存なしの自前実装）。
技術書では、これに加えて原本をそのままモデルに渡す経路があります。

- 相互参照表（xref）は読みません。壊れた xref・追記更新・xref ストリームのいずれでもオブジェクト自体は
  ファイルにあるため、走査して拾います。PDF 1.5+ のオブジェクトストリーム（ObjStm）は展開します。
- 対応フィルタは FlateDecode / ASCIIHexDecode / ASCII85Decode と PNG プレディクタ。
- 文字の復元は ToUnicode CMap（bfchar / bfrange）を最優先し、単純フォントは Differences → WinAnsi の順に
  フォールバックします。対応が取れない符号は推測せず `�` にします。
- フォント幅（単純フォントの `/Widths`、合成フォントの `/W` と `/DW`）を読み、描画でペンがどれだけ進んだかを
  追跡します。これがないと、和文組版が1文字ずつ配置する欧文（`Web` や `Ruby(Rails)`）が
  「W e b」のように空白だらけになります。
- 行の折り返しは結合し、段落は「大きな行間」と「行頭の全角字下げ」で区切ります。
  ページ番号は表示用の注記（`p.12`）として本文位置に紐づけて残します。**注記は本文ではない**ので、
  索引にも読み上げにもAIにも渡りません。
- **読み上げはテキストレイヤーの品質に依存します。** 画像PDFと、ToUnicode CMap 欠落で文字化けする
  PDF では読むモードのみ提供します。多段組・縦書きで読み順が崩れる問題は残りますが、影響は
  読み上げに限られます。引用は範囲選択のアンカーであり、読み順を要求しません。
- テキストを含まないPDF（スキャン画像）は、空のページとして取り込まず、その旨を伝えて拒否します。
- 未対応: 埋め込み画像・挿絵の抽出、ベクター描画の図、テキストで組まれた表、LZWDecode、暗号化PDF。

### 意図的にやらないこと

- **埋め込みモデル・ベクトル検索**: 場面の遡りは章要約とページ要約の二段で絞ります。
- **事前の名寄せ**: 同一性は読者と同じ材料から、聞かれた時点で解きます。
- ワークフロー、ダッシュボード、タスク管理、Kanban、推薦・選書、独自TTS基盤、DRM書籍。
