# AIまわりで苦労したこと

[README](../README_ja.md) · [English](ai-lessons.md) · [中で起きていること](technical_ja.md)

Kakeratta は、投稿を小さなAIの担当（ペルソナ）に渡し、担当は自分のメモに覚え、ときどき発言します。
モデルは Nebius Token Factory 上の NVIDIA Nemotron です。このページは、それを信頼できる形にするまでに何が起き、
それぞれにどう対処したかの記録です。以下の問題はすべて、実機での実行か本番データで実際に起きたものです。
どの修正にもテストがあり、主なものは修正を外すとテストが落ちることまで確かめています。

先に要点を書くと、**うまくいかなかった原因のほとんどは、モデルが考えられないことではありませんでした。**
プロンプト・スキーマ・例が見せたことを、見せるべきでない場面でモデルがそのとおりに使った。
そしてアプリ側に、それが起きたことを知る手段が無かった。この2つです。

## 最終的な形

```
投稿 / 返信
 ↓ 画像は1回だけ読む                     （GLM-5.3-Flash）
 ↓ 振り分け        Nemotron Super（任意でJev）が担当ごとの振り分け条件と照合する
 ↓ 届いた担当が並列に1ターンずつ         （深さは明示的な語句で決める。読むのはSuper、deepな依頼・AlwaysUltraの回答はUltra）
     read     → 今の事実・最近の記録・前の記録・過去の投稿検索・Web検索・店探し・経路を読む
     answer   → 回答の本文と出典に加え、予定権限があれば予定が要るかを決める
     plan     → 予定の変更を提案し、型・持ち主・時刻をコードで検査する
     review   → 予定がある場合だけ Nemotron Super が計画を確認する
     execute  → 失敗した変更で止まり、実行が成功したあとで回答を公開する
     memory   → 関連するユーザーのターンでは、黙ったときも公開後に別のメモ係が記憶の要否と内容を決める
 ↓ 1日1回: 本体がその日の投稿をまとめ、記憶のある担当が全員そのまとめを読んでチェックインする
 ↓ 振り分け1回・担当のターン1回ごとに構造化ログを1行。振り分けの判断は投稿ごとに保存する
```

## 1. 文章で決めた約束は、文章で守られた

最初、担当は返事の中にJSON（`{"action":"tool","tool":"schedule",...}`）を書き、アプリがそれを解析していました。
細かな用事を扱う plana は、「今夜ドラマを見る」のような投稿で自分を起こす予定を置くはずでしたが、
代わりにメモへ時刻を文字として書き（`予定: 22:30`）、予定は1件も作られませんでした。
モデルから見れば、メモの1行も道具の呼び出しも、どちらも自分が書いた文字だったからです。

**対処:** Token Factory のネイティブな tool calling に移し、`tool_choice: "required"` を付けました。
移行前に、Nemotron の各段が実際に `tool_calls` を返し、`required` を守ることを確かめています。
発言も道具にし、黙ることを「欄が空だった」ではなく、担当が選ぶ行為にしました。

## 2. 動かない道具

tool calling にしても、plana は投稿から予定を置けませんでした。投稿に反応するときの道具一式だけ、
予定の保存先を渡し忘れていたためです（起床のときの経路には渡っていました）。道具は提示され、呼ばれ、
「schedule が設定されていません」と返り、plana は残った手段としてメモに作り話のid（`s_xxx`）を書きました。

**学び:** 壊れた道具を避けようとするモデルは、ふるまいのおかしいモデルとまったく同じに見えます。
修正は1行でしたが、見つけるには本番データを読む必要がありました。

## 3. 振り分けが正しい答えを捨てていた

- 振り分けのモデルは `plana`（人が見る名前）と答えていましたが、idは `routine` です。
  知らないidは「振り分け失敗→全員に渡す」扱いだったので、食事の担当が薬の投稿に答え続けていました。
- 振り分けのプロンプトは「迷ったら渡す」でした。以前、誤って「渡さない」と判断して投稿が埋もれたからです。
  実際には「明日9:10に神谷町に着きたい」がワインの担当に渡っていました。
- 振り分けの呼び出しが失敗すると全員に渡していました。これは振り分けが防ぐはずの騒がしさそのもので、
  しかも「全員」がモデルの選択なのか失敗なのかを区別する記録がありませんでした。

**対処:** 振り分けは、投稿が本当に属する担当にだけ渡します。
idだけでなく名前でも担当を解決し、誰にも当てはまらない名前は推測せず無視し、失敗したら誰にも渡しません
（`@` で名指しした担当には必ず届きます）。判断は担当ごとの理由つきでログに残します。
このログの最初の1行で、ある投稿が6人全員に渡った理由（振り分けが `plana` と答えていたこと）が分かりました。

これを調べているあいだ、振り分けは Nemotron Ultra に移していました。問題は見えやすくなりましたが、
振り分けは投稿のたびに走ります。小さな思いつきを残すのにためらわせるような重さは、個人のメモ帳にはふさわしくありません。
振り分けが見るものを、担当ごとの短い振り分け条件（担当が果たすべきことではなく、受け取るべき投稿）に絞り、
特定の場面へモデルを引っぱる例も外しました。そのうえで本番の投稿20件を流し直すと、Super は1回あたり1.91秒・約0.098円、
Ultra は2.28秒・0.449円で、既定は Super に戻しました（[2026-09-19の比較](routing-model-comparison-2026-09-19_ja.md)）。

**学び:** 大きいモデルなら正しく振り分け、小さいモデルだと間違えるなら、振り分けの課題そのものが曖昧なのかもしれません。
モデルにお金を払う前に、課題を変える。

## 4. 決めることと、実行することが同時だった

道具を1つずつ呼ぶ担当には、「ドラマを見たとメモに書こう」と、実際にそう書かれたメモのあいだに何もありません。
実機では、まだ始まっていないドラマに `2026-09-16 22:21 済` と書き、
22:30に起きる予定を何も置かないまま「22:30ごろに聞くね」と発言しました。

**対処:** 担当は、書き込みと発言を順に並べた **workflow** を提出し、本体がそれを確認してから実行します。
初期の版では、確認の**あと**で `compose` ステップが発言の文面を作れました。最初の実機では、その隙間を通って、
予定の無い時刻の約束が出ていきました。今は、確認する時点で workflow のすべての文面が確定していて、
メモやWeb検索を読むのは workflow の前に済ませます。

本体側の実行は機械的です。上から順に実行し、失敗したステップで止め、`speak` は必ず最後に置きます。
これで、前提が成り立たなかった発言が出ていくことはありません。

## 5. 離れてはいけない2つを、1つのステップに

workflow を作るきっかけになった失敗は、「22:30」と書いたメモがあるのに、22:30に起きる予定が無いことでした。
2か所への2つの書き込みです。`write_schedule` は、予定を置くことと、その根拠のメモを書くことを1つのステップで行い、
メモが書けなければ予定を取り消します。取り消しの処理を外すとテストが落ちることも確かめています。

## 6. 構造化出力は、任意の項目を丸ごと省いた

ステップのスキーマで必須を `type` だけにしていたところ、実機では `{"type":"notes_write"}` だけのステップが返ってきました。
スキーマに沿うよう出力を制約すると、任意の項目は省かれてしまいます。自由な形の `args` オブジェクトも、
同じ理由で `{}` になりがちです。

**対処:** ステップのすべての項目を必須にし、使わない項目は空の値にしました。道具の引数は、
JSONオブジェクトを文字列にして渡します。

## 7. モデルは、見せたものを使う

別々に起きた3つの失敗が、同じ原因でした。

- 仕様に載せた経路検索の例が `"mode":"foot"` でした。実機の移動の担当はそれを毎回そのまま写し、
  本番では「徒歩で約259分」と答えていました。今は例に手段を書かず、担当が投稿と距離から手段を選びます
  （徒歩30分以内なら徒歩、1時間以上なら車、その間は両方）。
- 共通のプロンプトに「1時間後。」を使った例がありました。ランチの相談を受けた担当が、
  メモと発言に「1時間後に着く」と書きました。これは確認で止まりました。
- workflow のスキーマが全員に `tool` ステップを見せていて、仕様にもその下にWeb検索が載っていました。
  Ultra で動く担当が、workflow の中にWeb検索を入れました。

**対処:** workflow のスキーマと仕様の文章を、担当が持つ道具に合わせて担当ごとに組み立てます。
予定を置けない担当には `write_schedule` も `at` の項目も見せません。調べるだけの道具
（Web検索・店探し・経路・過去の投稿検索）は読む段階にだけあり、どの担当にも workflow のステップとしては見せません。
仕様の各ステップには、正しい例と、実機で実際に起きた間違いを載せています。

## 8. 確認役は狭く、そして確認役も確かめる

好みまで判定する確認役は、2人目の担当になってしまいます。以前は、回答の内容・言語や記憶の書き換えまで確認役に見せていました。
ある実機では、担当の発言が自分の作業計画（「神谷町駅周辺のランチ情報をWeb検索で探す」。要約と一字一句同じ）になっていたのに、
確認役は「店をいくつか挙げる発言」だと思い込んで通しました。当時は、要約と同じ発言をコードで差し戻し、確認役に発言の文面を引用させる対処をしました。

現在は、回答の確定、予定の計画、実行、公開、記憶の更新を分けています。
型・件数・権限・引数や既存予定のIDは、先にコードで検査します。モデルによる確認は、計画に予定がある場合だけです。
予定を作る権限があっても、計画に予定がなければ省略します。確認役は、変更がユーザーの依頼や回答の約束に沿っているか、操作どうしが矛盾せず依存を満たすかを見ます。
回答の品質・長さ・調査結果や記憶の更新はレビューしません。メモ係は公開後に別途動きます。
[現在のターン処理（英語）](system/personas.md#from-research-to-answer-publication)も参照してください。

**学び:** コードで確かめられることは、先にコードで確かめる。モデルに確認させるのは、コードで確かめられないことだけ。

## 9. 間違った理由でターンを終わらせていた回数制限

- 形の誤り（workflow にWeb検索を入れた）で差し戻された案が、確認役のための案の回数を使い切り、
  次の案を確認役が差し戻したところで、直す機会が残っていませんでした。形の差し戻しは、確認での差し戻しと別に数えるようにしました。
- 担当が、失敗し続ける地図検索を読める回数ぶん繰り返し、持っていたWeb検索を一度も試しませんでした。
  今は、読んだ結果の後ろに残りの回数と他に使える道具を添え、同じ呼び出しが同じ理由で失敗したらそう明示します。
  次の実機では、2回失敗したあとでWeb検索に切り替えました。

## 10. 担当ごとのモデルの段をやめ、明示的な依頼で回答の深さを決める

以前は担当ごとに段を持たせていました。low は Nemotron 3.5 Lightning で、メモ・Web検索・発言を直接呼びました。
read → workflow の構造でいちばんつまずいたのが、いちばん小さいモデルだったからです。middle と high は
Super と Ultra で workflow を通しました。その結果、ターンの動き方が2通りになり、low の担当には道具を持たせない決まりが要り、
担当を作る人は、その担当に来る投稿がどれくらい難しいかを当て推量で決める必要がありました。

現在の内蔵モデルは通常 Super で、届いた担当が並列に動きます。**常に熟考する** がオンなら、通常の依頼も最終回答を Ultra で生成します。深さは最初のモデル呼び出しより前に、今回の投稿の「詳しく」「in detail」などの明示的な語句、または AlwaysUltra で決めます。モデルが深さを選んだり、先に調査計画を出したりする処理はありません。通常はread 10回・Web検索2回、deep・AlwaysUltraは最初から20回・4回です。

通常のターンは Super が読み取りと回答を同じループで行います。deepで独自の調査ツールがある担当は Super で調べ、Ultra で最終回答を作ります。インフォグラフィックのように独自の調査ツールがない担当は、Ultra が読み取りと回答を同じループで行います。調査の各roundでWeb検索の実残数を伝え、使い切った検索や利用不能なreadをschemaから外します。Web検索が0回でも、別のreadや回答の提出（分離した調査中なら `finish_read`）はできます。予定の計画は Super で行い、予定が含まれる計画だけモデルが確認します。

以前の独立したLightning判定は、2026-09-22の合成返信15件では15/15、平均0.67秒（Superは15/15、1.30秒、費用約5倍）でした。しかし実利用では短い「詳しく」をfalseにする例があり、現在は独立した判定callを廃止しました。発言には最終回答のモデル枠を残し、Ultraの答えに印を付けます。

**学んだこと:** 深さの判断には、はっきりした決まりが必要です。依頼の明示的な語句と AlwaysUltra で選ぶと、判定だけの追加callを使わずにモデルの選択を予測できます。

## 11. 実データを壊していた小さなこと

- プロンプトとメモに、サーバーのUTCが漏れていました。今は、利用者のタイムゾーンを担当に伝えます。
- メモの改行がエスケープされたまま（`\n` が2文字）だったり、frontmatter が字下げされていたりして、
  読めない・種類が分からないメモになっていました。どちらも、担当の意図を変えずに書き込み時に直します。
- 利用者が投稿を消したあとの片付けのために起こした担当が、新しい投稿（「ドラマ、見てる？」）を出していました。
  片付けの起床は発言しないターンにし、`speak` 自体を渡さないようにしました。
- 起床のたびに担当へメモの一覧をすべて渡していたので、覚えるほどプロンプトが膨らんでいました。
  今は `index.md` とメモの件数だけを渡します。入口は index で、`notes_list` は新しい順に100件ずつです。
- 振り分けた直後から、届いた担当が全員「呼ばれましたが、黙っていました」と表示されていました。本番でだけです。
  Firestore は空の配列を nil のスライスとして返し、アプリは nil を「ターンを記録していない古いレコード」の目印にしていました。
  ローカル開発は JSON で保存するので両者は区別され、テストでは再現しませんでした。今はレコード自身が、ターンを記録していると示します。

## 12. 担当の答えが、担当の記憶になっていた

投稿に発言する担当はメモを残さなければならない、という決まりがあります。意見だけあって覚えていない担当は
おかしいからです。この決まりは正しく、副作用がありました。「草加に行く途中でランチどこがいい？」と聞かれた
食の担当は、検索して3軒を提案し、メモが要るのでその3軒を書きました。そのメモにユーザーのことは何もありません。
丁寧に答えるほど、記憶の中身は担当自身の出力になり、次に起きたときにはそれを学んだことのように読み返していました。

直し方は、何を残すかの判断を良くすることではありませんでした。メモに寿命を付けました。担当が自分で調べて
書いたメモには翌日の `expires` が付き、本体がその日に消します。ユーザーの返事があれば担当がこの行を外して
書き直し、それが記憶になります。ユーザーが言ったことのメモには、担当が内容から決めた `review` の日付を
付けられます。行きたい店なら数週間、関心のある話題なら数か月です。過ぎると担当が自分の投稿で「そろそろ
忘れていい？」と聞きます。本体はこちらを消しません。何を残すかを間違えても勝手に治るようになり、期限は
捨てる時刻ではなく、最後にもう一度ユーザーに戻す時刻になりました。

ついでに2つ直りました。担当が自分で立てた投稿への返事は、ほかの投稿と同じく振り分けを通っていて、誰にも
届かないことがよくありました。今は必ず作者に届きます。また「もういい」に `forget_note` と一言で答えると、
忘れることは「何かを残した」に数えられず、メモ必須の決まりに引っかかっていました。今は数えます。

## 13. 担当が自分で書く「1つのものに1つのメモ」は、読める形を保てなかった

記憶は最初、担当が自分で持つ OKF のバンドルでした。1つのものに1つのメモ、探す入口の `index.md`、
読むメモを選んで書き込みと削除を提案するメモ係です。本体が確かめるようになったことの多くは、これを
まとめておくためのものでした。1つの題名に1つのメモ、分類にある型、どのメモも索引の見出しの下に、
ターンのたびの索引の修復、統合したときの出典の引き継ぎ。それでも崩れていきました。1つのものが別の
path に分かれ、索引は2つ目の記憶のように膨らみ、担当は索引と数件のメモだけを読んで残りを見落としました。

次の形は2つで、どちらも本体が書くものでした。スキルが決めた分野ごとのまとめ1つ（2000字以内。かけらで変わるたびに
全文を書き直す）と、かけらごとの1行（1文、タグ、たどれる投稿。担当が返事をしたならその返事、しなかったならかけら自身）です。
当時のメモ係は1回の呼び出しで、1文・タグ・変わるまとめを出すだけで、それ以上読めず、path も選べませんでした。
記録はかつての索引の1行にあたり、12 の寿命もこちらに移りました。その場で用が済むかけら（「今日のランチどこがいい？」）には `expires`、
いつまで要るか分からないユーザーの話には `review` を付け、どちらも担当が投稿のために読み返すと延びます。

古いメモの移行は、動いている本体にはさせませんでした。使い捨てのコマンドで担当のモデルに下書きを作らせ、人が読みました。
最初の下書きは担当が調べた数値や解説を残し、ユーザーが贈った品のことを落としていました。直した下書きだけを書き込みました。
自分の古いメモをまとめさせると、モデルは自分が書いたものを残します。人が見る必要があります。

この形も長くは続きませんでした。かけらのたびに全文を書き直すまとめは、気づかないうちに細部を1つずつ落としますし、
削除したかけらの内容をまとめ文から外すにもモデルが要りました。次に、分野を事実の一覧で持つ形に変えました。1件1行で根拠のかけらが付き、
`add`・`update`・`invalidate`・`merge` で変えるので、明示した操作だけが適用されます。後の形では、当てはまらなくなった事実は履歴を残さず消すようにしました。
かけらを消せば、それだけを根拠にしていた事実はコードで消えます。この時点ではまとめ文を残しました。利用者が分野についての担当自身の見立てを
読みたかったからです。ただし、かけらのたびではなく担当のチェックインのときに、変わった事実をもとに書き直していました。

10月17日には、別のまとめ文もなくしました。今は担当ごとに1つの `Memo.md` に、今の事実とかけらの記録を持ちます。
事実は合計4,000字、1件200字までで、根拠のある傾向・条件・例外・役立つ変化も残します。通常の会話では短いタグ付きの記録だけを追加し、

## 14. これらを見つけられたのは、ログがあったから

振り分けの判断と、担当のターンごとに、構造化ログを1件書きます。誰をなぜ起こしたか、何を読んだか、
workflow の各案とその問題点・確認結果、実行した各ステップ、発言の内容です。上の修正の多くは、このログの1行から始まりました。
ログが無かったころは、「振り分けが全員を選んだ」と「振り分けが失敗した」の区別すらつきませんでした。

振り分けの判断は投稿ごとにも保存し、タイムラインから見られます。誰を選び、誰をなぜ選ばなかったかです。
利用者が「呼ばれるべきだった」「呼ばれるべきではなかった」と指摘すると、その担当の振り分け条件を書き直し、
保存する前に同じ投稿でもう一度振り分けを試します。変わるのは条件だけで、黙って何かを学習することはありません。

テストには1つの決まりを置きました。修正のテストは、その修正を外したら落ちなければいけない、です。
新しいテストが間違った理由で通っていたことが2回ありました。1回は、テストの台本のJSONが壊れていて、
確かめたい場面が一度も実行されていなかったためです。どちらも、元のコードで落ちるまで書き直しました。
