# AIまわりで苦労したこと

[README](../README_ja.md) · [English](ai-lessons.md) · [設計とペルソナ](architecture_ja.md)

Kakeratta は、投稿を小さなAIの担当（ペルソナ）に渡し、担当は自分のメモに覚え、ときどき発言します。
モデルは Nebius Token Factory 上の NVIDIA Nemotron です。このページは、それを信頼できる形にするまでに何が起き、
それぞれにどう対処したかの記録です。以下の問題はすべて、実機での実行か本番データで実際に起きたものです。
どの修正にもテストがあり、主なものは修正を外すとテストが落ちることまで確かめています。

先に要点を書くと、**うまくいかなかった原因のほとんどは、モデルが考えられないことではありませんでした。**
プロンプト・スキーマ・例が見せたことを、見せるべきでない場面でモデルがそのとおりに使った。
そしてアプリ側に、それが起きたことを知る手段が無かった。この2つです。

## 最終的な形

```
投稿
 ↓ 振り分け        Nemotron Ultra が、担当ごとの理由つきで渡す先を決める
 ↓ 担当ごと:
     low            メモ・Web検索・発言を直接呼ぶ。確認なし                 （Nemotron 3.5 Lightning）
     middle / high  read     → メモ・Web検索・店探し・経路・元画像を読む      （Nemotron Super / Ultra）
                    workflow → 書き込みと発言を、文面を確定させて並べる
                    コードで検査し、Nemotron Ultra が確認する
                    上から順に実行し、失敗したステップで止まる
 ↓ 振り分け1回・担当のターン1回ごとに、構造化ログを1行
```

## 1. 文章で決めた約束は、文章で守られた

最初、担当は返事の中にJSON（`{"action":"tool","tool":"schedule",...}`）を書き、アプリがそれを解析していました。
細かな用事を扱う plana は、「今夜ドラマを見る」のような投稿で自分を起こす予定を置くはずでしたが、
代わりにメモへ時刻を文字として書き（`予定: 22:30`）、予定は1件も作られませんでした。
モデルから見れば、メモの1行も道具の呼び出しも、どちらも自分が書いた文字だったからです。

**対処:** Token Factory のネイティブな tool calling に移し、`tool_choice: "required"` を付けました。
移行前に、Nemotron の各段が実際に `tool_calls` を返し、`required` を守ることを確かめています。
発言も道具にし、黙ることを「欄が空だった」ではなく、担当が選ぶ行為にしました。

## 2. 動かない道具

tool calling にしても、plana は投稿から予定を置けませんでした。投稿に反応するときの道具一式だけ、
予定の保存先を渡し忘れていたためです（起床のときの経路には渡っていました）。道具は提示され、呼ばれ、
「schedule が設定されていません」と返り、plana は残った手段としてメモに作り話のid（`s_xxx`）を書きました。

**学び:** 壊れた道具を避けようとするモデルは、ふるまいのおかしいモデルとまったく同じに見えます。
修正は1行でしたが、見つけるには本番データを読む必要がありました。

## 3. 振り分けが正しい答えを捨てていた

- 振り分けのモデルは `plana`（人が見る名前）と答えていましたが、idは `routine` です。
  知らないidは「振り分け失敗→全員に渡す」扱いだったので、食事の担当が薬の投稿に答え続けていました。
- 振り分けのプロンプトは「迷ったら渡す」でした。以前、誤って「渡さない」と判断して投稿が埋もれたからです。
  実際には「明日9:10に神谷町に着きたい」がワインの担当に渡っていました。
- 振り分けの呼び出しが失敗すると全員に渡していました。これは振り分けが防ぐはずの騒がしさそのもので、
  しかも「全員」がモデルの選択なのか失敗なのかを区別する記録がありませんでした。

**対処:** 振り分けは設定の中で最も賢いモデル（Nemotron Ultra）が行い、投稿が本当に属する担当にだけ渡します。
idだけでなく名前でも担当を解決し、誰にも当てはまらない名前は推測せず無視し、失敗したら誰にも渡しません
（`@` で名指しした担当には必ず届きます）。判断は担当ごとの理由つきでログに残します。
このログの最初の1行で、ある投稿が6人全員に渡った理由（振り分けが `plana` と答えていたこと）が分かりました。

## 4. 決めることと、実行することが同時だった

道具を1つずつ呼ぶ担当には、「ドラマを見たとメモに書こう」と、実際にそう書かれたメモのあいだに何もありません。
実機では、まだ始まっていないドラマに `2026-09-16 22:21 済` と書き、
22:30に起きる予定を何も置かないまま「22:30ごろに聞くね」と発言しました。

**対処:** 担当は、書き込みと発言を順に並べた **workflow** を提出し、本体がそれを確認してから実行します。
初期の版では、確認の**あと**で `compose` ステップが発言の文面を作れました。最初の実機では、その隙間を通って、
予定の無い時刻の約束が出ていきました。今は、確認する時点で workflow のすべての文面が確定していて、
メモやWeb検索を読むのは workflow の前に済ませます。

本体側の実行は機械的です。上から順に実行し、失敗したステップで止め、`speak` は必ず最後に置きます。
これで、前提が成り立たなかった発言が出ていくことはありません。

## 5. 離れてはいけない2つを、1つのステップに

workflow を作るきっかけになった失敗は、「22:30」と書いたメモがあるのに、22:30に起きる予定が無いことでした。
2か所への2つの書き込みです。`write_schedule` は、予定を置くことと、その根拠のメモを書くことを1つのステップで行い、
メモが書けなければ予定を取り消します。取り消しの処理を外すとテストが落ちることも確かめています。

## 6. 構造化出力は、任意の項目を丸ごと省いた

ステップのスキーマで必須を `type` だけにしていたところ、実機では `{"type":"notes_write"}` だけのステップが返ってきました。
スキーマに沿うよう出力を制約すると、任意の項目は省かれてしまいます。自由な形の `args` オブジェクトも、
同じ理由で `{}` になりがちです。

**対処:** ステップのすべての項目を必須にし、使わない項目は空の値にしました。道具の引数は、
JSONオブジェクトを文字列にして渡します。

## 7. モデルは、見せたものを使う

別々に起きた3つの失敗が、同じ原因でした。

- 仕様に載せた経路検索の例が `"mode":"foot"` でした。実機の移動の担当はそれを毎回そのまま写し、
  本番では「徒歩で約259分」と答えていました。今は例に手段を書かず、担当が投稿と距離から手段を選びます
  （徒歩30分以内なら徒歩、1時間以上なら車、その間は両方）。
- 共通のプロンプトに「1時間後。」を使った例がありました。ランチの相談を受けた担当が、
  メモと発言に「1時間後に着く」と書きました。これは確認で止まりました。
- workflow のスキーマが全員に `tool` ステップを見せていて、仕様にもその下にWeb検索が載っていました。
  Ultra で動く担当が、workflow の中にWeb検索を入れました。

**対処:** workflow のスキーマと仕様の文章を、担当が持つ道具に合わせて担当ごとに組み立てます。
予定を置けない担当には `write_schedule` も `at` の項目も見せません。調べるだけの道具
（Web検索・店探し・経路・過去の投稿検索）は読む段階にだけあり、どの担当にも workflow のステップとしては見せません。
仕様の各ステップには、正しい例と、実機で実際に起きた間違いを載せています。

## 8. 確認役は狭く、そして確認役も確かめる

好みまで判定する確認役は、2人目の担当になってしまいます。ここでの確認役が見るのは、困ることだけです。
起きていないこと・読んだ内容に無いことを事実として書いている、ありもしないid、置いていない時刻の約束、
投稿と違う言語での発言、読まずにメモを丸ごと書き換えている、担当自身への指示に反している、です。

それでも確認役は間違えました。ある実機では、担当の発言が自分の作業計画
（「神谷町駅周辺のランチ情報をWeb検索で探す」。要約と一字一句同じ）になっていたのに、
確認役は「店をいくつか挙げる発言」だと思い込んで通しました。今は、要約と同じ発言はコードで差し戻し、
確認役には判定の前に発言の文面を引用させています。

**学び:** コードで確かめられることは、先にコードで確かめる。モデルに確認させるのは、コードで確かめられないことだけ。

## 9. 間違った理由でターンを終わらせていた回数制限

- 形の誤り（workflow にWeb検索を入れた）で差し戻された案が、確認役のための案の回数を使い切り、
  次の案を確認役が差し戻したところで、直す機会が残っていませんでした。形の差し戻しは、確認での差し戻しと別に数えるようにしました。
- 担当が、失敗し続ける地図検索を読める回数ぶん繰り返し、持っていたWeb検索を一度も試しませんでした。
  今は、読んだ結果の後ろに残りの回数と他に使える道具を添え、同じ呼び出しが同じ理由で失敗したらそう明示します。
  次の実機では、2回失敗したあとでWeb検索に切り替えました。

## 10. どの段にも同じ構造を持たせる必要はない

read → workflow の構造でいちばんつまずいたのは、いちばん小さいモデルでした。今は段ごとに動き方が違います。

| 段 | モデル | 動き方 |
|---|---|---|
| low | Nemotron 3.5 Lightning | メモ・Web検索・発言を直接呼ぶ。workflow も確認も無し |
| middle | Nemotron Super | 読む → workflow を出す → 確認 → 実行 |
| high | Nemotron Ultra | middle と同じ |
| 本体 | Nemotron Ultra | 振り分けと、workflow の確認 |

調べる以上のことをする道具には workflow が要るので、そうした道具を持つ low の担当は保存時に断ります。
以前に保存されていたものは、道具を黙って取り上げず、1つ上の段で動かします。

## 11. 実データを壊していた小さなこと

- プロンプトとメモに、サーバーのUTCが漏れていました。今は、利用者のタイムゾーンを担当に伝えます。
- メモの改行がエスケープされたまま（`\n` が2文字）だったり、frontmatter が字下げされていたりして、
  読めない・種類が分からないメモになっていました。どちらも、担当の意図を変えずに書き込み時に直します。
- 利用者が投稿を消したあとの片付けのために起こした担当が、新しい投稿（「ドラマ、見てる？」）を出していました。
  片付けの起床は発言しないターンにし、`speak` 自体を渡さないようにしました。

## 12. これらを見つけられたのは、ログがあったから

振り分けの判断と、担当のターンごとに、構造化ログを1件書きます。誰をなぜ起こしたか、何を読んだか、
workflow の各案とその問題点・確認結果、実行した各ステップ、発言の内容です。上の修正の多くは、このログの1行から始まりました。
ログが無かったころは、「振り分けが全員を選んだ」と「振り分けが失敗した」の区別すらつきませんでした。

テストには1つの決まりを置きました。修正のテストは、その修正を外したら落ちなければいけない、です。
新しいテストが間違った理由で通っていたことが2回ありました。1回は、テストの台本のJSONが壊れていて、
確かめたい場面が一度も実行されていなかったためです。どちらも、元のコードで落ちるまで書き直しました。

## まだ残っていること

- geo の MCP サーバーでの地名検索が、近くの候補を優先しません。「車で東京タワーまで」が150km先の場所になったことがあります。
  直すべき場所は、このアプリではなくそのサーバーです。
- ここに書いたことを支えているのは、数回ずつの実機実行だけです。どの担当にどのモデルが合うかは、
  決まった投稿のセットを各段に流して比べるほうが、上の事例よりも確かなことを言えます。
