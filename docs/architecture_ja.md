# 設計とペルソナ

[README](../README_ja.md) · [English](architecture.md)

## 設計原則

**記憶は担当領域ごとに分かれる。** 分離の目的は隠すことではなく、**濃度を保つこと**です。

**本体は振り分けて、確認して、実行する。** 誰に渡すかは中央が決めます。発言するか、何を覚えるか、いつ圧縮するかは
各ペルソナが決めますが、ペルソナはそれを workflow として出し、本体が確認してから実行します。
本体は何を言うかを決めません。起きていないことを書く・置いていない予定を約束する、といったことを止めるだけです。

**黙っていい。** 全部には反応しません。解説してもらうためのアプリではなく、ただ眺めていたいだけのときに
毎回反応されるのは押し付けです。誰も反応しない投稿があってよい。

**喋らないことと覚えないことは別。** 発言しなかった投稿も、自分の領域のものならメモには入ります。

**@で呼べば必ず答える。** 領域が分かれているから、誰を呼ぶか迷えます。

**非同期が既定。** 反応は遅れて届きます。

## 本体がやること

4つです。本体の判断には、**設定された中で最も賢いモデル**（high。Nebius では Nemotron Ultra）を使います。

1. 投稿を受け取る
2. **どのペルソナに渡すか振り分ける**
3. **各ペルソナの workflow を確認し、実行する**
4. 発言をタイムラインに出す

要約するかどうかも、発言するかどうかも、本体は判断しません。

**振り分けは、投稿が本当にその領域に属するときだけ渡します**（`internal/persona/route.go`）。
地名・時刻・食べものの名前が出てきただけでは渡しません。「明日9:10に神谷町に着きたい」は移動の担当にだけ渡り、
ワインの担当には渡りません。誰にも渡さないのは普通の答えで、判定に失敗したときも誰にも渡しません。
判定は、担当ごとの理由とともにログに出ます。

**判定は残り、直せます。** 振り分けが投稿について言ったこと（誰を選び、誰を選ばず、その理由）は投稿ごとに
保存され（`routing.json`、Firestore では `routing` コレクション）、タイムラインから見えます。@指名で届いた
担当は振り分けの判断ではないので含めず、判定できなかったときは記録を残しません。タイムラインの各行から
判定に異を唱えると、担当を作る AI が理由から担当条件を書き直し、人がその文章を直して保存すると、同じ投稿で
振り分けだけを試します（`Runner.CheckRouting`。配送はしません）。変わるのは担当条件だけで、裏で何かを
学習することはありません。

**担当の発言にも同じように異を唱えられます。** こちらは口調と指示が対象です。書き直して保存したあと、同じ一手を
もう一度取らせます（`Runner.PreviewReply`）。通常の `run` を、本物から読んでどこにも書かないワークスペースの
包みの上で動かします。メモを読み、調べることはしますが、発言は追記されず、メモも予定も書かれず、起きた回数も
増えません。何を言ったはずかが返り、判断するのは人です。

### 1ターンの流れ: 読む → workflow

ペルソナは道具を1つずつ呼びません（`internal/persona/workflow.go`）。

1. **読む。** ターンの最初に `index.md` を中身ごと必ず渡します。そのうえで、メモの一覧・メモ・web 検索などの検索を、10回まで頼めます。何も書き換えないので、本体はそのまま実行して結果を返します。
2. **workflow を出す。** 決めたことを、文面をすべて書き切ったステップとして順に並べます。

   | ステップ | すること |
   |---|---|
   | `write_note` / `forget_note` | メモを1件書く・捨てる |
   | `write_schedule` | 予定と、その根拠のメモを**1つのステップで**作る。メモが書けなければ予定も取り消す |
   | `cancel_schedule` | 渡された一覧の id で予定を消す |
   | `tool` | 宣言した道具を呼ぶ（`schedule` は除く） |
   | `speak` | 発言する。**必ず1つ、最後に。** 黙るなら text を空にする。黙るかどうかを毎回はっきり決めさせるためで、speak の無い workflow は差し戻される。投稿に発言するなら write_note も要る（発言だけは差し戻し。メモだけは可） |

3. **本体が確認する。** まず機械的に（ステップの種類、宣言した道具か、仮の schedule id が無いか、発言できないターンに
   speak の text が空か、名指しなら空でないか、speak が最後に1つあるか、同じ題名のメモを別の path に作っていないか）。次に本体のモデルが、狭い項目だけを見ます: 起きていないことを事実として
   書いている、ありもしない id、置いていない時刻の約束、投稿と違う言語での発言、読まずにメモを丸ごと書き換えている、
   担当自身への指示にはっきり反している。差し戻しは理由をつけて1回まで。確認は Nemotron Super で行います。
   空の workflow と、メモを書いて発言するだけの workflow は確認しません。予定・メモの削除・道具を含むものは確認します。
4. **実行する。** 上から順に。**失敗したステップで止まる**ので、根拠が成り立たなかった発言は出ません。

担当に渡す workflow の仕様は、その担当が持つ道具に合わせて組み立てます（`internal/persona/workflow_spec.go`）。
各ステップの項目・正しい例・実機で実際に起きた間違いを載せ、schedule を持たない担当には write_schedule を教えず、
web 検索を持つ担当には、そのまま写せる呼び出し例を見せます。

1ターンは構造化ログ1件に残ります: 読んだもの、各案とその問題点・確認結果、実行した各ステップ、発言。

本体はメモを読みません。ペルソナが書いた文面を保存先へ運ぶだけで、確認のモデルに見せるのも、そのターンに
ペルソナが読んだものだけです。

**@指名は振り分けを飛ばします。** 指名されたペルソナには必ず渡り、必ず答えます。他のペルソナへの振り分けは
通常どおり行います。

### 実行順序

担当ごとに **low / middle / high** を選びます。**並列に実行せず、low から順に上へ**回します。

**段は、担当の動き方も決めます。** web 検索以外の道具（経路・店探し・予定など）を使う担当は middle か high で、
本体が確認する workflow で動きます。low の担当はそうした道具を持たず、メモを読む・web 検索する・メモを書く・
発言するを、workflow も確認もなしに直接呼びます（`internal/persona/light.go`）。web 検索はどちらの経路でも
「読む」扱いで、workflow の経路では workflow を出す前に使い、workflow の中には入れません。

掛け合いは、先行する発言が後続の入力に入っていることで成立します。同時に走らせると上の段が下の段の発言を
見られず、突っ込みに行けません。

```
投稿
 ↓ 画像を一度だけ解析（OCR・写っているもの・出典の手がかり）
 ↓ 振り分け
low     を実行 ──→ 発言があればコンテキストに足す
 ↓
middle  を実行（low の発言が入力に入っている）
 ↓
high    を実行（low と middle の発言が入力に入っている）
 ↓
先に動いた段に、後から出た発言を渡す（**発言はできない**。メモの更新だけ）
```

**後から出た発言は、先に動いた段も受け取ります。** 喋らないことと覚えないことは別なので、
覚えるために一度渡します。ただし**そのターンは発言できません** — でなければAI同士が勝手に
言い合い続けて、タイムラインが自分のものでない会話で埋まります。上の段が全員黙ったときは
渡すものが無いので、この往復は起きません（黙るのが既定なので、これが普通の状態です）。

下の段が黙った場合は待ちません。同じ段に複数体いる場合は並列です。直列性が要るのは段のあいだだけです。
上の段の応答はその分さらに遅れますが、非同期が既定なので許容します。

### 画像の解析

投稿を受けたら本体が vision モデルで一度だけ解析します（`internal/capture`）。写っているもの・文字・出典の手がかり、そして見た目
（色・形・数・配置など、あとで聞かれそうな特徴）をテキストにして、投稿とともに各ペルソナへ渡します。画像そのものはペルソナに渡しません。担当のモデル
（Lightning / Super / Ultra）はいずれも画像入力に対応しておらず、実機では画像を渡した turn がエラーで黙って終わりました。
原画像を求めた担当には、すでに持っている読み取り結果を使うよう伝えます。最初の読み取りを厚くしてあるので、聞き足すことは残らないはずです。

## ペルソナ

### 渡されるもの

- 振り分けられた投稿と、その解析結果
- **その投稿に付いた発言**（他ペルソナのものとユーザーの応答を含む）
- 自分のメモの一覧（必要な中身は道具で読む）

**タイムライン全体は渡しません。** 渡せば結局すべてのペルソナがすべてを見ることになり、領域ごとに分けた
意味が消えます。振り分けを中央に置いたのはそれを避けるためです。

**過去は自分のメモにしか残りません。** 遡って取り直す経路を持ちません。残っていなければ、そのペルソナが
残さないと判断したということです。

同じ投稿に付いた発言を渡すのは、掛け合いとユーザーの応答が成立するためです。

### メモ

**各ペルソナが自分のメモを育てます。** 何を書くか、何を残して何を捨てるか、いつ圧縮するかは、すべて
スキルの記述に委ねます。グルメ担当は好みの傾向を重視するかもしれないし、別のペルソナは個々の出来事を
重視するかもしれません。

**本体は閾値を持ちません。** 毎回渡される一覧と、道具で読んだ内容をもとに、整理が必要かを自分で判断します。
画面の「メモを見る」でそのまま読めます。

### 書き方は OKF を渡す

[OKF (Open Knowledge Format)](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) の
スキルをペルソナに渡し、メモをそのバンドルとして**自分で読み書きさせます**。
1概念1ファイル、YAML frontmatter と markdown 本文。

```
=== index.md ===
# 傾向
* [豚骨に寄る](/tastes/tonkotsu.md) - 選べるときは豚骨を選んでいる。

=== tastes/tonkotsu.md ===
---
type: Preference
title: 豚骨に寄る
description: 選べるときは豚骨を選んでいる。
---
# 根拠
* 9/08 醤油と豚骨が並んだときに豚骨
```

**読み書きはペルソナ自身が道具で行います。** 起こされたときに渡されるのは**一覧だけ**で、中身は渡しません。

| 道具 | |
| --- | --- |
| `notes_read` | 中身を読む（要るものだけ） |
| `notes_write` | 1ファイルを書く。**そのファイルだけ**が置き換わり、他は触られない |
| `notes_forget` | 1ファイルを捨てる |
| `notes_list` | 一覧を取り直す |

宣言は要りません。担当領域ごとに宣言するのは**外に出る**道具で、自分のメモは外ではないからです。

これで、育ったメモを毎回まるごと往復させずに済みます。1文字直すために全文を書き直させると、
メモ全体が毎回出入りするうえ、書き写し忘れたものが痕跡なく消えます。

**本体はメモを読みません。** 名前の付いた場所にバイト列を置くだけです — frontmatter を読まず、
index を組み立てず、形式に合っているかも見ません。本体から見て中身が OKF かどうかは区別が付きません。
ペルソナが従わなければそれまでです。

ファイルはそのままディスクにあるので、`cat` で読めますし、**そのまま別の OKF knowledge source として
指せます**。半年分の食べたものだけが溜まった相手が、持ち出せる資産になります。

スキルは `internal/persona/skills/okf/SKILL.md` です。形式は OKF そのままですが、手順はこのアプリの
道具に合わせて書いてあります。毎回すべてのペルソナのプロンプトに乗るので、短く保つ必要があります。

型（`type`）に何を使うか、いつ統合するかは担当領域ごとに違うので、各スキルの `instructions` に書きます。
tabe なら `Preference` と `Shop`、shiori なら `Book` と `Theme`。**形式は渡すもの、方針はスキルが持つもの。**

### スキル

| 項目 | 内容 |
| --- | --- |
| 名前・アイコン・口調 | 表示と応答の性格 |
| 担当領域 | 何に反応し、何を覚えるか。**中央がこれを読んで振り分ける** |
| 指示 | メモの書き方、圧縮の方針、発言の基準。**本人だけが使う** |
| モデル | `low` / `middle` / `high` |
| 使えるツール | 宣言したものだけが呼べる |

内蔵は4体（tabe 食事 / michi 移動 / shiori 読書 / plana 繰り返し）。`skill.json` を画面から追加できます。

```json
{
  "id": "wine",
  "name": "ぶどう",
  "icon": "🍷",
  "domain": "ワイン。銘柄、産地、ラベルの写真、飲んだ記録。食事全般や技術の話には反応しない。",
  "tone": "控えめ。おすすめを押しつけない。",
  "instructions": "概念は type: Wine（銘柄）と type: Preference（好み）。同じ好みが3回出たら Preference に統合し、根拠の銘柄は消す。",
  "model": "high",
  "tools": ["web_search", "place_search"]
}
```

**体数に上限はありません。** 担当領域の数だけ増やせます。中央で振り分けるため、体数が増えても毎回動くのは
関係する数体だけで、振り分けの判定は投稿ごとに一度です。
ただし**同時に喋る数は別の問題**で、領域を跨ぐ投稿で全員が反応すると会話ではなく合唱になります。
ここは実際に動かしてから調整します。

**担当領域が分かれていないと @ に意味が出ません。** 誰を呼ぶか迷える状態でなければ指名は不要になります。
モデルのサイズ差は掛け合いには効きますが、呼び分けの理由にはなりません。

### ツール

宣言したものだけが呼べます（`internal/tools`）。呼ぶのは本体で、鍵はサーバ側にあります。
プロバイダの差し替えも、出典リンクを必須にすることも、本体で担保できます。
道具の接続先は運用者のもの（環境変数から作る `tools.Config`）で、地図の接続先とMCPサーバーの一覧が
デプロイ全体で一組です。Tavilyの鍵は利用者の設定から取ります。

| 名前 | 中身 | 鍵 |
| --- | --- | --- |
| `web_search` | Tavily | 要（利用者の鍵） |
| `place_search` | 周辺の店と**営業時間**（OpenStreetMap / Overpass） | 不要 |
| `route` | 現在地からの所要時間（OSRM。道路のみ、公共交通は含みません） | 不要 |
| `schedule` | 担当が自分で起きる時刻を本体に預ける（外には出ず、`schedules.json` / Firestore に残る） | 不要 |
| `サーバー名.道具名` | 設定したMCPサーバーの道具（`internal/mcp`、Streamable HTTP） | 運用者の設定 |

MCPの道具はサーバーごとに一覧を取得してキャッシュします。担当には内蔵の道具とまったく同じ形で、
サーバーが返す入力スキーマのまま渡され、同じように呼ばれます。
結果のテキストはその呼び出しへの返事として戻り、resource link は出典になります。
