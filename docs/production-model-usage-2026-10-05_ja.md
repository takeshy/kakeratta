# 本番モデル使用量と費用の調査 2026年10月5日

[English](./production-model-usage-2026-10-05.md)

2026年10月5日に本番で取得したtoken使用量ログを集計した。記録範囲の推論費用は、割引を適用しない公開単価ベースで **$0.4410**。そのうち13時35分のdeep返信1件が **$0.2736、約62%** を占めた。

この返信では、Ultraを最終回答だけでなく調査14回とschedule phaseにも使用していた。同じ呼び出し数・token数のまま調査とphaseをSuperへ変更する試算では、返信全体の費用は **約63%減**、Ultraへの累積入力は **約93%減** となる。これは変更後の実測値ではない。

調査日: 2026年10月5日。以下の時刻は、明記したUTC値を除き日本時間。

## 対象と集計方法

Google Cloudプロジェクト `kakeratta` のCloud Runを対象に、`jsonPayload.path="model-usage"` の構造化ログを取得した。

| 項目 | 対象 |
| --- | --- |
| 検索期間 | 2026年10月5日 00:00以上、13:40未満 |
| 最初の記録 | 08:30:05 |
| 最後の記録 | 13:37:05 |
| 取得件数 | 101件、`insertId` の重複なし |
| サービス | 全件 `kakeratta-worker` |
| リビジョン | `kakeratta-worker-00006-5t5` が76件、`kakeratta-worker-00007-4nq` が25件 |
| 推論プロバイダー | 全件Nebius Token Factory |

取得には次のクエリを使用した。取得件数は上限10,000件に達していない。

```sh
gcloud logging read \
  'resource.type="cloud_run_revision" AND jsonPayload.path="model-usage" AND timestamp>="2026-10-04T15:00:00Z" AND timestamp<"2026-10-05T04:40:00Z"' \
  --project=kakeratta --limit=10000 --order=asc --format=json
```

1ログを1回のAPI呼び出しとして数え、`usage.prompt_tokens` と `usage.completion_tokens` を合算した。全101件で両方の値が記録され、`outcome=success` だった。API成功は、tool呼び出しの妥当性や回答品質の成功を意味しない。

質問別の集計には `trigger` を用いた。振り分け、deep判定、調査、最終回答、phaseのうち同じ `trigger` を持つ呼び出しを含める。`trigger` のないembeddingは特定の質問に推測で割り当てず、別枠とした。

使用量ログの仕様は [Model usage logging](./system/backend.md#model-usage-logging)、運用手順は [Inspecting model usage](./system/operations.md#inspecting-model-usage) を参照。

## 費用計算の前提

ログに記録されるのはtoken数であり、請求金額ではない。次の単価を適用して概算した。

| モデル | 入力100万tokenあたり | 出力100万tokenあたり |
| --- | ---: | ---: |
| Nemotron 3 Super | $0.30 | $0.90 |
| Nemotron 3 Ultra | $1.00 | $3.00 |
| Nemotron 3.5 Lightning | $0.06 | $0.24 |
| Qwen3 Embedding 8B | $0.01 | 出力なし |

Nemotronの単価は調査日に確認した [Nebius公式ベンチマークの設定](https://github.com/nebius/token-factory-cookbook/blob/main/agents/agent-cost-comparison-1/agent_cost_comparison_1.py)、embeddingは [Nebius公式Qwenモデル紹介](https://nebius.com/services/token-factory/models/qwen-models-inference) を根拠とした。公式サンプルに掲載された単価による見積もりであり、個別アカウントの請求単価を確認したものではない。

```text
概算費用 USD = 入力token数 × 入力単価 / 1,000,000
             + 出力token数 × 出力単価 / 1,000,000
```

Ultraではキャッシュ済み入力が合計174,080 token報告されていたが、キャッシュ割引・契約割引・クレジットは適用していない。reasoning tokenやキャッシュ済みtokenは入力・出力の内数として扱い、総数に加算しない。Web検索API、Cloud Run、Firestoreなどの費用も含めない。

## 直近のdeep返信で費用が増えた理由

13:35の返信は、Piのエージェントループの実装と活用について深掘りする回答だった。対応するworkflowログと使用量ログを照合すると、次の内訳だった。

| 処理 | モデル | 回数 | 入力token | 出力token | 概算費用 USD |
| --- | --- | ---: | ---: | ---: | ---: |
| deep判定 | Lightning | 1 | 1,094 | 26 | $0.000072 |
| 調査 | Ultra | 14 | 193,269 | 10,938 | **$0.226083** |
| 最終回答 | Ultra | 1 | 15,196 | 3,821 | $0.026659 |
| schedule phase | Ultra | 1 | 19,231 | 522 | $0.020797 |
| **合計** | | **17** | **228,790** | **15,307** | **$0.273611** |

調査だけで返信全体の概算費用の約83%を占めた。Ultraに送った累積入力227,696 tokenのうち、最終回答の入力は15,196 tokenであり、残り212,500 tokenは調査とschedule phaseだった。

workflowに記録されたreadは12回だった。

- Web検索4回で結果を取得した。
- Web検索上限に達した後も7回検索を要求し、毎回「このターンの web_search はもう使えません」と返された。これらは追加のWeb検索成功ではなく、拒否結果を返したreadである。
- 記憶無効の担当でrecordsを1回要求し、「この担当は記憶を使いません」と返された。

使用量ログでは調査の14ラウンド目に `attempt=2`、`retryCount=1` があり、形式修正のリトライも1回確認できた。調査13ラウンド目は出力8,192 tokenを消費していた。ただし、使用量ログだけでその出力内容や終了理由は確定できない。耐久ジョブやphase再生成によるリトライは記録されていなかった。

検索不能という結果でも会話履歴に追加され、次の調査判断には再びモデル呼び出しが必要になる。このケースでは、上限到達後もUltraで反復したことが累積入力を増やした。

## モデル分離後の試算

本調査時点の本番ログは、deepとAlwaysUltraで調査・回答・phaseをUltraに送る変更前の挙動だった。ローカルでは調査とphaseをSuper、最終回答をUltraに分離する実装を完了していたが、まだ本番へデプロイしていなかった。

13:35の返信について、呼び出し回数と各呼び出しの入力・出力token数を固定し、調査とschedule phaseの単価だけをSuperへ置き換えると、次の計算になる。

| 指標 | 変更前のログに基づく値 | モデル分離後の試算 | 削減率 |
| --- | ---: | ---: | ---: |
| 返信全体の概算費用 | $0.273611 | $0.100795 | 約63.2% |
| Ultra呼び出し数 | 16回 | 1回 | 93.75% |
| Ultra累積入力token | 227,696 | 15,196 | 約93.3% |

```text
分離後の概算費用
  = Lightning判定 $0.00007188
  + Super調査     $0.06782490
  + Ultra回答     $0.02665900
  + Super予定     $0.00623910
  =               $0.10079488
```

Superへ変更すると調査方針、ラウンド数、生成token数も変わり得るため、この試算は実際の削減額を保証しない。Ultraのキャッシュ割引も未反映であり、請求額ベースの削減率とは異なり得る。入力93.3%減はUltraへ送る分だけの比較で、Superへ移す入力を含む全モデル合計の削減率ではない。

最終回答の正常な提出は1回を想定する。回答形式不正などに対する既存の修正リトライはモデル分離後も残るため、すべてのターンでUltra呼び出しが必ず1回になるという保証ではない。

## 今後確認すること

デプロイ後は、deepとAlwaysUltraで `research`・`plan_schedule`・`plan_action` がSuper、`answer` がUltraになっているかを使用量ログで確認する。そのうえで実際のラウンド数、token数、回答品質を比較する。

検索上限後の7回の反復は、モデル分離とは別の改善対象である。上限到達後に利用可能な読み取り手段を明確にする、または調査終了へ誘導する制御の効果を検証する余地がある。このレポートの作成では、その制御変更は行っていない。

この集計はログ取得範囲の本番サービス内の使用量に限る。記録開始前の使用量、外部エージェントや開発環境からの直接呼び出し、13:40以降の利用は含まない。個別の回答品質や検索結果の正確性も、この費用調査では評価していない。
