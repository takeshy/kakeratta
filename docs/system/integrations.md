# Alexa custom skill

The Japanese and English HTTPS skill exposes `POST /api/alexa` through the Gateway's public integration boundary, enabled only with complete operator configuration and Firebase authentication. Before resolving an account it verifies the SHA-256 signature, a trusted certificate chain with the exact `echo-api.amazon.com` SAN, the skill ID, and a timestamp within 150 seconds in either direction. Certificate downloads accept only HTTPS `s3.amazonaws.com/echo.api/` URLs on port 443, with no redirects, a three-second timeout and a 64 KiB bound. A bounded process-local cache retains verified certificates, checking them again on use. Envelopes are capped at 256 KiB; invalid requests receive HTTP 400. There is no unsigned development bypass.

Account linking uses OAuth authorization code grant. The signed-in `/alexa` browser page requires explicit consent and posts to guarded `/api/alexa/authorize`. Client ID, response type, scope and an exact operator-configured HTTPS redirect are checked. A five-minute single-use code is exchanged at `/api/alexa/token`, authenticated by the client secret (HTTP Basic or form fields). Access tokens last one hour; the stable refresh token expires 365 days after linking. Expiry is enforced by application checks. Only SHA-256 credential hashes, expiry instants and the pending redirect are persisted in a versioned `SocialValue` under `alexa-credential`; compare-and-swap makes code consumption and rotation exclusive across instances. A completed new link replaces the previous one. The browser connection endpoint reports status or revokes all credentials, including pending codes. Active judge accounts may link through the same consent flow. The verified Firebase UID is first retained with the pending authorization code as `CodeJudgeUID`, never accepted from OAuth input. An explicit empty string marks a regular-account authorization; the active `JudgeUID` and tokens remain unchanged until code exchange succeeds. Authorization-code exchange validates the pending identity and atomically promotes it to `JudgeUID` (omitted for regular accounts), clearing `CodeJudgeUID` together with the consumed code. Refresh validates only the active identity and preserves any pending authorization. Authorization-code exchange requires `CodeJudgeUID` to be present, including an explicit empty value for regular accounts. Failed, expired, or abandoned authorizations do not change the active account classification. Token exchange/refresh and every data request require an active judge configuration and an available atomic usage counter; confirmed judge posts and replies charge the same per-UID quota as browser AI actions before acceptance. Drafts and corrections do not charge it. A retry whose draft ID already exists does not charge again; simultaneous first attempts may still consume extra quota units. Model settings are pinned to the operator judge provider/key before access, including after a process restart. Expired review access cannot be extended by refreshing an Alexa token.

Tokens contain a workspace locator and random secret; the locator alone is never authorization. Requests open only existing workspaces and honor closing state. Every data intent verifies the current access-token hash and expiry. Alexa credentials do not authorize ordinary browser or MCP requests. Missing, invalid or expired access tokens produce a `LinkAccount` card. Stop/cancel and session-ended requests require a valid signature but no account data.

`ThrowKakeraIntent` and `ReplyKakeraIntent` accept an `AMAZON.SearchQuery` slot of at most 2,000 characters. A bare “メモして” / “take a note” or “返信して” / “reply” elicits the text through `Dialog.ElicitSlot`; all six models include a manual (`SKILL_RESPONSE`) dialog model. Recognized text and a stable draft ID are held only in signed session attributes and read back in full before any write. `AMAZON.YesIntent` alone saves the current draft; `AMAZON.NoIntent` or `ReviseKakeraIntent` discards its text and elicits a replacement while retaining the reply target. A new note/reply, reading replies or reading schedules discards an unconfirmed draft. Stop/cancel ends the session without posting. Launch and fallback use short prompts; only explicit help repeats the full introduction. Reprompts are short and confirmation-specific. Device speech endpointing remains controlled by Alexa.

Confirmed posts use the same `acceptEntry` transaction and routing path as browser submissions, with `Language: ja` for Japanese or `en` for English. The entry ID derives from the original draft request ID to deduplicate confirmation retries. It does not fetch spoken URLs or wait for persona inference. Replies set `KindReply`, `Root` and `ReplyTo` to the last heard persona entry, resolving both that entry and its root in the authenticated workspace before confirmation is accepted; missing, deleted, or foreign-workspace targets cannot be posted to. Session attributes never grant cross-workspace authority. Confirmation clears the draft and remembered reply target; `postId` retains the conversation root for subsequent reading.

`ReadRepliesIntent` reads the most recent 100 conversation roots and their replies, selecting only the newest persona entry or external-agent reply (read as from the active connection's name, or the external agent without one), excluding user/app entries. Markdown becomes plain speech, capped at 700 characters per answer; complete HTML answers direct the user to the app. Same-session `postId` narrows retrieval to the conversation just posted to. The returned entry ID becomes the target for “返信して” / “reply”. This is recent-conversation retrieval, not unread tracking or an exhaustive latest-reply query over historical threads. `ReadSchedulesIntent` reads up to five future saved schedules in time order using the account timezone (missing, invalid or `Local` zones fall back to Asia/Tokyo in Japanese and UTC in English), including autonomous and user-requested schedules. It does not fetch external calendars. The signed request locale selects Japanese or English prompts, reprompts, errors and read-aloud notices. `en-US`, `en-GB`, `en-CA`, `en-AU` and `en-IN` have separate shipped models with the shared invocation name `kakeratta notes`; `ja-JP` has its own Japanese model with the two-noun invocation name `かけらったメモ` (Amazon rejects single-noun Japanese invocation names). Missing or unsupported locales retain the legacy Japanese fallback. English dates include a year and AM/PM; US English uses month/day order, other English locales day/month. Locale does not imply a timezone. Stored reply bodies, persona names and schedule notes are read as saved, without a translation call; persona generation already follows the language of the user post. Output uses Alexa `PlainText`, preventing saved text from injecting SSML. Proactive announcements are not implemented.

# External-agent answers

## Shared judge Hermes connection

Invitation registration first prepares the [English sample workspace](./backend.md#http-api-and-authentication). When shared Hermes is configured, the seed selects only `wine-assistant` for external answers; all other sample personas use built-in answers. Preparing saved examples does not itself submit any work to Hermes.

Judge registration installs one operator-managed connection (`judge-shared-hermes`) in the judge's isolated workspace. The server stores only the SHA-256 digest of `KAKERATTA_JUDGE_MCP_KEY` and unpauses external-agent use, without changing per-persona planner preferences. The shared connection is put in use only when the judge has no other active connection; a connection the judge made themselves is never deactivated, and a repeat registration does not change which one is selected. A durable marker containing the verified Firebase UID is written only after those steps succeed, so repeating registration repairs the same connection without duplicates and partially initialized workspaces are not discoverable. With Firestore, the workspace key is also recorded in the top-level `judgeWorkspaces` collection. The secret is never returned to the browser.

`GET /internal/judge-workspaces` requires that same 64-character bearer secret and an active judge period, and is not served by worker-mode instances. It reads only the recorded judge workspaces (the local store's workspace directories without Firestore), skips any that no longer exist, and opens each through the ordinary workspace path, so a workspace being deleted is skipped rather than touched. It returns those with both the judge marker and the active shared connection matching the current key, as `workspaceId`, `mcpPath`, and an informational `mcpUrl` built from `KAKERATTA_PUBLIC_URL` or the request host, never from `X-Forwarded-Host`. Ordinary users and paused/replaced shared connections are omitted. Discovery and every shared MCP request resolve the marker UID through Firebase Admin `GetUser`, require its workspace hash to match, and require an existing, enabled account with `judge: true`. Firebase failures refuse shared access. Thus deleting/disabling an account or removing its judge claim immediately excludes it without relying on a stale registration marker. Legacy one-byte markers require invitation registration again to bind the UID. The MCP handler also rechecks the current operator key and judge period for this fixed connection ID, so expiration or key rotation immediately refuses even a previously known workspace URL; ordinary connections retain their existing authentication behavior. Firebase Hosting explicitly rewrites this internal path to the service alongside its general `/api/**` rewrite.

The Wake Gate queries discovery without following redirects from the configured kakeratta host and joins each validated `workspaceId` to that same host, so the shared key goes nowhere else. It calls `list_asks` independently on every workspace; one that fails is logged and skipped for that tick without holding up the others. A normal per-user key cannot use discovery and retains the single-workspace behavior. The worker (`direct_request_worker.py`) is imported only after the integration self-update and handles both open direct requests and open persona asks in code without waking the Cron parent (`wakeAgent: false`). Worker state, locks, usage, and audit files are scoped by `workspaceId`, while the worker Hermes homes still link the parent `.env` for provider authentication; judge direct-request runs exclude the local file server, additional MCP servers, and action toolsets, using only `web,kakeratta`; each generated worker MCP configuration uses only that run's URL. For pending or claimed persona asks (both in the configured workspace and in detached judge workspace processes), the worker claims each ask in code (`claim_ask`), immediately submits an empty answer for `listening` or `post-deleted` turns with zero LLM calls, or runs one `hermes chat -Q` session on `nvidia/Nemotron-3.5-Super-VL` through a generated `persona-hermes-home` with only `read_for_ask` from kakeratta MCP plus the `web` toolset when permitted by the ask context (six tool-calling iterations, eight model calls and 250,000 tokens by default), parses the response into the structured answer, and calls `submit_answer` (or `release_ask` immediately on failure so the built-in planner takes over without waiting out `planBy`). A per-workspace `persona.lock` makes an overlapping tick skip a workspace whose persona run is still going. The parent configuration is not edited and Hermes is not restarted.

When `JUDGE_WORKSPACES_URL` is set, the gate uses that explicit HTTPS discovery endpoint with `JUDGE_MCP_KEY`, without requiring a configured seed workspace. It rejects redirects and workspace URLs outside that origin, polls all workspaces before inference, and uses the same detached workers and workspace locks as automatic discovery. Persona runs load only the kakeratta MCP server restricted to `read_for_ask`, and zero skills in the generated home and use only the parent's model/provider settings (`nvidia/Nemotron-3.5-Super-VL`). Direct requests preserve the dedicated `kakeratta_worker` / `delegation` model, reasoning and budget settings. Direct requests and judge persona asks run in detached processes so inference cannot block the next minute's discovery. The parent configuration is unchanged in shared mode. Same-workspace overlaps skip while another worker holds the corresponding lock.

## Persona inference budgets and deadlines

Worker version 10 derives each persona run's wall-clock budget from the `ask.planBy` returned by `claim_ask`, reserving 30 seconds for process cleanup and submission and taking the smaller of that allowance and the configured `run_budget`. Resuming a claim retains the original deadline; missing, malformed or nearly expired deadlines release the ask without inference. Persona runs have no additional 120-second subprocess grace period.

While the CLI is running, Python polls the isolated home's Hermes `state.db` once per second. A snapshot of existing session IDs excludes prior runs. Newly recorded session usage is added to the request's durable totals for the live check; reaching the token or API-call limit stops the CLI and its process group and releases the unfinished ask. The check observes persisted counters, not an in-flight provider request: Hermes's recording delay and a running API call can overshoot the limit. The iteration and output caps also remain in force. An unreadable initial session snapshot refuses inference; unavailable final usage blocks any subsequent run.

A normally completed, usable answer is submitted even if its final counters exceed the budget or cannot be read. The worker records that usage and retains the answer for transport retries without regenerating it, avoiding a second built-in generation solely because the completed run reached its limit. Interrupted output is never submitted as a completed answer. Verification: [persona budget and process cleanup tests](../../tests/test_hermes_judges.py).

## Hermes parent model and sandbox networking

The configured Token Factory parent/persona model is `nvidia/Nemotron-3.5-Super-VL`; direct requests and delegation retain `nvidia/Nemotron-3-Ultra-550b-a55b`. A generated persona home upgrades the legacy Super 120B model only when the parent explicitly uses the custom Token Factory endpoint. Other model/provider choices are preserved, and the parent file is not changed by the worker. When configuring or updating a Hermes parent, pin the kakeratta Cron job as well as `model.default` (and `cron.model` when set), because a pinned Cron model takes precedence over global defaults. See [Hermes configuration](../../scripts/nemoclaw/README.md#7-hermes-推奨設定-sandboxhermesconfigyaml).

Worker version 16 and gate version 13 adapt automatically to containerized and OpenShell sandbox environments (`/sandbox/.hermes`). An OpenShell sandbox has no network route or name resolution around its L7 forward proxy, so `kakeratta.net` and the web search backends (`api.keenable.ai`, `mcp.exa.ai`, `search.parallel.ai`) are removed from `no_proxy`/`NO_PROXY`, including entries left by earlier versions, and must be allowed by the sandbox policy. OpenShell proxy environments automatically load CA bundles (`/etc/openshell-tls/ca-bundle.pem`) and proxy configuration, and internal Hermes tool search is disabled (`tools.tool_search.enabled: "off"`) in worker sessions. Persona runs and copied provider entries route Token Factory through the sandbox inference gateway (`https://inference.local/v1`), which serves the gateway's model (Super). A direct-request run keeps the `base_url` configured in `kakeratta_worker` or `delegation`, so Ultra reaches Token Factory by name over OpenShell Provider v2; only when no endpoint is configured does it fall back to `NEMOCLAW_INFERENCE_BASE_URL` (which NemoClaw sets to `inference.local` in the sandbox image for the parent) and then `inference.local`. Verification: [worker endpoint and proxy tests](../../tests/test_hermes_judges.py).

## Connection and role

The user creates an MCP connection, enables external-agent use in settings, and selects `external` as a persona's planner. The preference control is shown only with a configured connection and external-agent use enabled; saved preferences survive disabling use. The server exposes `/api/mcp/users/{workspace}` per workspace and manages connection keys and settings. This is separate from the application's MCP client for calling external tools.

The external agent researches as the persona and submits the final answer with its `schedule` decision when scheduling is permitted. The answer schema handed to the agent uses the same permission-based selection as built-in answers and omits `schedule` for personas without that permission. The host plans, reviews and executes needed schedule changes, then publishes the answer. For memory-enabled personas, the note keeper subsequently judges retention for related user turns, including related silence, and corrects earlier memory for edits even when unrelated. `accepted` acknowledges receipt of the answer; it does not mean timeline publication is complete.

## Ask lifecycle

1. Use `list_asks` to find pending asks with deadlines.
2. Send the ask ID and a stable `claimId` to `claim_ask` to receive the persona, trigger, conversation, memory (`memory`: grounded facts and the latest kakera records), and available read tools.
3. Research through permitted `read_for_ask` calls: `records` steps (`tag`, `query`, `before`, or `ids` - up to 10 - to read the entries records point to, which may then be cited) and read-use tools (in the distributed Hermes worker, `persona-hermes-home` exposes only `read_for_ask` from kakeratta MCP plus `web` when permitted, while `list_asks`, `claim_ask`, `submit_answer`, and `release_ask` run in Python).
4. Submit text, sources, and an optional boolean `schedule` decision with `submit_answer`; `unrelated` identifies a silence outside the domain. An omitted schedule decision preserves legacy schedule behavior. Legacy `remember` values are accepted and ignored; answers no longer decide retention. Invalid submissions receive correction requests; source IDs not found by this ask's research are dropped rather than refused.
5. If unable to respond, call `release_ask` to return the turn to the built-in model.

Claiming and answering have separate deadlines. Unclaimed asks, answer timeouts, connection changes, explicit release, and exhausted correction attempts can trigger fallback. A connection with no recent MCP activity, or paused external-agent settings, can select the built-in model immediately.

An ask is an `asks` runtime record, not a waiting goroutine: opening it ends the turn, and claim, reads, answer, and release are transactions on the record, so the agent may reach any process serving the workspace and an ask survives a restart. The agent's reads run where they arrive, under the lock `ask:{id}` (a read stops if the lock is lost), and their results - reads used, lookups, cited posts - are kept on the record. Deadlines are enforced through the workspace's alarm: opening an ask asks to be woken at its claim wait, claiming it at its plan wait, and the due reaction closes what has run out (see [Times and wakes](./architecture.md#times-and-wakes)). A closed ask queues the reaction `ask-{id}` in the conversation's lane, which carries the turn on and deletes the ask. The agent's last call is the `presence` record, written at most every 30 seconds. An MCP request opens a workspace only if it exists.

# Direct requests to the external agent

## Addressing the agent

The user may address the connected agent itself. There is no setting for it: not naming the agent is the choice. The agent must not be paused (`ExternalAgent.Paused`), and a connection must be in use (`SetAgentName` gives its name, "" with none). When either is missing (`agentUnavailable`), an entry naming the agent is neither routed nor delivered: a `kakeratta` reply under it gives the reason (switched off, or not connected) and the settings to change. A reply that merely carries on a conversation with the agent, without naming it, goes to the personas as usual while the agent is unavailable. During route preparation, after image analysis and before the active-persona check, `directRequest` takes a user entry that mentions `@外部エージェント`, `@エージェント` or `@agent`, compared through `timeline.Mentions` and `foldTerm` (case, width, kana and honorifics ignored). The connection's name is not an address: the user may name a connection anything, and the request always goes to the connection in use. A reply without a mentioned persona is also a request when its parent is the agent's reply, or when its parent is the user's own entry or the app's notice in a thread whose root post named the agent; a mentioned persona takes such a reply instead. These aliases are reserved: a persona definition cannot be written with them as its ID, name or alias (see [Persona definitions](./personas.md)). A direct request opens a `requests` runtime record and returns no delivery plan: there is no routing record, persona turn, schedule, action or memory. Without a routing record, `GET /api/entry/{id}/routing` adds `agent: true` to `recorded: false` when `AddressedToAgent` finds the entry addressed to the agent (named, or carrying on its conversation, whether or not the agent could take it), and the browser's routing sheet ([routing-view.js](../../frontend/src/routing-view.js)) says the post went to the external agent instead of describing a routing that has not finished. Edits are described below.

## Request lifecycle

1. `list_asks` returns open requests under `requests` beside `asks` (`id`, `entryId`, `rootId`, `status`, `claimBy`, then `claimedAt` and `replyBy`). Expired requests are not listed. The Wake Gate hands both pending requests and pending persona asks to `direct_request_worker.py` (below) and returns `{"wakeAgent": false}`.
2. `claim_request` (`requestId`, stable `claimId`) claims it like an ask, the same `claimId` claiming again idempotently, and returns `DirectContext`: instructions allowing side effects the user clearly asked for, the user's profile name, `now`, `timeZone`, `place`, the trigger and the whole thread rendered with names (`agent` is the agent's earlier replies). A request whose entry was deleted is forgotten and reported as not found.
3. The Wake Gate does not wake the parent model for a direct request. It runs the distributed direct-request worker, which claims the request in code, runs `nvidia/Nemotron-3-Ultra-550b-a55b` (reasoning `high`) once as an ordinary Hermes agent through the Hermes CLI - never a direct provider request - with the worker's tools (by default read-only: kakeratta's read-only MCP reads `get_timeline`, `get_thread`, `list_personas`, `list_notes`, `read_note`, `search_timeline`, `list_schedules`, read-only local file reads and web search/extract; action tools are added through Hermes configuration), and posts the agent's final response through `reply_request`. There is no review step; what the agent does with its tools happens during the run. Side effects are allowed only when the trigger itself asks for them: earlier thread entries, other posts, persona answers, notes, search results and the user's past words may supply details the trigger refers to, but never ask for an action. The MCP tool `comment_on_entry` (`requestId`, `claimId`, `entryId`, `text`) remains for agents that work on requests themselves: it posts an `agent` reply under any live entry while the request is claimed, up to 10 per request (`Comments`), under the same lock; nobody is routed it, and a reply to it is the next request. The distributed worker does not use it.
4. `reply_request` (`requestId`, `claimId`, `text`) posts one `KindReply` entry under the trigger with speaker `timeline.Agent` (`agent`), normalizing escaped newlines and refusing empty or over-20,000-character text, then deletes the record. It runs under the lock `request:{id}`, so a retry finds the request answered rather than posting twice.

A pending request must be claimed within `directClaimWait` (two hours, `claimBy`), longer than an ask's claim wait since the agent works through one request at a time and nothing answers in its place, and a claimed one replied to within `directReplyWait` (two hours, `replyBy`). The due reaction's `sweepRequests` closes requests past either, and `nextDue` includes those times. A pending request is forgotten; a claimed one becomes `expired`, since the agent may already have acted: it is no longer listed, claimed or commented for, but `reply_request` with its `claimId` still posts the late reply. `sweepRequests` forgets requests whose entry was deleted, without a notice, and `ResetExternalAgent` (pausing or changing the connection) withdraws every open request and forgets expired ones. Each closure appends a `kakeratta` (`timeline.App`) reply under the trigger saying no reply came; there is no built-in fallback. A claimed request does not count as the agent working (`agentWorking`). Records carry a 24-hour `expireAt` (`requestKeep`) renewed on each change, which bounds how long a late reply is taken.

Editing an entry whose request is still pending refreshes it (`edited: true`, claim wait renewed). Editing one whose request is claimed or expired opens nothing - the agent could act twice - and appends the app's reply `処理中のため編集は反映されません。返信で伝えてください。` (`editedWhileClaimed`). An edit after the reply opens a new request.

The agent's entries are attributed to the active connection's name (`agentName`, `SpeakerNames`) wherever the personas, the note keeper, external-agent asks and the daily and monthly summaries read the timeline, and to 外部エージェント without a connection; the agent's own context marks them as its own. The name is attribution only, not an address.

## Request status and notifications

The runner emits `request` events (`id`, `entryId`, `state`: `pending`, `claimed`, `replied`, `closed`, and `notify`) through the workspace's event stream, and `GET /api/requests` lists open requests (`id`, `entryId`, `status`, `notify`) with the active connection's name (`agentName`) for a page that has just loaded; see [Direct request status](./frontend.md#direct-request-status). Whether a request's end is pushed is chosen per request: `DirectRequest.Mute`, off by default, is set by `PUT /api/requests/{id}/notify` (`{"notify": bool}`, `SetRequestNotify`) while the request is open, and an ended one answers 404. What ends an unmuted request - the agent's reply, including a late one, or the app's notice of a timeout or withdrawal - is emitted as `AgentReplyEvent` (`agent-reply`); `publishEvent` hands it to `sendAgentReply`, which pushes it through the same Web Push delivery as reminders (`pushEntry`). Comments on other entries and the edit notice are not pushed.

## Direct-request worker

The Wake Gate does not wake the Super parent for direct requests or persona asks when `direct_request_worker.py` is available: after `list_asks` it runs the distributed worker for every pending or claimed request (`worker.lock`) and every pending or claimed persona ask (`persona.lock`), oldest first, and returns `{"wakeAgent": false}`. Only one worker of each kind runs at a time per workspace: a non-blocking `flock` under Hermes home makes an overlapping tick skip instead of processing the same item twice. The worker owns both flows in code, so the parent model never wakes with the full MCP schema and platform toolsets.

- **Claim and resume**: the worker calls `claim_request` with a stable claimId derived from the request ID (`hermes-{requestId}`) and saves its stage under `kakeratta/state/` before the run, marking that a run has started. A claimed request is resumed only when that record exists, so requests claimed by anything else are ignored. When the worker's tools are read-only (the default), a Hermes, provider or network failure, or a crash, leaves the request claimed and a later tick reclaims it with the same claimId and runs it again, at most `MAX_RESUMES` (two) times, after which the worker replies that it could not finish. When action tools are configured (any toolset beyond `web`, `kakeratta` and `files`, or any added MCP server), a failed or interrupted run may already have acted, so it is never repeated: the worker replies that the run failed, or that it was interrupted and may have acted.
- **The run**: the work is one fresh single-query `hermes chat` session (`-Q --ignore-rules`, `--provider`, `-m`, `--reasoning`, `-t`, `--max-turns` 15, `--run-budget` 1,200 seconds; `max_turns` in the section overrides the turn limit) with Ultra (`nvidia/Nemotron-3-Ultra-550b-a55b`, reasoning `high`) as an ordinary Hermes agent. The prompt is a short preamble followed by the whole `DirectContext`; it tells the agent to do what the trigger asks with its tools and that its final message is posted as its reply (Markdown, in the user's language, under 18,000 characters, never claiming an action it did not perform). There is no review: the agent uses its tools directly, so anything it does happens during the run. The final response, without the notice lines Hermes prints first in quiet mode, is the reply; an empty response, or Hermes's turn-limit message, is replaced by a reply saying the request could not be finished within the turn limit. When replying with errors or fallback notices (turn limits, budget limits, interrupted executions, or tool failures), the worker replies in English when the trigger context contains no Japanese characters, and in Japanese otherwise.
- **Tools**: the session runs with the worker's own Hermes home, `kakeratta/hermes-home`, rewritten before each batch. Its `config.yaml` (mode 0600) takes the model, provider, endpoint and `${VAR}` key reference from `kakeratta_worker`, then `delegation` - never the parent's `model`, which names Super - sets the output cap to 16,000 tokens by default to bound cost (reasoning included; `max_tokens` in the section overrides it), copies the parent's kakeratta MCP server with `tools.include` limited to the seven read-only reads, and registers the worker script itself as a stdio MCP server `files` (`--fs-mcp`) offering only `read_file` and `list_directory`; `.env` is a symlink to the parent's. The toolsets enabled for the run default to `web,kakeratta,files` (`toolsets` in the section overrides them), and parent MCP servers named in the section's `mcp_servers` list are copied in as they are configured there, which is how action tools are added the usual Hermes way. kakeratta's write tools such as `reply_request` and `claim_request` are never loaded. The file server resolves every path inside the readable roots (`file_roots` in the section, default the user's home), refuses hidden entries (dotfiles such as `.hermes`, `.env`, `.ssh`) and secret-looking names (`config.yaml`, keys, names containing token, secret, credential, password or auth), returns at most 200,000 characters per call with an offset for the rest, and masks known secret values. Known secret values - the provider key, the MCP request headers' credentials, and secret-named environment variables - are also masked in the reply and the audit log. Skills, memory, cron jobs and sessions are not shared with the parent. The worker never sends a provider request itself.
- **Cost limits**: after the run the worker reads the session's `api_call_count`, `input_tokens`, `cache_read_tokens`, `cache_write_tokens`, `output_tokens` and `reasoning_tokens` from the `sessions` table of the worker home's Hermes `state.db` and adds them to the request's totals in `kakeratta/state/usage/{requestId}.json`, which persist across resumes. Before and after each run it compares those totals with `MAX_API_CALLS` (40 model calls) and `MAX_REQUEST_TOKENS` (1,500,000 tokens: input plus cache reads and writes plus output; reasoning is a breakdown of output and is not added again), overridable as `max_api_calls` and `max_request_tokens`. Reaching either limit, or a run whose usage cannot be read (no session ID, a timeout, a missing row or table), stops the request fail-closed: the run's response is discarded, no further model call is made, there is no resume, and the worker replies with the limits and the reason. A single run can still overshoot within its turn limit; the check runs between runs.
- **Delivery**: the worker calls `reply_request` directly with the reply. It is saved before it is sent; when sending fails, the next tick finds the claimed request with its saved reply and resends it without running again.
- **Audit**: one JSON line per event per request ID under Hermes home, flushed at each stage and rotated past a size cap, recording the claim (model, provider, reasoning, resume count), the run's Hermes session ID, token usage (`model_usage`) with the request's running call and token totals and the reply length, an unfinished run's last 300 characters, a skipped rerun, a `budget_exceeded` stop with its reason, failures, and the reply outcome. Secrets, full prompts, profiles and thread contents are never recorded.

# Posts as a persona by the external agent

Outside asks and direct requests, the agent may post as a persona with the MCP tool `post_as_persona` (`persona`, `text`), for example when the user or its operator has the agent share what it found in that persona's domain. Only an active persona that uses the external agent may be posted as: it must be in `Settings.Active`, since a persona switched off keeps its planner choice, and `Settings.PlansExternally` must hold, so its planner is `external` and the agent is not paused; otherwise the call is refused (`ErrNotAgentPersona`), as is an unknown persona.

`Runner.PostAsPersona` normalizes escaped newlines and refuses empty or over-20,000-character text, then appends one `KindPost` (its own root) with the persona as speaker and `Model: "agent"`, and emits `entry`. Nothing else runs: there is no ask, planning, schedule, action, review or note keeper, and the persona's memory and wake count are unchanged. No reaction is queued except search indexing, so no persona is woken and nothing is pushed; the user replying to the post is routed as usual and wakes that persona.

Each persona may be posted as at most `MaxAgentPostsPerDay` (5) times per day in the user's time zone. The count is an `agent-posts` runtime record keyed by the date (`YYYY-MM-DD`) holding a count per persona, incremented in the record's transaction before the post is appended - so concurrent calls on any instance cannot pass the limit - and decremented again if the append fails. Past the limit the call fails with `ErrAgentPostsExhausted`. The record expires 72 hours after its last change; reads ignore an expired record, and the Firestore TTL policy on `agent-posts` ([main.tf](../../infra/main.tf)) deletes it. The result carries `entryId` and `remaining`, the posts left for that persona today. The call is not idempotent; the distributed skill tells the agent not to retry a call that succeeded.

## Selecting capabilities

`Registry` holds built-in tools and tools from operator-configured MCP servers. `For(skill.Tools).As(skill.ID)` builds the persona's permitted set. Shared timeline search and access to the persona's own memory are also available. A persona permitted to use `schedule` automatically receives the read-only `schedules_list` tool, including in external-agent asks, to inspect filtered, paginated workspace schedules on demand. The schedule creation argument `user_requested` distinguishes tasks explicitly requested at a time or recurrence from autonomous checks; listings and own-schedule context expose that flag and the effective `notify` preference. The host schedule phase can update an owned schedule's time or Push preference without replacing its identity; external agents still submit answers only. The notification preference is persisted with an external ask and restored when its answer or fallback resumes. The host's schedule phase and review choose and check the flag, including after an external-agent answer, and scheduled wakes use it to select task or brief-reminder instructions; see [Scheduled wakes](./personas.md#scheduled-wakes).

A tool `Declaration` carries a name, description, JSON Schema, and read-only status. `schedule` is the only declared tool that changes state, and it is used only by the schedule phase; every other tool is a research read. `mcpTools` registers an external MCP tool only when its server marks it `readOnlyHint`, so an unannotated tool is neither listed for persona editing nor offered to a persona. There is no phase that runs other side effects. The host validates model-supplied arguments and makes the actual network requests. Built-in tools apply their own argument checks. For external MCP tools, `checkArgs` checks required top-level keys and the basic types of non-null top-level values only; it is not a complete JSON Schema validator. Enum values, ranges, nested constraints, additional properties, and nullability remain the external server's responsibility. External-agent declarations retain the original tool schemas. Built-in research nests each schema under its own tool-name branch with object arguments, rebasing local references without mutating the declaration; see [Research budgets and available reads](./personas.md#research-budgets-and-available-reads).

The advertised `timeline_search` schema requires at least one nonempty `query`, `from` or `to`, rejects extra fields such as `ids`, and describes limit/score ranges. Its period-only usage omits query; a concrete structured period example is included in built-in research instructions. ID-only reads use `entries` instead. Execution retains the existing period parsing, result-limit clamping and score validation. See [search.go](../../internal/tools/search.go) and [structured_reads_test.go](../../internal/persona/structured_reads_test.go).

For built-in answer research, `Set.ReadAvailable` additionally filters out tools known to be unusable from their configuration or the current post: missing keys/services, unavailable place-search endpoints. A delegated MCP map tool does not require its built-in fallback endpoints to be configured. This availability check does not execute the tool or change the persona's permissions. The research host combines it with live search/lookup budgets to generate the per-round read schema and instructions; see [Research budgets and available reads](./personas.md#research-budgets-and-available-reads). External-agent tool declarations and execution-time argument validation retain their existing behavior.

## Web search and news freshness

`web_search` accepts `query` and optional `topic` (`general` or `news`), `time_range` (`day`, `week`, `month`, `year`), and publication-date bounds `start_date` / `end_date` (`YYYY-MM-DD`). The tool rejects empty or non-string filters, unknown categories or periods, invalid dates, reversed date bounds, and a relative period combined with date bounds before making a provider request. `Client.SearchWithOptions` validates the options and forwards them to Tavily; `Client.Search` keeps the ordinary unfiltered search used by settings key verification.

News searches without any period default to `time_range: day`. Explicit relative periods or date bounds take precedence over this default. Tool instructions ask personas to use `topic: news` with `time_range: day` for latest-news requests and morning news digests, honor a user-specified period, and disclose when they widen the search. Category selection is performed by the persona, not by matching words in the query. Ordinary searches remain unfiltered unless a period is supplied. These filters use the provider's publication-date semantics, rather than a host-enforced guarantee of exact hours or complete news coverage; see [Tavily's date-filter guide](https://help.tavily.com/articles/3347142954-best-practices).

Provider `published_date` values are retained in results and shown with source URLs in research text when available. No publication date is invented when absent. Instructions distinguish publication time from search rank and do not present undated results as today's news. The same declared tool and validation serve built-in research and external-agent reads. Verification: [web_test.go](../../internal/tools/web_test.go) exercises requests through the tool to the HTTP transport, default daily news, explicit weekly and historical periods, ordinary unfiltered searches, returned publication dates and sources, and rejection before network access.

## Reading the kakeratta specification

`kakeratta_help` reads the shipped OKF v0.2 bundle. An omitted `path` returns `index.md`; an explicit path must be one of the seven root Markdown files listed in its schema. The result includes the file name and the entire chapter, including frontmatter and implementation review dates. Unknown files, non-string or empty paths, absolute paths, and traversal are refused. It reads only the embedded bundle, requires no workspace or API key, and exposes neither the host filesystem nor the user's configuration. The internal built-in name is not delegated to external MCP providers. Personas must declare it to use it; research and external-agent reads use the same permission checks as other read-only tools.

## Weather forecasts

`weather_forecast` is a declared read-only tool available during built-in research and external-agent `read_for_ask`. It calls WeatherAPI's `forecast.json` endpoint over HTTPS by default. `query` accepts a place name or coordinates; when omitted, the post's coordinates are used. Without either, the call fails rather than looking up the server's location; `auto:ip` is refused. Days default to three and must be an integer from 1 through 14. An optional `date` selects a `YYYY-MM-DD` forecast date, `hour` selects an integer local hour from 0 through 23, and `lang` is `ja` (default) or `en`. Availability depends on the provider's subscription. A shorter returned period includes a warning; a requested date absent from the response is an error.

Responses contain the matched location and timezone, current weather with its update time, and daily temperatures, rainfall/probability, wind, UV, and conditions. Hourly values are included only for a requested hour. Icons, unrelated API fields, and unrequested hourly data are omitted. Source attribution points to WeatherAPI.com without a credential-bearing API URL. Unknown fields are not passed through. HTTP, provider, transport, malformed-response, and missing-configuration failures remain errors rather than empty or invented forecasts. Requests have the shared 25-second HTTP timeout, bounded response decoding, and do not follow redirects. Provider error text and HTTP request URLs are not exposed because they may include the key.

The operator configures `KAKERATTA_WEATHERAPI_KEY`, or `KAKERATTA_WEATHERAPI_KEY_FILE`; a direct key takes precedence. Without either, an existing `tmp/weatherapi.key` relative to the process working directory is used for local development. An absent default file leaves weather unconfigured; an explicitly unreadable or empty file fails configuration. `KAKERATTA_WEATHERAPI_URL` defaults to `https://api.weatherapi.com/v1`. Keys stay in server-side tool configuration, outside persona settings, tool schemas, and browser responses. `tmp/` is excluded from Git and the Docker build context. Production Terraform and Cloud Build inject the existing `kakeratta-wheatherapi-key` secret through `KAKERATTA_WEATHERAPI_KEY`; see [Deployment](./operations.md#deployment).

The [WeatherAPI documentation](https://www.weatherapi.com/docs/) defines forecast parameters, response fields, and provider error codes.

# Selected sharing to Bluesky

## Publication plan

The frontend selects entries to publish and sends the root post, target, display language, selected IDs, and a per-entry `formats` map (`text` / `image`) to `previewSocial`. The server builds `PlanSelectionFormatsIn` from the current thread, resolving persona names, text, images, split posts, and the connected account. Each selected entry can be published as text or a browser-rendered image. Missing formats retain the legacy `ImageAnswer` default: complete persona HTML and laid-out infographic/agent Markdown use images; other entries use text. Explicit text mode converts Markdown to readable text and complete persona HTML to body text (`HTMLText`, skipping head/script/style/template content); user-authored code stays literal. Image mode requires browser-rendered `htmlImages` pages keyed by entry ID, including for ordinary user posts and persona replies. The browser's `imageSource` preserves complete persona HTML and the infographic layout. For ordinary content, `socialImageDocument` uses the existing Markdown renderer (literal text for user posts), includes any attached image as an inlined data URL, and builds a standalone light-theme document. Existing isolated capture renders the pages. Each capture carries a SHA-256 hash of the original entry text; missing or stale captures are rejected. Image conversion failure blocks publication until the user retries or chooses text. Captures never replace timeline media or saved entry text.

## Rich text

Bluesky has no markup; a post's rich text is facets over UTF-8 byte ranges. Persona answers that are not image answers (Markdown) go through `FromMarkdown` ([richtext.go](../../internal/social/richtext.go)), which converts them to plain text that reads as the answer:

- Headings become their own line after a blank line, and unordered items become `・` (nested items are indented with ideographic spaces).
- Ordered items keep their numbers, and tasks become ☑/☐.
- A table becomes its header row, then one `・` row per line, with cells joined by ` ｜ `.
- A quotation becomes a `＞` line, and a callout becomes its title.
- Mermaid flowcharts and sequence diagrams become `・A → B（label）` / `・A → B: message` lines; notes become `・📝 note`. They read the same syntax as the timeline renderer: multi-line and `<br>` labels joined with spaces, pipe labels, chains, `&` fan-out, skipped subgraph/style lines, continued message lines, and skipped control blocks. Other diagram types are omitted. Other code fences keep their lines.
- Emphasis, deletion and inline-code markers are removed.
- `[label](http…)` keeps only the label, with a link facet to the URL; other schemes stay plain text.

User posts keep their text exactly. In every post, bare URLs (including appended links and sources) also become link facets.

`SplitRich` ([split.go](../../internal/social/split.go)) treats each link label and URL as one unbreakable unit, which is never a sentence boundary. It returns each part's links as offsets into that part's text, prefix included. Out-of-order or out-of-range input facets are left as plain text. `Post.Links` (`start`, `end`, `uri`) is part of the sealed plan digest. `Publish` sends them as `app.bsky.richtext.facet#link` facets (`byteStart`, `byteEnd`), skipping any outside the text or not http(s). The preview dialog renders the same ranges as links (`richText` in [social.js](../../frontend/src/social.js)). Verification: [richtext_test.go](../../internal/social/richtext_test.go) and [social.test.js](../../tests/social.test.js).

The browser sends its display language (`language`), and `PlanSelectionIn` uses it for the few words the plan adds to posts: a persona prefix (`🍚 tabeからの返信:` / `Reply from 🍚 tabe:`), the continuation head (`つづき:` / `Continued:`), and image placeholders (`［画像］`, `［画像 2/3］` / `[Image]`, `[Image 2/3]`). Anything but `en` is Japanese. The language is part of the plan, so it is sealed by the digest. Verification: `TestPlanWordsFollowTheDisplayLanguage` in [richtext_test.go](../../internal/social/richtext_test.go).

A digest seals the plan. Publishing rebuilds it and compares the digest so changed content or accounts are not published after preview approval. The selection initially contains only the original post, but every entry can be deselected; at least one entry is required. Answers can be published without the original post. No other entry is selected automatically. The first selected entry in timeline/parent order becomes the publication plan root and is standalone. If a selected reply's direct parent is also selected, it stays attached to that parent's final part; otherwise it attaches to the first selected entry's final part. Omitted parents are never published, and the preview shows the resulting reply relationships. The dialog shows each selected entry’s actual planned posts inline and automatically refreshes them when selection or format changes. Its single **Post** button stays visible and is disabled until the current preview is ready. Request generations discard stale results; image captures are serialized and cached for the dialog. Posting uses the exact request snapshot that produced the displayed digest. Selected formats are also sealed into the plan, so switching formats invalidates approval. The digest includes image data, alternative text, and the source hash, so altering a capture or its source invalidates approval. Preview and publication bodies are limited to 32 MiB. JPEG/PNG captures must decode with valid dimensions and at most 50 million pixels, then use the existing Bluesky image preparation.

## Authentication and publication state

Bluesky connections use OAuth. Callback information and the browser secret are combined to complete the connection. Durable connection state is managed through Workspace social values.

Publication history is keyed by target, account, and post, and each publication is claimed before sending. Already published items are not resent, supporting retries after partial progress. Publication records retain the actual Bluesky root URI and CID; extensions use their saved parent's thread root even if a later selection omits the original post. Older records without those fields resolve their root from the original post's history. Reusing a published answer does not move or repost it into a new thread. Images are loaded and prepared for Bluesky before publishing. Partial success is possible; publication as a whole is not atomic. HTML captures travel as temporary data URLs in the preview/publication requests, are neither stored as timeline media nor written to blob storage, and do not modify the saved answer. The first image uses the entry history key; subsequent image pages use `:image:2` and so on, form a continuation chain, and the entry's replies attach to its final page. Source URLs remain text posts when they need splitting. Image uploads include the capture's alternative text.

# Connected Timeline import

Connected applications import the Timeline with the read-only MCP `get_timeline` tool; there is no write path for them. Besides a page (up to 50 posts with their whole conversations and the next cursor), it takes up to 200 `ids` to recheck: each returns the whole conversation containing it, wherever it is, so later replies and edits on old posts remain discoverable, and IDs that no longer exist are listed under `missing`. Rechecks of IDs not on the page are read at most 8 at a time (`recheckParallel`) and merged in the order given. An ID no entry could have (`validEntryID`: empty, over 200 bytes, or containing a path separator, NUL or line break, or `.`/`..`) is not read from the store and is listed as missing, so it cannot fail the whole call. `authors` maps every speaker in the response to its display name: `Runner.SpeakerNames` (the personas' names and the connected agent's name, or 外部エージェント) plus the user's profile name; the Alexa replies and schedules read the same names. Absence from a page never means deletion; only `missing` does. Imported posts are read-only in the application and are edited or deleted in Kakeratta.

The standalone [Web server](../../tools/google-bridge/internal/server/server.go) serves embedded assets and guarded connection APIs. It supports multiple comma-separated listen addresses (e.g. host loopback and container bridge). Its high-entropy management key establishes an eight-hour HttpOnly/SameSite Strict session (Secure for HTTPS). Only hashes and the management-key fingerprint are persisted for sessions. A separately issued MCP key authenticates each stateless Streamable HTTP POST to `/mcp`; when no separate MCP key is issued, `/mcp` also accepts the configured kakeratta Timeline MCP key or non-browser local/container requests on loopback or private container network IP origins, while always rejecting the management key (`adminToken`). Host and browser Origin are checked against the configured canonical origin and permitted listen/container hosts. Key rotation/revocation rejects later calls. Instances have separate credential workspaces and cannot select another owner in tool arguments.

[Google service](../../tools/google-bridge/internal/google/service.go) binds OAuth state, the initiating tab secret, client and PKCE verifier to an encrypted service record. OAuth completion uses the authenticated browser finish API, validates actual scopes and the Google account subject, and tests the target API. Gmail and Calendar can be connected together in a single OAuth flow (`both`) or individually, using the same Google account. Tokens and client secrets use AES-256-GCM with workspace/service AAD and versioned keys outside the data directory. Refresh, completion, reads and disconnect share a workspace lock and CAS. Invalid grants and repeated 401 responses require reconnection; raw provider errors and credentials are not returned.

The [MCP tools](../../tools/google-bridge/internal/server/api.go) are `google_connection_status`, `gmail_search`, `gmail_get`, `gmail_thread`, `calendar_list`, `calendar_events`, and `calendar_get`. Gmail requires readonly; Calendar requires events readonly and separately, when selected, calendar-list readonly. `openid`/`email` support account binding/display. Reads require explicit consent to share Google data with the user's agent and model. Results contain selected fields and mark content as untrusted external data. Text is bounded; Gmail attachments and HTML bodies are not imported. Interactive reads are not persisted. Opt-in important-mail import retains selected bodies in encrypted, bounded caches. Outgoing approval previews temporarily retain bodies and target snapshots in encrypted journals. Downstream Hermes history and model retention remain separate.

The [action service](../../tools/google-bridge/internal/google/actions.go) exposes a single write tool, `google_action_run`, for owner-direct requests to Hermes. It requires the owner's verbatim instruction (`userRequest`, up to 1000 characters) and executes without a Web confirmation step: `Run` builds the same immutable proposal (connection generation, SHA-256 payload digest, idempotency-key digest), records it as decided by `direct` with the request text, and executes it. Restricting calls to direct owner requests (never email/calendar/Timeline content, cron/triage jobs or agent initiative) is enforced by the tool description, MCP instructions and the cron gate wording; the server cannot verify request authenticity. Optional OAuth permissions are gmail.send, gmail.compose, or calendar.events plus calendar-list readonly; the connection form selects all by default. The owner-cookie decision/execute APIs remain for legacy proposals. The [history UI](../../tools/google-bridge/internal/server/web/actions.js) shows each action with the owner's request, recipients/body/reply target or before/after calendar data, timezone, attendees and notification impact. Execution consumes and durably saves the decision before the network write. The CLI wraps the file workspace with [fsync checkpoints](../../tools/google-bridge/internal/persistence/workspace.go) for the JSON file and parent directories, so consumption is flushed before an external write. Repeated calls with the same idempotency key return receipts; crashed, timed-out or ambiguous writes become unknown and never retry automatically. Preflight conflicts invalidate the proposal; Google If-Match additionally guards Calendar PATCH/DELETE. Reconnection changes the generation and invalidates outstanding proposals.

Gmail supports fixed-account plain-text send/reply and approved remote draft creation; mutable remote draft IDs cannot authorize sends. Calendar permits owner calendars, single events and individual recurring instances; recurring masters, special event types and delegated management are rejected. Supported event fields are replaced explicitly while other fields remain intact. All-day ends are exclusive; timed offsets must match an IANA timezone. Invitations use an explicit sendUpdates choice; Meet generation is create-only. Each service has at most eight active previews. Terminal/expired previews lose content on completion/disconnect or next journal access. Compact audit metadata and key digests remain for replay prevention until owner deletion of the dedicated data directory; backups have separate owner retention. Journal reads also rewrap ciphertext for key rotation.

Hermes uses its existing additional MCP-server configuration. For kakeratta direct requests, an owner can name `google_bridge` in `kakeratta_worker.mcp_servers`; the worker retains its existing rule against rerunning failed sessions with extra MCP servers. Shared judge workers and persona-ask homes do not load these additional servers. Neither Hermes core nor the distributed worker is modified. The [setup guide UI](../../tools/google-bridge/internal/server/web/setup.js) generates project-specific `gcloud` creation/enablement/readback commands and Console links for the selected services. It never executes shell commands or holds Cloud CLI credentials. OAuth consent/client creation remains a manual Console step, with recovery guidance. [google.js](../../tools/google-bridge/internal/server/web/google.js) presents a single unified OAuth connection form for Gmail and Calendar together, reads an owner-selected Web-client JSON locally (64 KiB maximum), validates the client type and exact redirect URI, and fills the client inputs; leaving the client fields blank on reconnect reuses the saved OAuth client. File contents are never sent as a file or persisted in browser storage; only validated fields enter the existing authenticated OAuth start API. Endpoint URLs from files are ignored. Logout disposes the credential form.

Local service disconnect deletes its credentials, pending OAuth and active approval payloads without changing the other local connection. Google-side revocation requires explicit selection because it affects other clients in the same Google project. Restricted scopes, Testing refresh-token expiry, personal-use verification exceptions and external-model data flow are explained in the [setup guide](../guides/google_ja.md). Owning the project is not presented as a general exemption guarantee.

The [import service](../../tools/google-bridge/internal/google/inbox.go) adds `gmail_sync` (one bounded batch) and `gmail_inbox` (consented cache read). Imports default off. Owner settings select labels/senders/exclusions, importance threshold, body characters and retention. Default classification is deterministic and local; urgency words cannot generate high urgency. Optional [Hermes triage](../../tools/google-bridge/internal/google/triage.go) adds `gmail_triage_context` / `gmail_triage_submit`, an editable owner prompt, and up to 50 encrypted candidates (10 per context). A kept decision requires a bounded factual summary that omits signatures, boilerplate, disclaimers, unsubscribe text, advertising and quoted history; Timeline delivery uses this summary instead of the original body. Model decisions bind to the current message and settings digest; stale results fail. Fixed external-data policy remains separate from the editable prompt. Exact normalized From exclusions apply before model disclosure and scrub queued candidates. Owner-selected excluded types are supplied to the model and enforced by ID in the tool layer. The settings UI lists the prompt, learned types and blocked Froms together; deleting a row and saving cancels that preference for future messages. The profile history baseline, bootstrap page condition, message queue and processed-ID set are checkpointed. Expired history falls back to the configured bounded lookback while preserving deduplication. Spam/trash are excluded. Cache holds at most 200 selected messages, pruned on reads/sync; disconnect clears it.

[timeline.go](../../tools/google-bridge/internal/google/timeline.go) now exposes a **Hermes-owned relay**, with no outbound kakeratta HTTP transport or stored destination/key. `google_review_context(service=gmail|calendar)` supplies at most five exact kakeratta tool/argument payloads with content-bound tokens. New candidates take priority and pending-card polls rotate to avoid starving later owner decisions. The Hermes-side Python worker uses the separately configured kakeratta MCP to call `propose_gmail_import` or `propose_calendar_import`, then passes the actual structured receipt to `google_review_receipt`. Lost responses remain unacknowledged and are retried with stable identities; the existing receiver keeps the original card and terminal decision. Stops, disconnects, cache deletion and expiry prevent stale candidates being relayed. `triage_submit` saves selection locally and never sends a card. Optional Calendar summaries replace the provider description while preserving event timing/context.

Receipt handling binds the token to current cached content and the entry ID to the item, records terminal feedback once, removes rejected cached items, and does not restore owner-cancelled exclusions on receipt replay. Sender/type and Calendar-event exclusions must match the cached source. Only the owner selects Import/Discard in kakeratta; see [review intake](./backend.md#owner-reviewed-gmail-imports) and [Timeline UI](./frontend.md#gmail-review-cards-on-the-timeline). The authenticated personal Hermes is trusted to relay actual kakeratta receipts; Bridge has no independent authenticated connection to verify their origin. It cannot approve a kakeratta review. The removed `/api/timeline-target` management endpoints return 404, old target ciphertext is deleted at startup without decrypting it, and a kakeratta key no longer authenticates Bridge MCP. Existing cached candidates and already delivered kakeratta cards remain usable.

The companion supplies [check_google_bridge.py](../../tools/google-bridge/hermes/check_google_bridge.py) and the separate daily [check_calendar_bridge.py](../../tools/google-bridge/hermes/check_calendar_bridge.py) gate. Each syncs its own service, draining at most ten read batches. Either `triagePending` or `deliveryPending` starts [google_bridge_worker.py](../../tools/google-bridge/hermes/google_bridge_worker.py) as a detached Python process in the owner's Hermes profile. Gates always return `wakeAgent:false`, so register them with `--no-agent`. The worker uses per-service nonblocking locks and at most ten sync batches. Delivery and receipt polling run entirely in code, with zero model calls when only those are needed. Bridge remains independent and has no kakeratta destination or credential.

The worker fetches up to ten triage candidates, runs one isolated Hermes model session, validates an index-based JSON selection/summary, binds the original IDs and tokens in code, and calls the triage submit tool itself. It reuses the installed [direct_request_worker.py](../../frontend/public/integrations/hermes/kakeratta/scripts/direct_request_worker.py) persona runtime for parent model/provider settings, CLI execution and usage/deadline monitoring. The generated per-service home has no MCP servers, tools, auto-loaded skills or inherited conversation memory. Explicit `platform_toolsets.cli: []` selects no tools. Each session has one turn; one invocation permits at most five model batches/API calls, 250,000 tokens and a 300-second model deadline, additionally honoring lower parent limits. An in-flight call can exceed the observed token budget. The classifier never constructs MCP calls, destinations, identities or receipts.

Before submitting, worker code durably saves the validated decisions in a mode-0600 `HERMES_HOME/google-bridge/<service>-decisions.json`; only generated summaries, classifications, IDs and tokens are stored, not provider message bodies. Transport failures retain this journal for submission without another model call; completion or a known context/consent invalidation removes it. Isolated Hermes session history follows the owner's Hermes retention policy. Code reads Bridge credentials from the private sibling `google_bridge.json`, and kakeratta endpoint/headers from the parent `config.yaml` with environment references resolved locally. Keys never enter prompts or cron output. `google_review_context` payloads and the actual kakeratta structured receipts are copied by code, with an allowlist of the two proposal tools, bounded responses, and redirects refused. A failed or lost send/acknowledgement leaves the same Bridge candidate retryable. A set of processed tokens prevents repeatedly polling the same card within one invocation. Successful status records contain counts only; the worker log has fixed failure text. No custom scheduler, routing loop or messaging channel is introduced. Real Hermes invocation and account setup remain separately unverified.

## Daily owner-reviewed Calendar intake

[calendar_inbox.go](../../tools/google-bridge/internal/google/calendar_inbox.go) implements opt-in `calendar_sync` using events readonly. The configured IANA timezone defines today's midnight to the day-after-tomorrow midnight using calendar arithmetic (including DST). Events are expanded into recurring instances. The encrypted `calendar-inbox` namespace keeps bounded page progress, processed occurrence identities and owner preferences. Normal sync reads Google once per completed local day; owner Web sync can refresh the same day. Existing occurrences are not re-posted or updated automatically. Cancelled events are omitted. Event cards format start and end dates compactly without timezones, omit empty location rows, and display all-day dates with explicit exclusive end notes, while the Google Calendar reference is provided through the review card and post source links.

The daily gate drains at most ten bounded batches; each service batch processes at most 20 events, pages contain at most 50, model candidates at most 50 and selected items at most 200. Page descriptions are truncated before checkpointing. Cache retention is lazy: remove data 24 hours after the event ends or seven days after acquisition. Disconnect clears Calendar intake independently of Gmail. Replay IDs remain until explicit cache/data deletion. Calendar intake has its own enable switch; Hermes relays its selected candidates using the same separately configured kakeratta MCP connection.

[calendar_triage.go](../../tools/google-bridge/internal/google/calendar_triage.go) adds consented `calendar_triage_context` and `calendar_triage_submit`; settings and event digests invalidate stale decisions. The editable prompt is separate from fixed external-data policy. Occurrence exclusions match calendar+event ID; recurring exclusions match calendar+master ID before model access. Hermes relays the owner-selected Discard exclusions from kakeratta receipts; they are shown in the companion and removable with Save. Applied-feedback receipts prevent old decisions restoring cancelled rules. Title matching is not used. Candidate review reuses the existing Timeline review pipeline; it introduces no Calendar router or memory subsystem and never performs Google writes.
