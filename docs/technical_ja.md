# 中で起きていること

[README](../README_ja.md) · [English](technical.md)

kakerattaを使うのに、この文書を読む必要はありません。使う人がすることは、思ったことを投稿することと、
自然な言葉で担当に「こうしてほしい」と伝えること。その2つだけを目指しています。
ここには、そのために中で動いているものと、サーバーを運用する人が決めることをまとめます。

## 全体の流れ

投稿されると、まず軽量なルーティングで関係しそうな担当だけを起こします。それぞれの担当が、
発言するか、記憶するか、何もしないかを自分で判断します。

長期記憶には [OKF (Open Knowledge Format)](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) を使い、
担当ごと、さらに内容ごとにファイルを分けています。巨大なコンテキストを毎回読むのではなく、
必要な記憶だけを読み書きします。

担当が記憶しなかったものも含め、タイムライン全体は残ります。キーワード検索と意味検索によって、
必要になったときに過去の断片を探せます。

推論には Nebius Token Factory 上の NVIDIA Nemotron を使い、light / middle / high のモデルを使い分けます。
担当は Web 検索や MCP などの道具も使えます。

メモは思いついた瞬間に書けることが重要です。そのため Service Worker を入れ、オフラインでも
タイムラインを読んだり書いたりできるようにしました。

まとめると、こういう構造です。

**雑多なタイムライン → 分野ごとの担当 → 担当ごとの構造化された記憶**

内部では MCP、RAG、OKF、スキル、意味検索、モデルのルーティングを使っていますが、
使う人がこの構造を理解する必要はありません。

## AI同士の会話を止める

複数のAIが互いに反応し続けると、token を消費し、タイムラインをAI同士の会話で埋めてしまいます。

そこで担当を light → middle → high の順に実行し、後のモデルほど、それまでの反応を見られるようにしました。
後段の判断を前段の担当へフィードバックして記憶を更新することはできますが、そのターンでは再発言できません。
AI同士の会話が続くのを防ぎながら、より強いモデルの判断を活かせます。

詳しい実行順序は [設計とペルソナ](architecture_ja.md#実行順序) にあります。

## 振り分けは「判断」ではなく「条件との照合」

当初は Lightning に「この投稿を誰に渡すべきか」を判断させていました。担当の説明には、その担当に
依頼したいことや実際に何をするのかまで含めていましたが、本来反応すべき担当を選ばないなどの誤振り分けが起きました。

そこで一度 Ultra へ変えました。Ultra にも当初は誤動作がありましたが、Prompt の修正に対する改善が分かりやすく、
調整を重ねて安定して運用できるようになりました。

その後、Usage で実際の利用額を確認し、構成を見直しました。Ultra 自体は極端に高価ではありませんが、
kakeratta では一つの投稿から複数のAI処理が発生するため、全体では1投稿あたり1〜2円程度になるケースがありました。
Personal AI では、ユーザーに「これはAIに送る価値があるか」と考えさせず、日常の小さな出来事も気軽に投稿してほしい。
だから、すべての投稿で必ず動く Router のコストを下げることは重要でした。

本番の担当6人・直近20投稿で比較したところ、1ドル150円換算で、Router 1回あたりの費用は Lightning が約0.069円、
Ultra が約0.456円でした。この段階で単純に Lightning へ変えた場合、Ultra との振り分け一致は 17/20 でしたが、
不一致の3件は、反応すべき担当の見落としが2件と、8,192トークンを吐いて判定にならなかった壊れた応答が1件でした。
数字の上では近くても、見落としと壊れた応答を含む Router を本番に置くことはできませんでした。
なお、ここでの一致数はモデル間の一致であり、人間が確認した正解率ではありません。

ハイエンドのモデルでうまくいき、ローエンドで間違えるなら、振り分け条件が複雑なのだろうと考え、
Router が読む各担当の情報を「担当して実現すること」から「担当条件」に変えました。単に条件に一致するかどうかだけを
判定すればよくなりました。これで改善しましたが担当の見落としが残ったため、選んだ理由を返す `reasons` をやめ、
**選ばなかったすべての担当について `excluded_reasons` を必須で返す**構成にしました。
また、具体例に判断が引っ張られることがあったため、Router の Prompt から具体例を削除しました。

途中の実験では Ultra との一致数は 15〜17/20 で、増えたのは中身のほうでした。壊れた応答が無くなり、
見落としていた食事の写真や本の質問を拾えるようになりました。最終の本番設定では 18/20 になり、残った2件は
「今日お風呂に入ったか、もう一度入るかも」のように予定に入れるには直近すぎる内容を Ultra は無視し、
Lightning は予定として取り込むという、どちらとも取れるものでした。この2件は目で確認して問題なしと判断しています。
測り方と各実験の数字は [Routing model comparison](routing-cost-experiment.md) にあります。

この方式のよかった点は、除外条件をユーザーにも見せることで、ユーザー自身で改善できるという仕様を思いついたことです。
はじめから完璧に振り分けることは Ultra でもできなかったので、違和感を覚えた振り分けに対して、
ユーザーが「呼んでほしかった」と理由を伝えることで担当を育てる機能につながりました。

## 担当の操作は workflow にして、制約と review を掛ける

Router とは別に、担当が生成した操作をそのまま実行しないための実行制御も作りました。担当は書き込みと発言を順に並べた
**workflow** を提出し、本体が確認してから実行します。

Nemotron（あるいは一般に LLM）の苦手なことに、同一フロー内で似たようなことを重ねて実行するのを避けたがる、
というのがあります。このアプリの重要な機能は、担当がユーザーのかけらを記憶して、必要があれば返事をすることです。
ところがメモと発言の内容が同じだと、うっかりメモに書いて発言はしなかったり、その逆が起きます。
そのため、発言した場合はメモを必須にするチェックを入れ、メモだけにしたいときも `speak` のステップ自体は必須にして、
不要なら空文字にする、という形で発言を意識させるようにしました。

予定に関しては、予定の登録とメモの内容が同じでも問題ないので、逆に1つのステップでメモと予定の登録を行うようにしました。

さらに予定は間違えると信頼に関わるため、schedule の道具を持つ担当は、workflow に対して review 用の Super を呼び、
メモの内容も含めて確認します。整合性が取れていない場合や、発言だけして予定を登録していない場合は、担当に差し戻します。

## モデル

KakerattaはNebius Token Factoryを通じてNVIDIA Nemotronモデルを使用します。担当の実行、振り分け、
workflow の確認にはネイティブな tool calling（`tool_choice: "required"`）を使います。画像の読み取り、
担当案の作成、音声入力の整形、embedding は、構造化出力や embedding 用のAPIを使います。

| モデル（Token Factory） | 役割 |
|---|---|
| Nemotron 3 Ultra | high の担当と、担当案の作成 |
| Nemotron 3 Super | middle の担当と、メモ・発言以外へ及ぶ workflow の確認 |
| Nemotron 3.5 Lightning | 投稿の振り分け、low の担当、音声入力の文を整える（任意） |
| GLM-5.3-Flash | スクリーンショットや写真を、投稿ごとに一度だけ読む |
| Qwen3-Embedding-8B | 過去の投稿の意味検索 |

Web検索には Tavily を使います。これを信頼できる形にするまでに苦労したことと、その対処は
[AIまわりで苦労したこと](ai-lessons_ja.md) にまとめています。

## 動かす

ブラウザで使うアプリで、静的な画面と Go の API の2つに分かれています。画面は開発中は Vite、
公開時は Firebase Hosting が配信し、Go のバイナリは API だけを持ちます（Cloud Run でも手元でも同じ）。

必要なもの: Go 1.26 以降、Node.js、Task（`task` コマンド）。
リポジトリのルートで実行します。

```sh
task setup  # 初回のみ。画面側の開発依存（Vite・Storybook）
task dev    # API（:8787）と画面（:5173）を同時に起動
```

ブラウザで <http://127.0.0.1:5173> を開きます。新しいワークスペースには担当がまだ誰もいないので、
呼ぶまでは画面がそれを先頭で伝えます。

<img src="captures/ja/nobody.png" alt="担当が誰もいない状態。内蔵の担当をワンタップで呼べる" width="390">

そのあと「設定」でNebius Token FactoryのAPIキーを入力します。各段のモデルはLightning・Super・Ultraが既定で設定されています。
画面は `/api` をバイナリへ中継します。公開時と同じ分け方です。API だけなら `task run`、
バイナリのビルドだけなら `task build`（出力は `bin/kakeratta`）、Storybook は `task stories`、
テストは `task test` です。

| 環境変数 | 既定 | 用途 |
| --- | --- | --- |
| `KAKERATTA_PUBLIC_URL` | 空 | Bluesky OAuthに使う公開HTTPSオリジン |
| `KAKERATTA_BLUESKY_KEY` | 空 | Bluesky接続の署名・暗号化用秘密鍵（64桁の16進文字列）。[運営設定](social-sharing.md)を参照 |
| `KAKERATTA_ADDR` | `:8787` | 待ち受けアドレス |
| `KAKERATTA_HOME` | OS の設定ディレクトリ | 投稿・メモ・画像の保存先 |
| `KAKERATTA_TOKEN` | 空（認証なし） | アクセス用トークン |
| `KAKERATTA_FIREBASE_PROJECT_ID` | 空 | Firebaseによるマルチユーザー認証を有効化 |
| `KAKERATTA_FIREBASE_API_KEY` | 空 | Firebase Web APIキー（公開値） |
| `KAKERATTA_FIREBASE_AUTH_DOMAIN` | 空 | Firebase Authドメイン |
| `KAKERATTA_GCS_BUCKET` | 空 | 画像を保存する非公開Cloud Storageバケット |
| `KAKERATTA_STORE` | `file` | Cloud Runでは`firestore`を指定 |
| `KAKERATTA_FIRESTORE_PROJECT_ID` | Firebaseプロジェクト | Firestoreのプロジェクト |
| `KAKERATTA_MCP_SERVERS` | 空 | 担当が使えるMCPサーバーの一覧（JSON） |
| `KAKERATTA_NOMINATIM_URL` ほか | OpenStreetMapの公開サービス | 店舗・経路検索の接続先（後述） |

**外からアクセスできる場所で動かす場合は `KAKERATTA_TOKEN` を設定してください。**
各ブラウザで一度 `/?token=<URLエンコードしたトークン>` を開くと、画面が API 経由でトークンを
渡し、以後はセッションCookieで認証されます。

公開するマルチユーザー環境では、代わりにFirebaseの3変数をすべて設定します。
Googleでログインした利用者ごとにデータが分離されます。Firebase認証を設定した場合は、共有の `KAKERATTA_TOKEN` より優先されます。
保存先は次の組み合わせで決まります。

- `KAKERATTA_STORE=firestore`（Cloud Run向け）: 投稿・設定・担当メモ・担当の定義をFirestoreの `users/<uidのハッシュ>` 以下に保存します。
- `KAKERATTA_STORE=file`（既定）: 同じデータを `KAKERATTA_HOME/users/<uidのハッシュ>/` 以下のディスクに保存します。
- `KAKERATTA_GCS_BUCKET` を設定すると、どちらの場合も画像は非公開バケットの `users/<uidのハッシュ>/blobs` に保存します。

## 1日1回のチェックインと timer

担当画面で、有効な担当ごとに「1日1回のチェックイン」と希望時刻を設定できます
（初期状態はOFF）。時刻とともに端末のタイムゾーンを保存します。
JST以外にも対応し、夏時間も考慮します。移動後も保存したタイムゾーンを維持し、現状は手動の
選択UIはありません。担当は自分のメモ・過去のかけらの検索・普段の道具を使い、伝えることが
ある日だけ新しいスレッドに投稿します。黙る日はシステム投稿も空のスレッドも残りません。

`schedule` を宣言した担当は、自分で起きる時刻を本体に預けられます。担当ごとに20件まで、
30日以内、1回きりか毎日です。接続先や有効な担当と同じく、予定は本体が持ちます。中身を決めるのは
担当で、その予定のもとになったメモを書くときに、同じ返答の中で預けます。時刻はユーザーに尋ねず、
担当が自分の記録から決めます。声をかけるのはいつも「その時刻のあと」で、やる前に急かすことは
しません（「花、買った?」）。発火前に実行権を保存するので、沈黙や失敗でも同じ回は繰り返しません。
10分以上遅れたものは鳴らさずに捨てます。メモを消すと担当が起きて、そのメモに紐づく予定を
見直します。記憶を全部消したとき、担当を停止・削除したときは、予定も消えます（メモは残ります）。

投稿を消したときも同じ形です。本体は投稿を消し、その投稿で起こした担当に伝えます。
誰に伝えるかは、本体が持っている「その投稿で誰を起こしたか」の記録から決めます（メモは読みません）。
伝えられた担当は自分のメモを見て、その投稿を出典にしている記述があれば直すか捨て、無ければ何もしません。
本体がメモを書き換えることはありません。

サーバーが毎分確認し、通常の投稿と同じ実行キューで処理します。処理が混んでいる
場合は希望時刻より遅れます。ブラウザを閉じても動きますが、サーバーの稼働は必要です。
再起動時にはFirestoreを含む設定済みユーザーを復元します。同梱のCloud Run構成は
すでに最小1インスタンス・リクエスト外もCPUを割り当てる設定です。

チェックインは実行前に日付を保存し、沈黙・失敗も含めて現地の日付ごとに1回までに制限します。
Firestoreではトランザクションで複数インスタンス間の重複を防ぎます。ローカル保存は
ワークスペースごとに1つのサーバープロセスで動かしてください。時刻の変更や記憶の削除で
当日の実行済み状態は戻りません。停止期間の分をまとめて投稿せず、再開した当日分だけを
実行します。実行日を保存した直後に停止した場合、その日の定期便はスキップされます。

## 道具は運用者が用意する

[道具の一覧・用途・設定・依頼例・制限](https://kakeratta.web.app/manual/?lang=ja#ja-tools)

担当の道具がどこへ行くかは、サーバーを動かす人が環境変数で決め、全利用者で共有します。
地図の接続先とMCPサーバーがそれです。利用者が自分で入れるのは `web_search` に使うTavilyのAPIキーだけで、
設定画面で保存します。スキルは道具の名前を宣言するだけで、呼ぶのは本体、鍵を持つのも本体です。

**MCPサーバー**で道具を増やせます。`KAKERATTA_MCP_SERVERS` はJSONの配列です。

```json
[{"name":"geo","url":"https://geo.example.com/mcp","headers":{"Authorization":"Bearer …"}}]
```

各サーバーの道具は `サーバー名.道具名`（例: `geo.compute_commute`）として内蔵の道具と並び、
スキルはその名前で宣言します。対応するのはStreamable HTTPのリモートサーバーだけです。
道具の一覧は数分キャッシュし、応答しなくなったサーバーは最後に取得した一覧を保ちます。
呼び出しの失敗は握りつぶさず、担当にそのまま伝えます。

## 店舗検索・経路検索

`route` は投稿に付いた位置情報を必要とします。車・徒歩・自転車で接続先を分け、
`KAKERATTA_OSRM_CAR_URL`・`KAKERATTA_OSRM_FOOT_URL`・`KAKERATTA_OSRM_BIKE_URL` で指定します。
既定は順に `https://router.project-osrm.org`、
`https://routing.openstreetmap.de/routed-foot`、
`https://routing.openstreetmap.de/routed-bike` です。URLの移動手段名を書き換えるだけでは
切り替わらず、自前のサーバーでも対応する経路データが必要です。公共交通の時刻表や
リアルタイムの渋滞を含まない道路の目安です。非対応の移動手段はエラーを返します。

`place_search` は位置情報があればOverpass（`KAKERATTA_OVERPASS_URL`）で周辺検索、なければ
Nominatim（`KAKERATTA_NOMINATIM_URL`）で名前を検索します。
営業時間はOpenStreetMapに登録がある場合だけ返り、営業中である保証はありません。
周辺検索の一時的な障害は一度再試行し、失敗したら「店がない」ではなく取得不能と伝えます。
公開サービスの混雑や停止による失敗は引き続き起こり得ます。

geo-home-mcp のように、同じ名前で位置（`lat`・`lng`）を受け取る道具をMCPサーバーが持っていれば、
`route` と `place_search` は投稿の位置を補ってそのサーバーを呼びます。サーバーに繋がらないときは
上の内蔵の呼び出し（OpenStreetMap）で答え、サーバー自身が返したエラーはそのまま担当に伝えます。

定期チェックインでは現在地を取得しないため、`route` は使えず、`place_search` は名前検索のみです。
メモ、過去のかけらの検索、宣言済みのWeb検索は使えます。
