# Hermes-4-405B subagent evaluation report

- Date: 2026-10-14 (JST)
- Environment: OpenShell 0.0.116 / `hermes-sandbox` / Nebius Token Factory Provider v2
- Configuration: parent `nvidia/nemotron-3-super-120b-a12b`, subagent `NousResearch/Hermes-4-405B`

[日本語](hermes-4-405b-visual-evaluation_ja.md) · [NemoClaw integration report](nemoclaw-hermes-integration.md) · [Model comparison](nemoclaw-hermes-model-comparison.md)

## Purpose

A direct request from kakeratta asked for a single-page, 1280×640 HTML infographic explaining how Hermes Agent and kakeratta work together. The run examined the quality of an artifact generated by Hermes-4-405B as a subagent and how the parent relayed its output.

This was not a controlled model benchmark. A comparison giving Nemotron-3-Ultra the identical prompt had not been conducted.

## Run results

| Metric | Observation |
| --- | ---: |
| Subagent API calls | 2 |
| Subagent execution time | Approximately 44.3 seconds |
| Subagent final response | 5,811 characters |
| HTML sent to kakeratta | 4,996 characters |
| String similarity between subagent response and final reply | Approximately 92.5% |
| Parent API calls | 28 |
| `reply_request` | HTTP 200; completed successfully |

The subagent's 5,811 characters included the completed HTML, an introduction, Markdown code fences, and a self-assessment claiming that the requirements were met. The Super parent removed the surrounding material and submitted the self-contained HTML, from `<!DOCTYPE html>` through `</html>`, using `reply_request`. The main HTML and CSS were retained, so the final artifact's quality problems were largely not caused by the parent's rewriting. The original subagent response remains in the Hermes session database.

## Artifact quality

What worked:

- The HTML was self-contained, with no external assets or JavaScript.
- It explicitly named Hermes, kakeratta, NemoClaw, OpenShell, MCP, and Nebius Token Factory.
- It represented Hermes and kakeratta as cards on the left and right, with a bidirectional arrow in the center and a list of key points below.
- It produced a visual HTML/CSS artifact rather than only explanatory prose.

Problems:

- The diagram was a simple arrangement of two cards and a text arrow. It did not explain the flow or responsibility boundaries in much visual detail.
- The body text was English, without localization for the Japanese-speaking user.
- It claimed to fit within 1280×640, but placed a heading, a 240px diagram, spacing, and a six-item list inside a fixed-height 580px container with `overflow: hidden`. The CSS dimensions made clipping at the bottom likely.
- It reported compliance without rendering the page in a browser or inspecting a screenshot.
- It added an introduction, code fences, and an explanation afterward when only HTML was requested.

The run demonstrated text generation and self-contained HTML creation, but strict constraint verification and the finished visual design were insufficient.

## Review instructions were not passed through

The distributed skill and kakeratta's direct-request context instructed the parent to give the subagent these Action–Review requirements:

- Action: perform the necessary research and creation immediately, without spending turns on a written plan.
- Review & Refine: critically check factual accuracy, completeness, format, prohibited elements, naming, character limits, viewport dimensions, and other constraints; fix defects within the same session.

Inspection of the saved subagent session showed that the parent actually sent Hermes-4-405B only a request to create an HTML infographic and return the complete HTML, along with a description of the execution environment. It omitted Action–Review, actual rendering, and defect-correction instructions.

This run therefore cannot be used to judge the quality of Hermes-4-405B with Review enabled. It was a generation result without Review, and the Super parent's omission of delegation instructions contributed to the constraint-checking failure.

## The Super parent's relay behavior

The subagent returned the artifact in two API calls, but Super did not immediately pass it to `reply_request`. Instead, it read and wrote files, attempted code execution that was refused, and ran multiple checking commands, using 28 API calls in total. The final HTML was valid, but this relay was slow and costly.

The skill and direct-request context said to return the subagent's result without recreating it. That was a model instruction, not an enforcement mechanism. Reliable forwarding without modification would require a code path that sends the delegated result directly to `reply_request.text`, without returning it to another parent-model inference step.

## Reasoning mode

This test did not explicitly enable Hermes-4-405B's specific thinking mode, and the skill's Action–Review instructions were also missing from the actual subagent prompt. Correctly enabling thinking mode or passing the Review instructions might improve the result, but textual self-review alone cannot reliably detect every rendering problem. Visual artifacts need a combination of checks:

1. Render the HTML in a browser at the requested dimensions.
2. Inspect a screenshot or DOM dimensions.
3. Check overflow, clipping, readability, language, and required elements.
4. Fix any problems and check again.

## Operational decision

After this evaluation, the subagent model was switched back to `nvidia/Nemotron-3-Ultra-550b-a55b`. Super remained the parent, and the Ultra subagent was configured with `delegation.reasoning_effort: high`. A short live delegation confirmed that Ultra responded as requested.

In this configuration, Super handles fetching and replying through kakeratta MCP and the outer tool control. The Ultra subagent concentrates on delegated generation and reasoning. Earlier tool-calling problems observed when Ultra acted as the parent planner therefore do not directly prevent its use as a subagent here. The main subagent evaluation criteria are artifact quality, constraint compliance, reasoning time, and cost.

For subsequent direct requests, the intended procedure was to launch the first Ultra subagent with Hermes's `role=orchestrator`. This supervising Ultra would delegate generation to a separate leaf Ultra and review the result, rather than create the artifact itself. If the result failed review, it would send the original constraints, the complete candidate, and specific defects to a new leaf Ultra for revision. The procedure allowed the initial generation plus at most two revisions, for three leaf calls in total. Super would handle only the initial delegation and return of the final result. Nested delegation required `delegation.max_spawn_depth: 2` in the Hermes configuration.

### Live nested-delegation check on 2026-10-14

After applying skill v25 and `max_spawn_depth: 2`, the same direct request for an HTML infographic was run. Super's `delegate_task` arguments included `role: "orchestrator"`, and the cron session had loaded the full text of skill v25. However, the parent constructed the delegation `goal` as a request to create HTML and omitted the Generate–Review procedure from both `goal` and `context`. Ultra, despite being launched as an orchestrator, created the HTML itself without calling its own `delegate_task`.

Super also used files, code, and the terminal after fetching the request and before delegation, then processed the artifact again afterward. The parent ultimately made 31 API calls and successfully sent 833 characters of complete HTML, from DOCTYPE through the closing HTML tag, via `reply_request`. The intended Super → supervising Ultra → leaf Ultra generation-and-review loop did not run.

This result shows that natural-language skill instructions and `role=orchestrator` alone cannot enforce role separation. Reliable execution requires Hermes-side delegation orchestration or a dedicated tool that controls the supervisor's fixed prompt, the number of leaf calls, candidate handoff, pass/fail decisions, and retries in code.

Any reevaluation of Hermes-4-405B should give Ultra the identical request and complete Review instructions and apply the same dimension checks. Compare API calls, elapsed time, tokens, and rendered output as well as the artifact itself.
