# Hermes-4-405B 子エージェント実測レポート

日時: 2026-10-14 (JST)  
環境: OpenShell 0.0.116 / `hermes-sandbox` / Nebius Token Factory Provider v2  
構成: 親 `nvidia/nemotron-3-super-120b-a12b`、子 `NousResearch/Hermes-4-405B`

[English](hermes-4-405b-visual-evaluation.md) · [NemoClaw統合レポート](nemoclaw-hermes-integration_ja.md) · [モデル比較レポート（英語）](nemoclaw-hermes-model-comparison.md)

## 目的

kakerattaの直接依頼から、Hermes Agentとkakerattaの連携を説明する1280×640の単一ページHTML図解を生成させ、Hermes-4-405Bを子エージェントとして使った場合の生成品質と中継動作を確認した。

これは統制されたモデルベンチマークではない。Nemotron-3-Ultraへ同一プロンプトを与えた対照試験はまだ実施していない。

## 実行結果

| 項目 | 観測値 |
| --- | ---: |
| 子モデルのAPI呼び出し | 2回 |
| 子の実行時間 | 約44.3秒 |
| 子の最終応答 | 5,811文字 |
| kakerattaへ送ったHTML | 4,996文字 |
| 子応答と最終返信の文字列類似度 | 約92.5% |
| 親モデルのAPI呼び出し | 28回 |
| `reply_request` | HTTP 200、正常完了 |

子の5,811文字には、完成HTMLのほかに導入文、Markdownコードフェンス、要件を満たしたとする自己評価が含まれていた。親Superがそれらを除去して、`<!DOCTYPE html>` から `</html>` までの自己完結HTMLを `reply_request` で送信した。主要なHTMLとCSSは維持されており、最終成果物の品質低下はほぼ親の書き換えによるものではなかった。元の子応答はHermesのセッションDBに保存されており、失われていない。

## 生成物の品質

良かった点:

- 外部アセットとJavaScriptを使わない自己完結HTMLだった。
- Hermes、kakeratta、NemoClaw、OpenShell、MCP、Nebius Token Factoryを明記した。
- Hermesとkakerattaを左右のカード、中央の双方向矢印、下部の要点一覧で表現した。
- 単なる説明文ではなく、HTML/CSSによる視覚的な成果物を生成した。

問題点:

- 図は2枚のカードと文字の矢印を中心とする簡素な構成で、フローや責任境界を視覚的に詳しく表現していない。
- 本文は英語で、日本語利用者向けのローカライズがなかった。
- 1280×640に収まると自己評価したが、固定高さ580pxのコンテナ内に、見出し、240pxの図、余白、6項目の一覧を配置し、`overflow: hidden` を指定している。CSSの寸法上、下部が切れる可能性が高い。
- ブラウザでのレンダリングやスクリーンショット検査を実施せず、誤った適合判定を返した。
- HTMLだけを返すべき場面で、導入文、コードフェンス、事後説明を付加した。

したがって、文章生成と自己完結HTMLの作成能力は確認できたが、制約の厳密な検証と視覚設計の完成度は十分ではなかった。

## Review指示の伝達不良

配布Skillとkakerattaの直接依頼コンテキストには、子に次のAction–Reviewを指示するよう記載されていた。

- Action: 計画文にターンを使わず、必要な調査・作成を直ちに実行する。
- Review & Refine: 事実、完全性、形式・禁止事項・命名・文字数・viewportなどの制約を批判的に検査し、欠陥を同一セッション内で修正する。

しかし、保存された子セッションを調べると、親が実際にHermes-4-405Bへ渡したプロンプトは、HTML図解を作り完全なHTMLを返すという依頼と実行環境の説明だけだった。Action–Review、実レンダリング、欠陥修正の指示は子へ渡っていなかった。

したがって、この実測を「Reviewを実行したHermes-4-405Bの品質」と評価してはならない。これはReviewなしの生成結果であり、制約検査の失敗には親Superによる委譲プロンプトの脱落も影響している。

## 親Superの中継動作

子は2回のAPI呼び出しで成果物を返したが、親Superは結果を直ちに `reply_request` へ渡さず、ファイルの読み書き、実行が拒否されたコード処理、複数の確認コマンドを行い、合計28回のAPI呼び出しを使った。最終HTMLは有効だったものの、この中継は遅く高コストである。

Skillと直接依頼コンテキストには「子の結果を再作成せず、そのまま返す」と記載したが、これはモデルへの指示であり強制機構ではない。確実な無加工転送が必要なら、委譲結果を親の次の推論へ戻さず、コードで `reply_request.text` に渡す経路が必要になる。

## 推論モードについて

この試験ではHermes-4-405B固有のthinking modeを明示的に有効化しておらず、Skillに書いたAction–Reviewも実際の子プロンプトから脱落していた。thinking modeやReview指示を正しく渡せば改善する可能性はあるが、テキスト上の自己検証だけで表示崩れを確実に発見できるとは限らない。視覚成果物では次の検査を組み合わせる必要がある。

1. 指定寸法でHTMLをブラウザにレンダリングする。
2. スクリーンショットまたはDOM寸法を検査する。
3. はみ出し、切れ、可読性、言語、必須要素を確認する。
4. 問題があれば修正して再検査する。

## 運用判断

比較後、子モデルは `nvidia/Nemotron-3-Ultra-550b-a55b` に戻した。親はSuperのままとし、子Ultraには `delegation.reasoning_effort: high` を設定した。短い実委譲でUltraが指定どおり応答することを確認した。

この親子構成では、kakeratta MCPの取得・返信と外側のツール制御は親Superが担当する。子Ultraは委譲された生成・推論に集中するため、Ultraを親プランナーとして使った過去のツール呼び出し不具合が残っていても、今回の子モデル用途を直接妨げるものではない。子の評価対象は主に成果物品質、制約遵守、推論時間とコストである。

今後の直接依頼では、最初の子UltraをHermesの `role=orchestrator` で起動する。監督Ultra自身は成果物を作らず、別のleaf Ultraへ生成を依頼して結果をレビューする。不合格なら、元の制約、完全な候補、具体的な欠陥を新しいleaf Ultraへ渡して修正版を依頼する。初回生成に加えて修正を最大2回、合計3回のleaf呼び出しを許可する。親Superは最初の委譲と最終結果の返却だけを担当する。ネスト委譲のため、Hermes設定は `delegation.max_spawn_depth: 2` とする。

### 2026-10-14 ネスト委譲の実地確認

Skill v25と `max_spawn_depth: 2` を適用した後、同じHTML図解の直接依頼を実行した。親Superの `delegate_task` 引数には `role: "orchestrator"` が入っており、cronセッションにもSkill v25の全文がロードされていた。しかし親が委譲の `goal` を「HTMLを作成する」と組み立て、Generate-Review手順を `goal` / `context` に含めなかった。監督として起動されたUltraも、自分の `delegate_task` を使わず直接HTMLを作成した。

親Superは取得後・委譲前にもファイル、コード、terminalを使用し、委譲後も成果物を再処理した。最終的に親は31回のAPI呼び出しを行い、833文字の完全なHTML（DOCTYPEから閉じHTMLタグまで）を `reply_request` で正常送信したが、意図したSuper → 監督Ultra → leaf Ultraの生成・Reviewループは実行されなかった。

この結果から、Skillの自然言語指示と `role=orchestrator` だけでは役割分離を強制できない。確実に実行するには、Hermes側の委譲オーケストレーションまたは専用ツールで、監督用の固定プロンプト、leaf呼び出し回数、候補の受け渡し、合否と再試行をコードとして制御する必要がある。

Hermes-4-405Bを再評価する場合は、Ultraへ同一の依頼とReview指示を省略せず渡し、同じ寸法検査を行う。成果物だけでなくAPI呼び出し回数、所要時間、トークン、レンダリング結果を比較する。
