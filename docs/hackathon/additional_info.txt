### Which model(s) did you use, and why did you choose that size/variant?

kakeratta uses six models through Nebius Token Factory, chosen by how often each task runs and how much a mistake affects later work:

- Nemotron 3 Super (120B, 12B active) is the everyday workhorse. It is the default Router, runs ordinary persona research, writes ordinary persona answers, and keeps memory notes. These roles run on every post, so speed, quality, and cost all matter. It also runs the once-a-day work: daily and monthly check-ins, memory tidying, and the day's and month's summaries. On October 28, moving a production daily run for nine personas from Super VL to Super cut its estimated cost from about $0.061 to $0.025, mostly by eliminating reasoning tokens. I briefly moved answers and notes to Nemotron 3.5 Lightning, which is fast and cheap on simple turns, but on one ordinary reply about a family member it hit the 26,000-token output limit three times in a row, about 80 seconds each, and never produced an answer.
- Nemotron 3.5 Super VL handles ordinary direct `@ai` questions as well as work whose mistakes carry forward: research for deep requests, schedule planning and review, and research and final answers for personas set to always think deeply (including Markdown infographics with emoji and Mermaid). I briefly made it the default for everything, but in production routing its median reasoning was about 1,430 tokens against Super's 70, so I kept it where that longer reasoning pays off.
- Nemotron 3 Ultra (550B, 55B active) handles rare or high-impact tasks: drafting personas and composing final answers for deep requests. Because a poorly written routing condition affects every later post, persona drafting justifies the largest model. In my Hermes environment, Ultra also handles direct @agent requests.
- Nemotron 3.5 Lightning (30B, 3B active) handles optional voice-input cleanup.
- GLM-5.3-Flash analyzes each attached photo or screenshot once per post, sharing the text description with the relevant personas.
- Qwen3-Embedding-8B powers semantic search over past fragments, with vectors stored in Firestore.

I arrived at this allocation by testing the actual tasks. A smaller model was not always faster, and a larger model was not always necessary.

Unless stated otherwise, the Super measurements and production observations below used Nemotron 3 Super (120B, 12B active).

### How would you rate Nemotron's output quality for your use case?

7/10

Native tool calling and Japanese-language quality were strong. Super and Ultra reliably returned tool calls when required, and their Japanese answers felt natural, which matters for an app built around casual personal notes.

When I switched the default from Nemotron 3 Super to Nemotron 3.5 Super VL on October 16, the token prices and prompts stayed the same, but reasoning increased substantially—even on everyday tasks where I was already satisfied with 3 Super's quality. Across production routing calls, median reasoning rose from about 70 to 1,430 tokens, and median cost rose from about 0.12 yen to 0.30 yen per call: roughly 2.5 times as much. Super VL also spent 1,905 reasoning tokens just to write a one-line memory record. These are observations across production calls, not a controlled replay of identical inputs. They made Super VL too expensive as an across-the-board replacement, so I kept 3 Super for frequent everyday work and reserved Super VL for selected tasks. The implementation lessons document records the switch and measurements (https://github.com/takeshy/kakeratta/blob/main/docs/design/ai-lessons.md#14-a-newer-model-thought-far-more-and-a-smaller-one-never-stopped).

The weakness was consistency when several instructions had to be followed together. Three patterns kept appearing across Super and Ultra:

- Incomplete follow-through: A persona promised a reminder without creating its schedule, or recorded a future event as already done.
- Copying examples literally: A route-search sample with "mode": "foot" led to "about 259 minutes on foot" for a trip that called for driving.
- Weak recovery and perspective: One check-in repeated the same rejected lookup ten times instead of switching to the search it was offered. When I noted that a friend's father had given me taranome sprouts, his persona thanked me on his behalf, as if I had given him the sprouts.

The same pattern appeared in Hermes Agent, running in an NVIDIA NemoClaw sandbox and connected through MCP. When answering for a persona, Super wrote a good answer but printed it to the console instead of calling submit_answer, because Hermes's own prompt said final responses were delivered automatically. After I clarified the submission rules in the skill and tool responses, Hermes reliably delivered 30 persona replies in production from September 27 to October 2 (https://github.com/takeshy/kakeratta/blob/main/docs/reports/nemoclaw-hermes-integration.md).

Direct @agent requests to Hermes showed a similar limit with multi-step instructions. When the skill told the Super parent to delegate the job to an Ultra subagent and review the result, the parent did the work itself, dropped the review steps, and ran dozens of rounds. I tried a review-and-retry loop in code, but it rarely improved the output and wasted tokens. Instead, a worker script now runs an Ultra Hermes session without a separate review loop, and the agent returns Markdown that the app renders rather than generating complex HTML. Each run has iteration, time, and usage limits (https://github.com/takeshy/kakeratta/blob/main/docs/design/direct-request-worker-spec.md).

These experiences shaped kakeratta: small single-purpose phases, tool lists built from the tools each persona actually holds, validation in code, a cap on repeated malformed reads, and a check that promised reminders were actually planned. Nemotron was capable enough to build on, but reliable execution required enforcing boundaries in code rather than relying on prompts alone.

### Did you fine-tune, prompt-engineer, or use Nemotron out of the box? What was your approach?

I did not fine-tune. I used Nemotron out of the box with prompt and context design, native tool calling, and checks in code. Production failures and usage measurements guided the changes. Seven changes mattered most.

1. Routing became condition matching. At first a lightweight Router read each persona's full purpose and decided who should receive a post. It missed posts that seemed clearly relevant. Ultra did better, but routing runs on every post. Instead of keeping the larger model, I simplified the task: Ultra helps write a short routing condition for each persona when it is created, and the Router only checks the post against those conditions. It must also give a reason for every persona it excludes. Those reasons let users see why a persona was not called and ask the AI to revise its condition.

2. The Router was chosen by replaying real posts. I replayed 20 posts from my production timeline, giving every model the same conditions and thread context, with thinking enabled. As a reference, I compared each model's decisions with Jev, a specialized decision model:

- Nemotron 3 Super: 1.91 s mean latency, $0.00065 est. cost/post, 17/20 agreement with Jev
- Nemotron 3 Ultra: 2.28 s mean latency, $0.00300 est. cost/post, 19/20 agreement with Jev
- Nemotron 3.5 Lightning: 6.55 s mean latency, $0.00047 est. cost/post, 17/20 agreement with Jev
- Nemotron 3 Nano: 9.26 s mean latency, $0.00046 est. cost/post, 19/20 agreement with Jev

On the five posts where the models disagreed, a manual check found that it followed the conditions each time. This is a comparison, not an accuracy benchmark. The surprise was that the smallest models were the slowest: Lightning and Nano generated about seven times as many output tokens as Super. With thinking off they became fast but fell to 11 of 20. Super's three disagreements all concerned whether an activity, such as a weekend visit to a hair salon, should also go to the daily-routine persona. A person could read those cases either way, so Super became the default Router. The full report (https://github.com/takeshy/kakeratta/blob/main/docs/reports/routing-model-comparison-2026-09-19.md) describes the method.

3. Answering, planning, and memory became separate steps. When one response had to contain the answer, notes, schedules, and actions, answers got shorter and promised operations were still missing. Now the persona first researches and writes its answer. A separate phase then plans schedules against that fixed answer, only for personas permitted to schedule. Code validates the plan, and Super VL reviews any plan with schedules against the request and the answer's promises; a failed review regenerates the schedule plan. After publication, a note keeper decides what to remember from the user's own words, so a memory failure never hides a good answer.

On October 17, I simplified memory further: each persona now keeps one file of records and grounded current facts. I removed the separate prose summary and gave facts more room to retain tendencies, conditions, exceptions, and useful changes over time, with their original-post sources. An ordinary turn makes one keeper call to append a short tagged record, or decide nothing needs keeping, without loading existing facts, older records, or the newly generated answer. At check-in (daily, or monthly for people set to monthly), new records are folded into facts and removed, and facts are enriched, merged, or deleted as circumstances change. New facts must cite source records; updates and merges retain the existing sources. Post edits and record reviews retain the fuller correction path. This replaces the earlier field-selection step. In the first production posts after the change, the note call on Nemotron 3 Super cost about $0.0007 and took about two seconds, and a whole post - routing, answer and note - cost $0.0028 to $0.0037 (about 0.4 to 0.55 yen). These are two posts, not an average.

4. Each stage got the model it needs. Super handles research and ordinary answers. For a deep request, Super VL does the reading and Ultra only composes the final answer from the full transcript. A deep request is recognized by explicit phrases such as "詳しく" ("in detail"), with no extra model call. Each round, the host also tells the model its remaining Web-search allowance and removes reads that are no longer available. In production, a deep reply before this split used 17 calls, 14 of them Ultra research rounds, for about $0.274; one after it used six calls for about $0.027. The questions differed, but repricing the new reply's tokens under the old assignment gives $0.052, so the model split alone accounts for a 48% difference. The usage report (https://github.com/takeshy/kakeratta/blob/main/docs/reports/production-model-usage-after-improvements-2026-10-05.md) records the method.

5. Production logs drove the cost work. An October 7 review of 112 calls found that silent daily check-ins were still paying for reads, empty answers, and schedule plans. One persona sent an invalid period lookup ten times in one check-in and eight times in the next. I gave each read tool its own argument schema with a correct period-search example, ended research after three malformed responses, and ran schedule planning only for personas allowed to schedule. The cost report (https://github.com/takeshy/kakeratta/blob/main/docs/reports/production-ai-cost-2026-10-07.md) has the details. I then restructured the daily check-in: the app summarizes the day's posts once and every persona reads that shared summary, and a persona with no new posts, no record due for review, and no plan within a week can skip the conversational part of a daily check-in. Memory maintenance runs first and may still need a model call.

6. Extra layers that did not help were removed. I tested Switchyard v0.3.0 as a second routing layer that picked which model would answer. In five synthetic cases, the direct path averaged 2.84 seconds and Switchyard 9.56 seconds. Its classifier produced 9,746 output tokens and sent a reconsideration request to Lightning instead of Ultra. These were single runs, not a full benchmark, but they did not justify the extra layer, so I removed it. The comparison report (https://github.com/takeshy/kakeratta/blob/main/docs/reports/switchyard-comparison-2026-10-03.md) records the experiment.

7. Hermes request handling moved into code. The worker now claims persona requests and submits answers itself, exposing only read_for_ask and permitted Web tools to the model. In two recorded production runs on October 16, both using Nemotron 3.5 Super VL, the old flow used four model calls and 62,847 input tokens; the new flow used two calls and 15,774 input tokens. Estimated inference cost was about $0.0205 versus $0.0062, roughly 70% lower. This is a comparison of two runs, not an average saving across all requests. The integration report records the sessions and token counts (https://github.com/takeshy/kakeratta/blob/main/docs/reports/nemoclaw-hermes-integration.md#code-driven-persona-ask-optimization-verified-2026-10-16).

### How did Nemotron's performance compare to other models you've used for similar tasks?

In everyday development, Nemotron was competitive with models such as Gemini for Japanese responses and tool calling. That is a practical impression, so I also ran two direct comparisons with OpenAI models through OpenRouter.

Routing: I ran the same 20 routing posts through GPT Luna with required tool calling. With reasoning on, Luna averaged 3.65 seconds at an estimated $0.00042 per post and agreed with Jev on 19 of 20. With reasoning off, it averaged 2.02 seconds at $0.00037 and still agreed on 19 of 20. Nemotron 3 Super, the default at the time, averaged 1.91 seconds at $0.00065 and agreed on 17, with its disagreements on borderline cases. Unlike Lightning and Nano, Luna did not lose agreement without reasoning, so whether reasoning can be turned off depended on the model, not just the task.

A real conversation: I replayed a three-turn production thread on Luna (Router and middle model) and GPT Sol (high model), with the same Web search tool that production had. The user asked about "Grok Bot," a new xAI product separate from the ordinary Grok app, then asked for details, then for a diagram.

- Super / Ultra (production): 9 LLM calls, 0 Web searches, $0.039 LLM cost, 35.2 s total API time
- Luna / Sol: 10 LLM calls, 6 Web searches, $0.058 LLM cost, 64.8 s total API time

Nemotron never searched. It described the ordinary Grok app, and Ultra added a detailed timeline, plan prices, and storage rules it could not verify. Luna also took Grok Bot for ordinary Grok in the first turn, even after two searches, but on the follow-up Luna's searches found xAI's announcement, and Sol used it to explain what Grok Bot is and who can use it. That cost about 50% more and took nearly twice as long.

This is one thread replayed with the current code, not a controlled benchmark. Nemotron was the fastest Router, though Luna matched or beat it on agreement at a lower cost; where Nemotron clearly fell short was knowing when to look something up. That is why I measure each model on the work I actually want it to do.

For image analysis, I compared GLM-5.3-Flash with Nemotron 3.5 Super VL. In my photo-description tests, quality was similar while Super VL cost nearly twice as much, so I kept GLM-5.3-Flash.

### Which Nebius platform capabilities were most valuable to your project and how?

Two platform capabilities were particularly valuable to kakeratta:

1. Direct template and reasoning control via chat_template_kwargs.
In kakeratta's routing experiments, Nemotron 3.5 Lightning and Nano spent 6–9 seconds generating long reasoning traces for simple categorization tasks. Passing a top-level flag did not disable thinking on Token Factory; it required chat_template_kwargs: {"enable_thinking": false}. That control let me compare latency, cost, and routing agreement with thinking on and off, using the same posts.

2. Native tool calling with tool_choice: "required".
Early versions of kakeratta asked models to emit JSON actions in prose, but personas sometimes recorded a reminder in a note without creating its schedule. Native tool_calls gave the host a structured proposal to inspect. kakeratta validates arguments, permissions, and consistency before execution, and rejects or retries malformed proposals. Required tool calling makes submitting an answer or choosing silence explicit; it does not replace those checks.

### How likely are you to recommend running Nemotron on Nebius to other developers?

8/10

I would recommend it for applications that make many small decisions around each user interaction. In kakeratta, routing, research, schedules, and memory each need their own calls. Keeping most of that work on Super, and reserving Super VL and Ultra for selected tasks, made the cost practical for everyday use.

I stop at 8 because low token prices do not remove the work of building a reliable application. I still needed validation, retry limits, and ways for users to correct mistakes. Developers should test the model on their actual tasks, especially when deciding whether to search or how to respond to a correction.

### How would you rate your experience running Nemotron inference on Nebius compared to previous cloud or local development environments?

8/10

I could not run the 120B and 550B models on my own hardware. Token Factory let me test them through an OpenAI-compatible API without operating GPU servers. In my production observations, it handled concurrent persona calls, and I observed no 429 errors or timeouts.

The model-by-model usage and spending view was especially useful: I could compare the console totals with application logs when changing model assignments or investigating expensive Hermes sessions. The billing incidents described below also showed why visibility alone is not enough; I want a hard spending stop as well.

The main model limitations were accepting corrections and selecting a fast Router. The conversation replay and routing experiments above describe those failures. They made testing on my own workload essential even though accessing the models was straightforward.

### What additional features or improvements would have made the Nemotron on Nebius experience more effective for your project?

Two additions would help most: billing tools for individual app users and hard spending limits for developers.

For end-user billing, I currently have two options. I can ask each user to create a Nebius account and paste an API key, or I can use my own key and build the accounting myself. I would like an API that lets an application issue and revoke credentials for each user, retrieve priced usage for each credential, set a spending limit or prepaid balance that can be topped up from the app, and stop inference automatically when the balance reaches zero. A small starter allowance would also help. A personal AI needs time to build useful memory, and asking people to configure billing before they experience that value makes onboarding harder.

For developer billing, I could not find a way to stop inference when my credit ran out. This mattered twice during the project. In the first case, a coding agent used the Token Factory key in my environment without my intending it to. It used up my remaining $25 credit, and a $55 invoice followed. In the second case, a network-policy change broke Hermes Agent's MCP credentials, while my wake-up check treated errors as a reason to start the agent. Hermes woke every minute without usable tools and entered debugging loops of up to 60 turns. Running on Hermes-4-405B, the model Hermes used at the time, it used 34.54 million input tokens and 0.15 million output tokens, costing $34.98 in total.

The second incident was caused by my own configuration. I fixed the wake-up check to stop on errors, reduced the turn limit to 15, and restored the credential policy. The incident report (https://github.com/takeshy/kakeratta/blob/main/docs/reports/nemoclaw-hermes-runaway-incident.md) documents the cause and the fixes. A platform spending cap would have limited the bill, and a spending alert would have helped me notice the problem sooner. Even without credit running out, daily spikes were a risk: on October 13, testing direct requests through Hermes cost nearly $10 in one day, before the worker's usage checks existed. The worker now checks cumulative usage before and after each direct-request run and stops further runs at the limit. A running session can still exceed that threshold, so a provider-enforced cap per API key would offer protection beyond these application checks.

### What do you most hope to see from the Nemotron team next?

First, I would like a model specialized for fast, structured decisions. kakeratta's Router does not need to write prose. It needs to evaluate one post against several persona conditions and return a reliable decision, with reasons for each exclusion.

Routing requires checking many conditions at once. Lightning and Nano took a long time with thinking enabled and made more routing errors without it. Super is the practical default, but it is a large model for a classification task.

Jev showed what a specialized model could offer. On the same 20 posts, it averaged 0.37 seconds and about $0.00017 per post, roughly one quarter of Super's estimated cost. Manual review favored its decisions in all five cases where the original models disagreed. kakeratta now offers Jev through OpenRouter, but Super remains the default because Jev does not provide the exclusion reasons that the routing-inspection and refinement features rely on. I would like a Nemotron model with Jev's speed and cost profile that also gives useful decision reasons without a long reasoning trace. Routing, validation, and workflow review could all benefit from it.

The move from 3 Super to 3.5 Super VL also made me want finer control over reasoning effort. For tasks where 3 Super's quality was already sufficient, longer reasoning raised costs without solving a problem I needed solved. I would like the newer model to use less reasoning on those tasks, with a configurable reasoning budget that preserves reliable tool calling and instruction following.

Second, I would like managed retrieval that connects directly to inference. I would like to create a persistent store, add documents or memories to it, and pass its ID with a Nemotron request. The platform would handle embedding, retrieval, reranking, and adding the relevant context. The application could then focus on what to remember instead of maintaining the retrieval pipeline.
