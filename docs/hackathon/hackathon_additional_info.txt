## Which model(s) did you use, and why did you choose that size/variant?

By default, kakeratta uses five models through Nebius Token Factory. Models are assigned by role based on call frequency and how far the consequences of an error can propagate.

Nemotron 3 Ultra (550B, 55B active) — Persona drafting and deeper follow-up answers on request. Drafting happens infrequently, but a bad routing condition can affect every later post, so I assign it to the largest model. Ultra is also used when a user explicitly asks a persona to reconsider or explore an answer in greater depth.

Nemotron 3 Super (120B, 12B active) — The default Router, normal persona responses, and pre-execution review of plans that include schedules or external actions.

Nemotron 3.5 Lightning (30B, 3B active) — Narrow, contained tasks: judging whether a reply explicitly asks for a deeper answer, and proofreading or formatting voice input. For the reply judgment, Lightning with thinking disabled matched Super on all 15 test cases while running at about half the latency (0.67 s vs 1.30 s) and roughly one fifth of the cost.

GLM-5.3-Flash — Image understanding. Each image is analyzed once per post and the result is shared with every relevant persona.

Qwen3-Embedding-8B — Embeddings for semantic search over the timeline and persona memories, with vectors stored and queried in Firestore.

I arrived at this allocation through experiments with routing accuracy, latency, cost, reasoning settings, and tool use. Super became the default for high-frequency agentic work, Lightning is limited to tasks where mistakes remain contained, and Ultra is reserved for lower-frequency work where an error can have a larger downstream effect or where the user explicitly asks for deeper reasoning.

## How would you rate Nemotron's output quality for your use case? (1 = Poor, 10 = Excellent)

7 / 10

The strongest parts were native tool calling and Japanese-language quality. With tool_choice: "required", Super and Ultra reliably returned valid tool calls, which became the foundation for kakeratta's routing, persona workflows, and execution review. Japanese posts and responses also worked naturally, and I encountered no language-related problems.

The main difficulty was consistency in multi-step instructions. In one representative case, an example in my route-search tool specification contained "mode": "foot", and the travel persona copied that value literally, answering "about 259 minutes on foot" for a distance that clearly called for driving.

I also encountered cases where a model exposed its internal plan in the user-facing reply, recorded a future event as already completed, or promised a time without creating the corresponding schedule. I observed these issues with Ultra as well as Super.

The same literalism appeared when I let Nemotron 3 Super run as an external planner inside Hermes Agent (an agent framework running in an NVIDIA NemoClaw sandbox, connected to kakeratta over MCP). Hermes's cron job prompt says the model's final response is delivered for it. Super took that at its word: it researched an ask for about 50 seconds, wrote a good answer, printed it to the console, and stopped without calling the submit tool, so the ask timed out and kakeratta's built-in model answered instead. When the deliverable was a nested JSON workflow the call was never skipped, but once it became plain text the model treated printing as delivery. The fix was again structural rather than a prompt tweak alone: the skill and the tool responses now state that printed text never reaches kakeratta, and a final check looks for claimed asks left unsubmitted.

In the same setup, Nemotron 3.5 Lightning was extremely fast (2-3 seconds) but omitted arguments, broke JSON in multi-step MCP calls, and fell into troubleshooting loops on transient tool errors, so I used Super as the planner at first. I later dropped Super after it confused two frameworks and kept the error even when I corrected it. I then tried Hermes-4-405B, the model Hermes Agent recommends, but that trial ended in the runaway bill described below. The planner now runs on Nemotron 3 Ultra, which kakeratta already uses for persona drafting and deeper answers.

Rather than relying on prompt tuning alone, I changed the application structure: workflows are validated before execution, models see only the tools and schema relevant to their role, and deterministic checks are handled in code. The original failures are now covered by regression tests.

Tool calling and Japanese-language quality were strong, but reliable multi-step execution still required application-level safeguards, so I rate the raw output quality 7 / 10.

## Did you fine-tune, prompt-engineer, or use Nemotron out of the box? What was your approach?

I did not fine-tune. I combined prompt engineering, native tool calling, structured output, and application-level constraints on persona actions.

1. Shifting the Router from "judgment" to "condition matching"

Initially, Lightning directly judged which persona should receive a post. Each persona description included what that persona was trying to accomplish, and this led to misrouting: personas that clearly should have responded were sometimes not selected.

I temporarily switched the Router to Ultra. It was not perfect either, but it responded predictably to prompt changes and reached acceptable routing quality after several adjustments.

I then reconsidered the design itself. A single post can trigger multiple inferences, so even a relatively inexpensive Router matters when it runs on every post. For a Personal AI product, users should not have to wonder whether a note is worth sending to an LLM.

This led to a different hypothesis: if larger models were making better decisions while lightweight models struggled, perhaps the criteria I was giving the Router were too complicated.

Instead of describing what each persona does, the application now gives the Router a short, explicit condition describing which posts that persona should handle.

Ultra generates these conditions infrequently. The high-frequency Router only decides whether each post matches them.

I also made excluded_reasons mandatory for every persona that was not selected. Since concrete examples had sometimes distorted model behavior elsewhere in the application, I removed examples from the Router prompt as well.

2. Choosing the Router model by measurement

With the conditions simplified, I replayed the 20 most recent posts from my own everyday use of kakeratta across several Nemotron models.

Each model received the same posts, persona conditions, and thread context, with call order rotated per case. The replay did not activate personas, execute tools, or modify production data.

I manually labeled the expected routing for all 20 posts against the six persona conditions active at the time. This was a post-hoc baseline created after seeing the model outputs, not a pre-registered ground-truth dataset.

* Nemotron 3 Super: avg 1.91 s | p95 2.53 s | $0.00065/post (0.098 JPY) | baseline match 17/20
* Nemotron 3 Ultra: avg 2.28 s | p95 2.64 s | $0.00300/post (0.449 JPY) | baseline match 19/20
* Nemotron 3.5 Lightning: avg 6.55 s | p95 9.28 s | $0.00047/post (0.070 JPY) | baseline match 17/20
* Nemotron 3 Nano: avg 9.26 s | p95 22.85 s | $0.00046/post (0.069 JPY) | baseline match 19/20

Converted at 1 USD = 150 JPY.

The full measurements are in the [routing model comparison report](https://github.com/takeshy/kakeratta/blob/main/docs/routing-model-comparison-2026-09-19.md). The report compares each model against Jev's output, which matched my post-hoc baseline on all 20 posts, so its agreement counts are the same as the baseline matches here.

All four models were measured with thinking enabled. The surprising result was that the lightweight models were the slowest. Lightning and Nano each generated about 31,000 output tokens across the 20 calls, roughly seven times Super's output, because of their reasoning traces.

I tested disabling thinking with chat_template_kwargs.enable_thinking: false.

Latency improved sharply, to 1.40 s for Lightning and 1.16 s for Nano, but routing quality deteriorated. Nano fell from 19/20 to 11/20, with clear errors against the persona conditions. Lightning showed similar degradation.

For this workload, the reasoning trace was not merely overhead; it was contributing to judgment quality.

Super therefore became the default Router. At 1.91 s it was the fastest Nemotron model I measured with thinking enabled, while costing roughly one fifth as much as Ultra. Its three mismatches were concentrated around one boundary condition — whether plana should also receive same-day plans — rather than unrelated routing failures.

I use Lightning only for narrow tasks where mistakes remain contained. One example is the reply judgment described above: deciding whether a reply explicitly asks a persona to correct or deepen an answer.

If Lightning returns yes, the persona answers again on Ultra with a larger reading budget. A false positive costs one Ultra call; a false negative simply leaves the conversation on Super.

3. Letting users improve the Router

Exposing excluded_reasons led to a feature I had not originally planned.

When a routing decision feels wrong, users can say that they wanted a persona to answer, did not want it to answer, and optionally explain why.

An agentic rewrite step updates that persona's routing condition from the feedback and checks the same post through the Router. If the previously missed persona is selected, kakeratta accepts that decision without routing again and runs the persona's normal turn on the original post, including its reply and memory updates. Reply feedback works similarly: the user can accept a revised response and apply that exact preview to the original thread.

Even Ultra could not infer every user's preferred boundaries perfectly. Rather than trying to build a perfect universal Router, I designed one whose decisions users can inspect, correct, and refine over time.

4. Splitting each persona turn into phases

Personas do not change application state directly. An earlier design asked one call for the reply, notes, schedules, and tool calls as a single workflow. The model spent its attention on the schema, shortened replies to make room for required notes, and still sometimes omitted the second of a paired operation, such as promising a time without creating the schedule.

Each turn is now split by responsibility. The persona reads with read-only tools and hands in only its answer. Separate schedule and action phases then see that fixed answer and fill their own typed parts. Those phases must also state whether every promise in the answer is backed by an operation; a turn that cannot be made consistent is not published. Notes are not part of the turn: once the answer is out, a note keeper on the persona model writes them, so a note that fails to come out can no longer take a good answer with it (that is how a good answer once showed up as "stayed quiet"). The application assembles the parts into a workflow.

Each phase sees only the schema it needs, and a persona that cannot create schedules or take actions never sees those phases.

Anything that can be verified deterministically is checked in code. Only plans that include a schedule or an external action are reviewed by Super, and a failed review regenerates only the phase it blamed.

## How did Nemotron's performance compare to other models you've used for similar tasks?

Compared with models I have used for agentic tasks, including the Gemini family, Nemotron has been competitive in both tool calling and Japanese-language quality.

Super and Ultra reliably honor tool_choice: "required", which was especially important for an application that turns model output into structured operations rather than simply displaying generated text.

Two behaviors stood out during development.

Omitting the second of a paired operation. When the same intent had to appear in two forms, such as a note and a reply, or a time promised in a reply and the corresponding schedule entry, Nemotron sometimes omitted the second operation. I addressed this structurally by moving each operation into its own phase with an explicit consistency check, rather than adding more prompt instructions.

Literalism toward examples. Values included only as illustrations were sometimes adopted verbatim, such as the travel mode in a route-search example. I observed this with Ultra as well, so I reduced the amount of irrelevant schema and examples each persona sees.

The most interesting comparison came from the Router experiments described above. Disabling thinking made lightweight Nemotron models much faster, but significantly reduced routing quality.

To test whether this was an unavoidable tradeoff for low-cost reasoning models, I ran the same 20 posts through OpenAI GPT Luna using OpenRouter's Exacto provider and the same required-tool-call setup.

* Luna, reasoning on: avg latency 3.65 s | baseline match 19/20 | about $0.00042/post (0.063 JPY)
* Luna, reasoning off: avg latency 2.02 s | baseline match 19/20 | about $0.00037/post (0.055 JPY)

Unlike the lightweight Nemotron models, Luna retained the same baseline-match score with reasoning disabled.

This suggests that the degradation I observed when disabling thinking was specific to the lightweight Nemotron models on this multi-condition routing task, rather than an unavoidable property of low-cost reasoning models in general.

Japanese tokenization differs across model families, so token counts are not directly comparable. The costs above are the actual charges I observed.

## Which Nebius platform capabilities were most valuable to your project and how?

Token Factory was by far the most valuable.

kakeratta originally had an OpenAI-compatible abstraction that allowed users to choose among several AI providers.

After using Nemotron through Token Factory and measuring both output quality and actual cost, I made Nemotron the default for all three text-generation model roles.

Image understanding with GLM-5.3-Flash and embeddings with Qwen3-Embedding-8B are available through the same Token Factory API. This means the default kakeratta configuration can use text generation, vision, and embeddings through a single inference platform rather than requiring users to configure multiple providers.

Advanced users can still point individual model roles elsewhere, but ordinary use does not require choosing a provider or model.

Native tool calling was particularly important. tool_choice: "required" allowed kakeratta to implement routing, persona workflows, and execution review as actual tool calls rather than asking models to generate JSON inside normal responses.

Usage visibility also directly influenced the architecture. Being able to see consumption and actual cost by model helped me decide which work justified Ultra and which belonged on a cheaper tier. Those measurements were one reason I redesigned the Router instead of simply using Ultra everywhere.

The application itself runs on Google Cloud Run and Firestore and calls the Token Factory public API over HTTPS. The personas' web search tool uses Tavily with each user's own key (route search is separate and uses OSRM). I did not provision GPU instances on Nebius. I chose Google Cloud for the application infrastructure because I already work fluently with Terraform on GCP and wanted to spend the hackathon building the product rather than learning a new infrastructure stack at the same time.

## How likely are you to recommend running Nemotron on Nebius to other developers? (1 = Unlikely, 10 = Highly Likely)

7 / 10

I would recommend it to developers and teams building AI-centric services that benefit from using different model sizes for different kinds of work.

Having Lightning, Super, and Ultra behind one API made it easy to experiment with model allocation and compare latency, quality, and actual cost without changing providers.

The standout model in this project was Super. It was capable, fast, and affordable enough to become the center of kakeratta's agentic workload.

The main reason I stopped at 7 / 10 is that the model tradeoff changes depending on the product.

For a consumer-facing product such as kakeratta, Nemotron is a very good fit. Inference happens frequently, so cost and latency matter alongside quality. Super provides enough capability for agentic work at a price that makes repeated inference practical, while Ultra can be reserved for the smaller number of cases that justify a more expensive call.

For business-facing work, however, the tradeoff is different. When producing material that will be shown directly to customers, I care more about the highest possible reasoning and output quality than inference cost. For those workloads, I currently choose closed frontier models such as GPT-6 because I find the quality difference significant enough to justify the additional cost.

Since those models are not available on Nebius, I would use Nebius as a strong inference platform for cost-sensitive, high-volume workloads rather than as the single platform for every AI workload.

A secondary factor is infrastructure tooling: the official Nebius Terraform provider, public examples, and coding-assistant knowledge of Nebius are less established than for GCP, which is why I kept kakeratta's application infrastructure on Google Cloud.

## How would you rate your experience running Nemotron inference on Nebius compared to previous cloud or local development environments? (1 = Poor, 10 = Excellent)

8 / 10

The biggest difference from a local environment was being able to call whichever model I needed immediately.

Running several large models simultaneously on personal hardware is impractical, switching between them requires loading and unloading models, and Ultra-class models are not realistic to run locally. The model comparisons that determined kakeratta's current architecture would not have been practical on my own hardware.

Compared with other cloud AI APIs, the most striking quality was stability.

With other APIs, I have encountered 429 Too Many Requests responses during development with as few as four concurrent calls. During this project and at my usage volume, I did not encounter a single 429 response or inference timeout from Token Factory.

That mattered because one kakeratta post can fan out into several concurrent and chained model calls. After routing, selected personas run in parallel, and each persona may read data, answer, run its schedule and action phases, have the plan reviewed, and retry if the review rejects it. A failure anywhere in that chain can cause that persona's turn to be lost.

Usage visibility was another advantage. As I changed how Lightning, Super, and Ultra were allocated, I could immediately see the effect on actual spending by model.

The main limitation was image handling. Although multimodal Nemotron models exist, they were not available through the Token Factory public API I used. kakeratta therefore analyzes each image once with GLM-5.3-Flash and passes the result to personas as text.

This keeps the entire default model stack within Token Factory, but a persona cannot return to the original image to inspect a detail that the first analysis omitted.

I rate the experience 8 / 10: immediate access to different model sizes, stability across concurrent and chained calls, and clear usage visibility were major strengths. Direct image input to the persona models would improve it further.

## What additional features or improvements would have made the Nemotron on Nebius experience more effective for your project?

Two things: per-end-user billing primitives, and hard spending limits.

1. End-user credentials and billing. I wanted Token Factory to be embeddable in a consumer app. Today there are two options. I can ask every user to create a Nebius account and paste an API key, which is a large onboarding barrier. Or I can use my own credential server-side and build token accounting, per-model pricing, and cost tracking myself.

A scope below Project would solve this. I'd want to be able to:

issue and revoke credentials per end user
retrieve priced usage per credential via API
set per-user spending limits or prepaid balances, and top them up from the app
automatically suspend inference when a user's balance hits zero

A small starter allowance for new users would complete this. A personal AI only shows its value after it has accumulated enough memory to recall earlier events at the right moment. Requiring key setup and billing before that point loses most users.

2. Hard spending limits for developers. I couldn't find a way to disable automatic charging and stop inference when credit runs out.

This cost me twice. First, a coding agent picked up my Token Factory key from an environment variable and used it without my intending it to. My remaining $25 credit was exhausted, and a $55 invoice followed.

Second, later in the hackathon, my Hermes Agent wake-up check failed open on errors, and a network-policy change had silently broken its MCP credential binding. Hermes was woken every minute without usable tools and ran 60-turn self-debugging loops on Hermes-4-405B via Token Factory. It consumed 34.54M input tokens ($34.98) before I stopped it. The cause was my configuration, and I've since fixed it: the check now fails closed, turns are capped at 15, and the policy is restored. But nothing on the platform side would have stopped the spend. A hard limit, or even a spend alert, would have caught it on day one.

## What do you most hope to see from the Nemotron team next?

1. A Nemotron model specialized for structured decisions

kakeratta's Router evaluates every post against several persona conditions and decides which personas should receive it.

It does not need prose. It needs an accurate, fast, structured decision.

My benchmarks showed that the lightweight Nemotron models could either reason for a long time and remain reasonably accurate, or become fast when thinking was disabled but lose too much accuracy on this multi-condition task.

Super is currently the most practical Nemotron option, but it is still a large model for what is essentially a classification layer.

The limitation is not short judgment in general: Lightning with thinking disabled handles the narrow yes/no reply judgment well (see above). The difficulty appears when one input must be evaluated against many conditions simultaneously.

Late in development, I benchmarked TypeSafe's Jev on the same 20 routing cases. It averaged 0.37 s, cost about $0.00017 per post (0.026 JPY), roughly one quarter of the default Super Router, and matched my post-hoc baseline on all 20/20 posts.

That profile was compelling enough that kakeratta now offers Jev as an optional Router. Super remains the default because Jev does not return exclusion reasons, while kakeratta's routing-inspection and persona-refinement features depend on them.

What I want from Nemotron is therefore not simply a smaller general-purpose model. I want a model optimized for structured judgment across many conditions, without needing to generate a long reasoning trace.

Routing, validation, and workflow review often need only a typed decision. A first-party model of that shape inside Token Factory could move more of kakeratta's high-frequency decision layer from Super onto a smaller model without leaving the Nemotron ecosystem.

2. A File Search-style managed retrieval layer for Nemotron

The second thing I would like is a managed retrieval layer that can be attached directly to Nemotron inference.

Ideally, an application could create a persistent store, add documents or memories to it, and then pass that store's ID with an inference request. The platform would handle embedding, retrieval, reranking, and injecting the relevant context into the Nemotron request.

This is similar to the File Search-style workflow available on other AI platforms: the application manages the contents of the store, while the inference platform manages the retrieval pipeline.
