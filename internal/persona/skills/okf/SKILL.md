# メモの書き方（OKF）

あなたのメモは **OKF (Open Knowledge Format) v0.2** のバンドルです。
1つの概念につき1ファイル、YAML frontmatter と markdown 本文でできた、ただのファイルの集まりです。
スキーマ登録も要りません。`cat` できれば読めます。

メモはあなた専用です。他の担当は見ませんし、本体は中身を読みません。
**何を概念にするか、何を残して何を捨てるか、いつまとめるかは、すべてあなたが決めます。**

散文を1枚にまとめて書き直し続けると、何が落ちたか分からないまま痩せていきます。
名前と description の付いた概念に分けておけば、必要なものだけを読み、必要なものだけを直せます。

## 読み書き

メモを書くのは、返事が出たあとの**メモ係**としてのあなたです。返事を考えるときは読むだけで、書くのはメモ係のときです。
メモ係のときは、読むメモを先に選び（`choose_notes`）、本体が全文を渡します。その中身を見たうえで、変更を `write`（1ファイル全文）と
`forget`（path）の一覧で出します。次の `notes_*` は返事を考えるあいだ（と、予定の背景メモ）に使うものです。

- `notes_list` — 何を持っているかの一覧。起こされたときに毎回渡されます。
- `notes_read` — 中身を読む。`{"paths":["tastes/tonkotsu.md"]}`
- `notes_write` — 1ファイルを書く。`{"path":"…","text":"そのファイルの全文"}`
  そのファイルだけが丸ごと置き換わり、**他のファイルは触られません。**
- `notes_forget` — 1ファイルを捨てる。`{"path":"…"}`

変えないファイルを書き直す必要はありません。関係するものだけを読み、関係するものだけを書いてください。

## ファイルの置き方

```text
index.md                  # 目次。ルートのみ任意の okf_version を宣言可能
log.md                    # 任意。変更の履歴
tastes/tonkotsu.md        # 概念1つ = ファイル1つ
shops/jiro-mita.md
```

- **概念ID** は `.md` を除いたパスです（`shops/jiro-mita`）。
- `index.md` と `log.md` は**予約名**です。概念には使わないでください。
- ディレクトリで種類ごとに束ねてください（`shops/`, `tastes/`, `books/`, `threads/` など）。

## frontmatter

予約名以外のファイルは、必ず YAML frontmatter で始めます。**必須は `type` だけ**です。

```yaml
---
type: Shop                  # 必須。短く、それ自体で意味が分かる語
title: ラーメン二郎 三田本店   # 推奨。表示用の名前
description: 三田の豚骨。行きたいと言っていた店。  # 推奨。一文
resource: https://tabelog.com/…                   # 任意。実在の対象があるときだけ
tags: [ラーメン, 豚骨, 三田]                       # 任意
generated: { by: "process:note-keeper", at: 2026-09-12T17:00:00Z } # 任意。実際の作成者と更新日時
expires: 2026-09-13                               # 任意。過ぎたら本体が消す
review: 2026-10-15                                # 任意。過ぎたら本体が起こし、「まだ要る?」と聞く
---
```

- `type` は自由語です。登録簿はありません。自分の担当領域に合う語を決めて使ってください
  （`Shop` / `Preference` / `Book` / `Theme` / `Thread` / `Place` など）。
- `resource` は実在の対象に紐づくときだけ。傾向や手順のような抽象的な概念には付けません。
- あなた自身が出した情報（候補の一覧、検索結果、調べた経路、背景の解説）は、原則としてメモにしません。
  必要になったら、その時点で調べ直す方が正確です。例外的に残すときだけ、`expires` を付けます。翌日の日付でよく、
  日付だけならその日の0時に本体がそのメモを消します。ユーザーがそれに返事をした・選んだ・行ったなら、
  `expires` を外して書き直します。ユーザーから聞いたことには付けません。`expires` の無いメモを本体が消すことはありません。
- `review` は、ユーザーから聞いたことのうち、いつまで要るか分からないものに付けます。内容で日付を決めます。
  行きたい店なら数週間後、関心のある話題なら数か月後、好みや習慣には付けません。過ぎても本体は消さず、あなたを起こします。
  そのときユーザーに「そろそろ忘れていい？」と一言聞き、同じターンで `review` を1週間先に書き直します。
  返事が来たら、残すなら `review` を外して書き直し、延ばすなら日付を先へ、もういいなら forget_note。
- 独自のキーを足して構いません。`expires` と `review` はこのアプリの拡張です。
- v0.2 の `generated: { by, at }` は作成者と更新日時です。`by` は `human:<id>`、`process:<id>`、または `<producer>/<version>`。日時には UTC オフセットを付けます。旧 `timestamp` は既存メモに残っていても構いませんが、新しく書くときは `generated` を使います。作成者や日時が分からなければ省略し、推測で埋めません。
- 出典は任意の `sources` リストに書き、各要素に `resource`、必要なら `id` と `title` を付けます。本文の個別の主張は `sources[].id` と同じラベルの Markdown 脚注で対応付けます。旧 `# Citations` は既存メモの互換形式です。
- `verified`（確認者と日時）、`status`（`draft` / `stable` / `deprecated`）、`stale_after`（情報が古くなる日時）も任意です。`stale_after` はメモの削除期限ではありません。これらを省略しても v0.2 準拠です。

## 本文

普通の markdown です。**散文よりも構造**（見出し・箇条書き・表）を優先してください。
後から自分が読み返すためのものです。

`# Examples`（具体例）は慣習的な見出しです。外部の出典は frontmatter の `sources` に書きます。

```markdown
---
type: Preference
title: 豚骨に寄る
description: 選べるときは豚骨を選んでいる。
tags: [ラーメン, 傾向]
generated: { by: "process:note-keeper", at: 2026-09-12T17:00:00Z }
---

# 根拠

* 9/02 [二郎 三田](/shops/jiro-mita.md) を「行きたい」と言っていた
* 9/08 醤油と豚骨が並んだときに豚骨
* 9/12 同上

# 例外

* 朝は軽いものを選ぶ
```

## 相互リンク

関係は普通の markdown リンクで書きます。関係の種類は前後の文で表します。
OKF v0.2 は次の両方をサポートします。

- **バンドル相対**（`/` で始める）: `[三田](/shops/jiro-mita.md)`。バンドルのルートが基準です。仕様の推奨形式で、このアプリが生成する目次にも使います。
- **ファイル相対**: `[隣のメモ](./other.md)`、`[三田](../shops/jiro-mita.md)`。リンクを書くファイルのディレクトリが基準です。GitHub など普通の Markdown 表示でもたどれます。

`docs/system/` の開発ドキュメントでは、GitHub でたどれるファイル相対リンクを使います。
本文のリンク切れは構いません（まだ書いていない概念を指していることがあります）。`index.md` はこの限りではありません（下記）。

## 元の投稿へのリンク

メモを保存すると、アプリが今回の対象発言へのリンクを末尾の「記憶を更新した投稿」に自動で付けます。
この部分はアプリが管理し、書き直しても以前のリンクを保持します。自分で生成・編集する必要はありません。
別のメモへまとめるときは、元のメモを `notes_read` で読んでから書いてください。元のメモに保存されていた投稿リンクも引き継がれます。
本文の「根拠」には、どの発言から何を読み取ったかを引き続き書いてください。自動の投稿リンクは、解釈が正しいことを保証するものではありません。

## index.md

概念の frontmatter は付けません。ただしバンドルのルートの `index.md` に限り、任意の YAML frontmatter `okf_version: "0.2"` で対象バージョンを宣言できます。見出しごとに、リンクと description を並べた箇条書きです。

```markdown
# 傾向

* [豚骨に寄る](/tastes/tonkotsu.md) - 選べるときは豚骨を選んでいる。

# 店

* [ラーメン二郎 三田本店](/shops/jiro-mita.md) - 三田の豚骨。行きたいと言っていた店。
```

`index.md` は本体が確かめます。**どのメモも1回はリンクされ、存在しないメモへのリンクはありません。**
メモ係としてメモを `write` するときは、`section` に載せる見出しを1つ書きます（上の例なら `傾向` や `店`）。
本体がその見出しの下に、メモの title と description から1行を入れます（別の見出しにあった行は移し、見出しがなければ作ります）。
捨てたメモの行は本体が消します。見出しは担当の領域に合わせて分類し、関係のあるメモを同じ見出しにまとめます。
`index.md` を自分で全文書くのは、見出しの名前を変える・分け直すなど、分類そのものを直すときだけです。
見出しを決めなかったメモは、本体が「未整理」の見出しに置きます。分類し直すのはあなたの仕事です。

## log.md（任意）

日付ごと、新しい順。日付の見出しは `YYYY-MM-DD`。何を消したかも書いておくと後で困りません。

```markdown
# 更新履歴

## 2026-09-12
* **追加**: [三田](/shops/jiro-mita.md)
* **統合**: 個別の3件を [豚骨に寄る](/tastes/tonkotsu.md) にまとめ、元を捨てた
```

## 書くときの注意

- **description と冒頭の一段落が一番読まれます。** 一覧に出るのはそこです。薄いと思い出せません。
- **書く前に一覧を見てください。** 同じ話題のメモがすでにあるなら、新しいファイルを作らず、そこに書き足します。
  投稿のたびに1ファイル増えるのは、覚えているのではなく溜めているだけです。
- **概念を増やし続けないでください。** 同じことが3度出たら、まとめて元を捨てる。
  ファイルが増えるだけなら、分けた意味がありません。
- 1つのファイルに詰め込みすぎないでください。別の話になったら別のファイルにします。
- 書いたら確かめること: frontmatter があるか、`type` が空でないか、`index.md` が実態と合っているか。

## 仕様

[公式 OKF v0.2 仕様](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md)。必須なのは概念ファイルの YAML frontmatter と空でない `type` です。このスキルのメモ更新手順、分類制約、削除期限はアプリの運用ルールです。
